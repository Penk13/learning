Ch.1 · Trade-offs in data systems architecture

🛠 Operational vs 📊 Analytical

OLTPOLAP
Readpoint query by keyaggregate many rows
WriteCRUD single recordsbulk ETL / stream
Queriesfixed, in app codead hoc
Datalatest statehistory of events
SizeGB–TBTB–PB
  • Real-time/product analytics (Pinot, Druid, ClickHouse) = OLAP queries, low latency, user-facing.
  • HTAP = both in one system; doesn't replace the warehouse.

🏛 Warehouse · 🌊 Lake · 🔁 Pipelines

  • Warehouse = separate read-only copy, relational/SQL, for analysts.
  • Why separate: silos, wrong layout, perf impact on users, network/compliance.
  • ETL (or ELT) moves data in; SaaS via connectors.
  • Lake = files, any format, no schema; cheap object storage; for data scientists. Sushi principle: raw is better.
  • Streams → seconds-level analytics. Reverse ETL → results back to production.

📌 System of record vs derived

  • System of record: source of truth, written first, each fact once.
  • Derived: cache, index, materialized view, warehouse copy, ML model. Redundant; rebuildable.
  • Disagreement → system of record wins.
  • Role depends on how you use the tool, not the tool.

☁ Cloud vs 🏠 self-host

  • Core competency → in-house; commodity → vendor.
  • Self-host cheaper when: skills exist + load predictable.
  • Cloud better when: unfamiliar system, spiky load.
  • Cloud cons: no control, outages, no internals, lock-in, sanctions, trust for security.
  • Cloud native: separate storage & compute, object storage, local disk = cache, multitenant.
  • Ops: capacity planning → financial planning; still need security, monitoring, integration.

🌐 Distributed vs 🖥 single-node

  • Reasons: inherent, cross-service, fault tolerance, scalability, latency, elasticity, special hardware, legal residency, sustainability.
  • Costs: timeouts (did it happen?), network ≫ function call, hard debugging (observability/tracing), cross-service consistency.
  • Prefer single-node if it fits.
  • Microservices = people problem solution; own DB each.
  • Serverless = pay per execution; limits, cold starts.

⚖ Law & society

  • GDPR, CCPA, EU AI Act (locally: UU PDP).
  • Right to be forgotten vs immutable logs & derived data.
  • Storage cost includes leak, fine & user-safety risk.
  • Data minimization: purpose-limited, not kept longer than needed.
  • PCI (payments), SOC 2 Type 2 (vendors).
Design-review questions
  1. Is this workload operational or analytical? Are we running analytics on the OLTP database?
  2. What is the system of record for each piece of data? What is derived, and what keeps it in sync?
  3. Do we self-host or buy this? Is it core to us? How variable is the load? What's our exit plan from the vendor?
  4. Does this really need to be distributed — which reason applies? Could one node do it?
  5. If we split into services, how do we keep data consistent across them?
  6. What personal data do we keep, why, for how long — and can we actually delete it everywhere, including derived copies?
Terms (38)
Data-intensive application
App where data management (volume, change, consistency under failure/concurrency, availability) is a primary challenge — vs compute-intensive.
Frontend / backend
Frontend: client-side code (browser, mobile app), one user's data. Backend: server-side code handling requests for all users.
Data infrastructure
The databases, caches, message queues etc. a backend reads and writes.
Stateless
Forgets everything about a request once handled; anything persistent lives on the client or in data infrastructure. Easy to scale out.
Operational system / OLTP
Backend services where data is created; point queries and single-record writes, driven by users. Online transaction processing.
Analytical system / OLAP
Read-only copy of operational data optimized for aggregate queries by analysts and data scientists. Online analytical processing.
Point query
Look up a small number of records by key.
Business intelligence (BI)
Reports on an organization's activity to support management decisions.
Data engineer / analytics engineer
Data engineer: integrates operational and analytical systems, owns data infrastructure. Analytics engineer: models and transforms data for analysts.
Product / real-time analytics
Analytical (aggregate) queries embedded in user-facing products; real-time ingest, low latency (e.g. Pinot, Druid, ClickHouse).
Data warehouse
Separate database with a read-only, analysis-friendly copy of data from many OLTP systems.
Data silo
Data spread across separate systems, hard to combine in one query.
ETL / ELT
Extract–transform–load: pull from sources, reshape and clean, load into the warehouse. ELT transforms after loading.
HTAP
Hybrid transactional/analytical processing: OLTP and analytics in one system. Doesn't replace a warehouse.
Data lake
Central repository of files in any format, no imposed schema; often on object storage.
Sushi principle
"Raw data is better": keep data unprocessed so each consumer can transform it their own way.
Data pipeline
Generalized ETL: processes moving and transforming data between systems.
Reverse ETL
Making outputs of analytical systems (e.g. an ML model) available to operational systems.
System of record / source of truth
Holds the authoritative version of data; written first; each fact once (normalized). Wins any disagreement.
Derived data
Data produced by transforming other data (cache, index, materialized view, warehouse copy, ML model). Redundant; can be rebuilt from the source.
Self-hosting / on premises
Running software yourself — on your own hardware (even in a rented rack) or on cloud VMs.
IaaS
Infrastructure as a service: renting VMs (instances) with CPU, memory, disk, network; you administer the software.
SaaS
Software as a service: vendor builds and operates it; you use a web UI or API.
Vendor lock-in
High cost of switching providers, typically because there's no standard compatible API.
Cloud native
Architecture designed to take advantage of cloud services, built on lower-level cloud services (e.g. object storage).
Object storage
Cloud service storing large files (S3, Azure Blob, R2) across many machines; simpler API than a filesystem; no disk-space worries.
Separation of storage and compute (disaggregation)
Durable data lives in a storage service; compute nodes treat local disk as cache. Scale each independently; costs network transfer.
Multitenancy
Many customers' data and computation on the same shared hardware/service. Needs performance and security isolation.
DevOps / SRE
Shared responsibility for development and operations; SRE is Google's implementation. Emphasis on automation, ephemeral infrastructure, frequent updates, learning from incidents.
Distributed system / node
Several machines communicating over a network; each participating process is a node.
Elasticity
Automatically scaling resources up or down with demand, paying only for what you use.
Data residency
Laws requiring data about people in a jurisdiction to be stored/processed in that country.
Observability / tracing
Collecting execution data so both high-level metrics and individual events can be queried. Tracing (OpenTelemetry, Zipkin, Jaeger) tracks which service called which, and how long it took.
Microservices (SOA)
Application split into services with one purpose, an API and one owning team, each with its own database. Solves a people problem.
Serverless / FaaS
Cloud allocates resources per request; billed only for execution time. Limits: execution time, runtimes, cold starts.
HPC (supercomputing)
Large batch scientific computation; checkpoint and restart on failure; trusted users. Contrast: cloud services must stay continuously available.
Right to be forgotten
GDPR right to have personal data erased on request — hard with immutable logs and derived data.
Data minimization (Datensparsamkeit)
Collect and keep only data needed for a specified purpose, no longer than necessary.

Ch.2 · Defining nonfunctional requirements

🐦 Case study: home timelines

  • 5.8k posts/s (spikes 150k), 200 follows/followers avg, visible in 5 s.
  • Polling a join: 2M polls/s × 200 = 400M lookups/s.
  • Materialize (fan-out on write): 5.8k × 200 ≈ 1.16M writes/s; reads = cache.
  • Spikes → enqueue deliveries. Celebrities → store separately, merge at read. Super-followers → sample.

⚡ Performance

  • Response time (users care) vs throughput (cost).
  • Near capacity, queueing makes response time explode.
  • Retry storm → metastable failure. Fix: backoff + jitter, circuit breaker, load shedding, backpressure.
  • Response time = latency (network + queueing) + service time. Measure client-side.
  • Use percentiles (p50, p95, p99, p999), not mean.
  • Tail amplification: P(slow) = 1 − (1 − p)ⁿ
  • SLO = target; SLA = contract + consequences.
  • Never average percentiles → add histograms (HdrHistogram, t-digest, DDSketch).

🛡 Reliability

  • Fault (one part) ≠ failure (system misses SLO).
  • Find & remove SPOFs. Tolerance is always for certain faults.
  • Fault injection / chaos engineering. Prevent only where no cure (security).
TypeShapeDefence
Hardwaremostly independentredundancy → tolerate loss of machines/AZs; rolling upgrades
Softwarehighly correlatedtest assumptions, isolate, crash-restart, avoid retry loops, monitor
Humanconfig = top outage causetests, fast rollback, gradual rollout, observability, blameless postmortems

📈 Scalability

  • Ask "if load grows this way, what are our options?" — never "does it scale?"
  • Early product: simplicity > hypothetical scale.
  • Describe load: throughput, peaks, read:write, hit rate, items/user.
  • Linear scalability = 2× resources → 2× load.
  • Shared-memory (up) · shared-disk (NAS/SAN) · shared-nothing (out).
  • Rethink every ~10×; plan ≤ 1 order ahead. No magic scaling sauce.
  • Split into independent parts; don't over-complicate (5 services < 50).

🔧 Maintainability

  • Most cost is after launch; everything becomes legacy.
  • Operability: observability, no single-machine dependency, docs, defaults + overrides, self-heal + manual control, predictable. Automation is two-edged.
  • Simplicity: avoid big ball of mud; essential vs accidental (Brooks) — fuzzy line; weapon = abstraction.
  • Evolvability: loose coupling; minimize irreversibility.
Design-review questions
  1. What are our 2–3 load numbers, with current and peak values?
  2. What's our SLO in percentiles, measured from the client side?
  3. How close to capacity do we run at peak? What happens when clients retry?
  4. Which single fault would cause a user-visible failure today (SPOF)?
  5. Which faults are correlated (same code/config/dependency on every node)?
  6. How fast can we roll back a bad config? Do we roll out gradually? Are postmortems blameless?
  7. Which upcoming change is irreversible — and can we make it reversible?
Terms (44)
Functional / nonfunctional requirement
Functional: what the app does. Nonfunctional: how well — fast, reliable, scalable, maintainable, secure, compliant.
Polling
Client repeatedly re-sends a query to check for changes.
Fan-out
Factor by which one request multiplies into downstream requests (e.g. one post → one write per follower).
Materialization / materialized view
Precomputing a query's result and keeping it updated (e.g. the home-timeline cache). Faster reads, more work on writes.
Response time
Elapsed time from request to answer, as the client sees it; includes all delays. What users care about.
Throughput
Requests or data volume processed per second. Determines required resources and cost.
Service time
Time the service is actively processing the request.
Queueing delay
Time spent waiting (for a CPU, for an output buffer…). Not part of service time; rises sharply near capacity.
Latency / network latency
Catch-all for time a request is latent — not being processed. Network latency = time travelling through the network.
Jitter
Variation in network delay.
Head-of-line blocking
A few slow requests hold up the fast ones queued behind them.
Retry storm / metastable failure
Overload → timeouts → client retries → more load; system can stay overloaded even after load drops.
Exponential backoff · circuit breaker · token bucket
Client-side overload protection: increasing randomized waits between retries; temporarily stop calling a failing service; rate-limit retries.
Load shedding · backpressure
Server-side protection: proactively reject requests near overload; tell clients to slow down.
Percentile (p50, p95, p99, p999)
Sort response times; pX = threshold X% of requests are faster than. p50 = median.
Tail latency
High-percentile response times — the slowest experiences.
Tail latency amplification
When a request needs many backend calls, the chance at least one is slow grows: 1 − (1 − p)ⁿ.
SLO / SLA
Service level objective: target for performance/availability, often in percentiles. Service level agreement: contract saying what happens if the SLO is missed.
Reliability
Continuing to work correctly — expected function, tolerates user mistakes, good-enough performance, prevents abuse — even when things go wrong.
Fault
A particular part of a system stops working correctly (a disk, a machine, a dependency).
Failure
The system as a whole stops providing the required service — doesn't meet its SLO.
Fault-tolerant
Keeps serving users despite certain faults — always limited in number and type.
Single point of failure (SPOF)
A part whose fault escalates into failure of the whole system.
Fault injection / chaos engineering
Deliberately triggering faults (e.g. killing processes) so fault-tolerance machinery stays tested.
Availability zone
Cloud label for physically co-located resources, which are more likely to fail together.
Rolling upgrade
Restarting/patching one node at a time so the service never goes down.
Correlated (systematic) fault
Fault that hits many nodes at once because they share code, config or a dependency. Typical of software.
Cascading failure
A problem in one component overloads another, which brings down another…
Blameless postmortem
Incident review where people share full details without fear of punishment, so the organization learns.
Scalability
A system's ability to cope with increased load — having options for specific growth. Not a yes/no label.
Linear scalability
Doubling resources lets you handle double the load at the same performance.
Vertical scaling / shared-memory
Moving to a bigger machine; threads share RAM. Cost grows faster than linearly.
Shared-disk
Several machines with own CPU/RAM sharing a disk array over a fast network (NAS/SAN). Limited by locking and contention.
Horizontal scaling / shared-nothing
Many nodes each with own CPU, RAM, disks; coordination in software over a normal network. Can scale linearly; needs sharding.
Autoscaling
Automatically adding/removing resources in response to demand. Manual scaling may have fewer surprises if load is predictable.
Maintainability
Ease of keeping a system running and changing it over the long term = operability + simplicity + evolvability.
Legacy system
Long-lived system with outdated tech and lost institutional knowledge. Every valuable system becomes one.
Operability
Easy for the organization to keep the system running: observability, no single-machine dependency, clear operational model, good defaults, predictable behaviour.
Simplicity
Easy for new engineers to understand: well-understood consistent patterns, no unnecessary complexity.
Big ball of mud
A software project mired in complexity.
Essential vs accidental complexity
Essential: inherent in the problem domain. Accidental: from limitations of our tooling. The boundary shifts as tools evolve.
Abstraction
Clean façade hiding implementation detail (e.g. SQL hides storage, concurrency, crash recovery). Main tool for managing complexity.
Evolvability
Ease of changing a whole data system for new requirements — agility at system level.
Irreversibility
A change you can't undo (e.g. a migration with no way back). Major obstacle to evolvability; minimize it.

Ch.3 · Data models and query languages

🗃 Relational vs 📄 document

  • Relation = table, tuple = row (Codd 1970). NoSQL → document model; NewSQL → NoSQL scale + relational guarantees.
  • Impedance mismatch: objects ↔ tables. ORMs cut boilerplate, help caching and migrations, but make N+1 easy. Fix with a join or eager loading.
  • Doc weaknesses: can't reference nested items directly; whole doc loaded and rewritten → keep docs small.
  • Relational weaknesses: shredding trees; reorderable lists need tricks (fractional indexing).
  • Locality also via Spanner interleaving, Oracle clusters, Bigtable column families.
  • Converging: JSON in SQL; joins and indexes in Mongo/Couchbase.

⚖ Normalize vs denormalize

  • ID (normalized): consistent, unambiguous, update once, localizable, smarter search.
  • Normalized → fast writes, joins on read. Denormalized → fast reads, costly writes, copies drift.
  • Denormalized = derived data; needs a sync process (transactions or streams).
  • OLTP / moderate scale → normalize. Analytics → denormalize.
  • X timelines: store IDs, hydrate at read (app-level join). Copy what's slow-changing, keep fast-changing data normalized.

📐 Schema

  • "Schemaless" = schema-on-read (implicit; ≈ dynamic typing).
  • Schema-on-write = enforced (≈ static typing).
  • On-read suits heterogeneous data / external formats. On-write documents and enforces uniform data.
  • ADD COLUMN … DEFAULT NULL is fast; a full UPDATE rewrites every row.

⭐ Analytics schemas

  • Fact table: one row per event (huge, wide). Dimensions: who / what / where / when / how / why.
  • Star (simple) · snowflake (sub-dimensions, more normalized) · OBT (pre-joined).
  • Denormalizing is fine: history rarely changes.

🕸 Graphs

  • Property graph: vertex (id, label, in/out edges, props); edge (id, tail, head, label, props). = generalized join table.
  • Edges link only 2 vertices (else add a vertex / hypergraph).
  • Cypher -[:WITHIN*0..]-> = 4 lines; SQL WITH RECURSIVE = 31. GQL ISO 2024.
  • Triple store (subject, predicate, object), RDF/Turtle, SPARQL :within*.
  • Datalog: facts + rules → virtual tables; recursive rules traverse graphs.
  • GraphQL: client-shaped JSON for OLTP UIs; no recursion or arbitrary search (untrusted clients); any backend DB.

📜 Event sourcing + CQRS

  • Command → validate → event (immutable, past tense) → append to log → materialized views (projections / read models).
  • Views can't reject events; rebuild = delete + replay in the same order.
  • + intent, reproducible, many views, new views from old log, fewer irreversible actions, audit log, absorbs bursts.
  • − external data must be deterministic; GDPR vs immutability (crypto-shredding); no side effects on replay; ordering is hard when distributed.

🔢 DataFrames & arrays

  • Table-like, imperative command chains; join = merge.
  • Pivot to a sparse matrix; one-hot encoding for categories; then linear algebra / ML.
  • Array DBs (TileDB): rasters, imaging, astronomy.
Design-review questions
  1. Are our relationships mostly one-to-many, many-to-many, or "everything to everything"? Does our model match?
  2. Which fields are copied (denormalized)? What keeps the copies in sync, and what happens on a crash halfway?
  3. Is our schema enforced on write or assumed on read? Who handles old-format records?
  4. Any N+1 query patterns hiding behind the ORM? Check the query count per page.
  5. Do our documents stay small, or do we rewrite big documents for tiny updates?
  6. Would an append-only event log give us an audit trail or easier rebuilds? Can we meet deletion requests if we use one?
Terms (37)
Data model
How data is represented for the layer above: tables, JSON documents, graph, event log, DataFrame. Shapes how you think about the problem.
Declarative query language
States what result you want (conditions, sorting, grouping), not how. The query optimizer picks indexes, join algorithms and order. E.g. SQL, Cypher, SPARQL, Datalog.
Query optimizer
Database component that decides how to execute a declarative query.
Relational model / relation / tuple
Codd (1970): data as relations (SQL tables), each an unordered collection of tuples (rows).
NoSQL / NewSQL
NoSQL: 2010s set of ideas (new data models, schema flexibility, scaling, open source). NewSQL: NoSQL-style scale with relational model and transactions.
Document model
Data as self-contained documents, usually JSON. Fits trees of one-to-many relationships.
Impedance mismatch
The awkward translation between application objects and relational tables, rows and columns.
ORM
Object-relational mapping framework (e.g. ActiveRecord, Hibernate) that reduces translation boilerplate between objects and tables.
N+1 query problem
1 query fetches N records, then 1 extra query per record fetches related data. Fix with a join or eager loading.
One-to-many (one-to-few) / many-to-one / many-to-many
One parent, several children (a tree) / many records reference one shared record / both sides have many (needs a join table).
Join (associative) table
Table whose rows each link one ID on each side of a many-to-many relationship.
Normalization / denormalization
Normalized: human-meaningful data stored once, referenced by ID (fast writes, joins on read). Denormalized: copies stored where used (fast reads, costly writes, risk of drift). Denormalized data is a form of derived data.
Join
Resolving a reference (ID) into the record it points to, in the database or in application code.
Hydrating IDs
Looking up human-readable data for IDs at read time. A join in application code (e.g. X timelines).
Locality
Storing data that's read together in one place, so one read fetches it. Documents have it; also Spanner interleaving and Bigtable column families.
Shredding
Splitting a document-like tree into multiple relational tables.
Schema-on-read / schema-on-write
On-read: structure implicit, interpreted when read ("schemaless", like dynamic typing). On-write: schema explicit and enforced on every write (like static typing).
Schema migration
Changing the structure of stored data (e.g. ALTER TABLE). Big rewrites are slow and operationally risky.
Aggregation pipeline
MongoDB's JSON-syntax query language for filtering, grouping and joining ($lookup) documents.
Star schema / fact table / dimension table
Warehouse schema: central fact table (one row per event) with foreign keys to dimension tables (who, what, where, when, how, why).
Snowflake schema
Star schema whose dimensions are split into sub-dimensions. More normalized, more joins.
One big table (OBT)
Warehouse design that folds dimensions into the fact table (pre-joined). More storage, sometimes faster queries.
Graph / vertex / edge
Vertices (nodes, entities) connected by edges (relationships, arcs).
Property graph
Vertices and edges each have an ID, a label and key-value properties; edges have a tail (start) and head (end) vertex. E.g. Neo4j.
Cypher / GQL
Declarative property-graph query language (from Neo4j, now openCypher). GQL: ISO standard based on Cypher (2024).
Recursive CTE
SQL WITH RECURSIVE: expresses variable-length traversals, but clumsily compared with graph languages.
Triple store / RDF / SPARQL
Data as (subject, predicate, object) triples. RDF is the Semantic Web data model (written e.g. in Turtle). SPARQL is its query language.
Datalog
Older relational query language (subset of Prolog): facts plus rules that derive virtual tables. Rules can be recursive.
GraphQL
Client query language for OLTP UIs: the response JSON mirrors the requested shape. No recursion or arbitrary search, because clients are untrusted. Works on any backend.
Event sourcing
Store every state change as an immutable, past-tense event appended to a log. The log is the source of truth.
CQRS
Command query responsibility segregation: write to a write-optimized form (event log), and derive separate read-optimized views from it.
Command vs event
Command: a user request, validated first and possibly rejected. Event: a fact recorded after a valid command. Views may not reject events.
Projection / read model
A materialized view derived from an event log. Can be deleted and rebuilt by replaying the events in order.
Crypto-shredding
Encrypt personal data with a per-user key and delete the key to "erase" the data from an immutable log.
DataFrame
Table-like structure manipulated by a series of commands (R, Pandas, Spark). Join is called merge.
Sparse matrix / one-hot encoding
Matrix where most cells are empty / one 0-or-1 column per category value, turning categories into numbers for ML.
Array database
Database specialized in large multidimensional numeric arrays (e.g. TileDB): rasters, imaging, astronomy.

Ch.4 · Storage and retrieval

🪵 LSM-tree

  • Write → log (crash recovery) + memtable (sorted, RAM) → flush as immutable SSTable → background compaction (mergesort, newest wins).
  • SSTable: sorted, unique keys, sparse index per block, compressed blocks.
  • Delete = tombstone. Read = memtable → newest → oldest segment.
  • Bloom filter: 0 bit = definitely absent; all 1 = probably (false positive). ~10 bits/key ≈ 1%.
  • Size-tiered: write-heavy, big temp disk. Leveled: read-heavy, incremental, less disk.

🌳 B-tree

  • Fixed-size pages (4/8/16 KiB) overwritten in place; page refs form a tree.
  • Branching factor ~hundreds; depth O(log n), usually 3–4 levels.
  • Full page → split, update parent (maybe up to root).
  • WAL before page writes; guards against orphan/torn pages. fsync = durable.
  • Variants: copy-on-write (LMDB), abbreviated keys, sibling pointers.

⚖ B-tree vs LSM

  • Reads: B-tree predictable; LSM checks several SSTables. Range: Bloom filters useless.
  • Writes: B-tree random; LSM sequential (faster, even on SSDs: erase-block GC).
  • Write amplification = disk bytes ÷ plain-log bytes. Usually lower in LSM.
  • B-tree: fragmentation, vacuum. LSM: backpressure spikes, slow true deletes, cheap snapshots.
  • Always benchmark your own workload, long enough for compaction to kick in.

🔑 Indexes & memory

  • Secondary index: non-unique keys → list of row IDs, or key + row ID.
  • Clustered (row in index, InnoDB PK) · heap file + pointer (Postgres) · covering (some columns included).
  • Moved heap row → update all indexes or leave a forwarding pointer.
  • In-memory DBs fast because no on-disk encoding, not because no disk reads. Durability via log, snapshots, replicas.
  • Embedded engines (SQLite, RocksDB, DuckDB) run in-process; DB-per-tenant.

📊 Analytics storage

  • Cloud DW: object storage, storage/compute decoupled. Stack: query engine · storage format · table format (Iceberg, time travel) · catalog.
  • Column-oriented: same row order in every column; blocks per time range.
  • Bitmap per distinct value + RLE (roaring). IN → OR; across columns → AND.
  • Sort whole rows; first sort key compresses best. Writes in bulk via an LSM-like in-memory store.
  • Not to be confused with wide-column (Bigtable, HBase): row-oriented.

⚡ Execution & precompute

  • Query compilation (LLVM, JIT-like) vs vectorized batches of column values.
  • Both: sequential memory, tight loops, SIMD/threads, work on compressed data.
  • Materialized view = stored query result (more write work). Virtual view = saved query.
  • Data cube: grid of aggregates per dimension; fast but inflexible → keep raw data.

🔎 Search indexes

  • Concatenated (last, first): useless for "first name only".
  • Multidimensional: R-tree, Bkd-tree, space-filling curve, hex grids.
  • Inverted index: term → postings list (bitmap). n-grams for substring/regex. Edit distance via Levenshtein automaton.
  • Embeddings: 1,000+ floats; cosine or Euclidean distance. IVF (partitions, probes) · HNSW (layered graph). Used for RAG.
Design-review questions
  1. Is our workload read-heavy or write-heavy? Is the storage engine (B-tree or LSM) a match, and did we benchmark it on our data?
  2. Which indexes exist, which queries use them, and what does each one cost on writes?
  3. Do our reports run against the OLTP database? Should they run on a column store instead?
  4. When we delete personal data, how long until it's really gone (tombstones, compaction, backups)?
  5. Does search need exact words (inverted index), locations (spatial index), or meaning (vector index)?
  6. Are we keeping raw data, or only aggregates that can't answer tomorrow's question?

Extra structure derived from the primary data to speed up reads. Costs disk space and slows every write.
Storage engine
The part of a database that lays data out on disk/memory and finds it again (e.g. B-tree, LSM-tree, column store).
Hash index
In-memory hash map from key to byte offset in a log. Fast point lookups; no range queries, must fit in RAM.
SSTable (Sorted String Table)
Immutable file of key-value pairs sorted by key, each key once, split into (compressed) blocks.
Sparse index
Index storing only some keys (e.g. the first key of each block); scan the block to find the rest.
Memtable
Sorted in-memory structure (red-black tree, skip list, trie) receiving new writes before they're flushed as an SSTable.
Segment
One SSTable file in an LSM engine; written once, then immutable.
Compaction / merging
Background process combining segments mergesort-style, keeping the newest value per key and dropping overwritten or deleted data.
Tombstone
Special deletion record; tells compaction to discard older values for that key.
LSM-tree (Log-Structured Merge-tree)
Storage engine of memtable + cascading SSTables merged in the background (1996). RocksDB, Cassandra, ScyllaDB, HBase.
Bloom filter
Small bit array giving a fast, probabilistic "definitely not present" or "probably present" for a key.
False positive
A check says "present" when the item isn't (Bloom filter bits set by other keys).
Size-tiered / leveled compaction
Merge small SSTables into ever-larger ones (write-heavy) / fixed-size SSTables in key-range-partitioned levels L0, L1… (read-heavy, less disk).
Embedded database
Storage engine running as a library inside the application process, no network API (SQLite, RocksDB, LMDB, DuckDB).
B-tree
Balanced tree of fixed-size pages sorted by key, overwritten in place. Standard index in relational DBs.
Page
Fixed-size block (4 KiB traditionally; PostgreSQL 8 KiB, MySQL 16 KiB) referenced by page number.
Leaf page
Bottom B-tree page holding individual keys with their values or references to them.
Branching factor
Number of child-page references in one B-tree page; typically several hundred.
Page split
Splitting a full B-tree page into two half-full pages and adding the boundary to the parent.
Write-ahead log (WAL)
Append-only file every change is written to before it's applied to data pages; replayed after a crash. Journaling in filesystems.
Torn page / orphan page
Partially written page after a crash / page no longer referenced by any parent.
Copy-on-write
Write modified pages to a new location and create new parent versions instead of overwriting (LMDB).
Sequential vs random writes
Few large contiguous writes vs many small writes scattered across the disk. Sequential is faster, even on SSDs.
Write amplification
Bytes actually written to disk ÷ bytes a plain append-only log would write. Limits write throughput and wears SSDs.
Fragmentation / vacuum
Unused pages left inside B-tree files after deletes / background process that reorganizes them (PostgreSQL).
Backpressure
Engine pauses reads and writes when it can't flush and compact fast enough (e.g. RocksDB).
Primary key / secondary index
Unique identifier of a row, document or vertex / extra index on other columns, whose keys need not be unique.
Clustered index
Index storing the whole row inside it (InnoDB primary key).
Heap file
Unordered file holding rows; indexes point to row locations in it (PostgreSQL).
Covering index
Index that includes some extra columns so certain queries are answered from the index alone.
In-memory database
Serves all reads from RAM; may still log or snapshot to disk for durability (VoltDB, Redis, RAMCloud).
HTAP
Hybrid transactional/analytical processing: one product for both, increasingly two engines behind one SQL interface.
Query engine / storage format / table format / data catalog
Unbundled warehouse parts: runs SQL (Trino) / encodes rows into files (Parquet) / defines which files form a table, time travel (Iceberg, Delta) / lists tables (Polaris, Unity).
Row-oriented vs column-oriented storage
All values of a row stored together (OLTP) / all values of a column stored together, same row order in each (analytics).
Wide-column (column-family) model
Rows with many, varying columns (Bigtable, HBase). Despite the name, row-oriented.
Bitmap encoding
One bitmap per distinct column value, one bit per row. Filters become bitwise OR / AND.
Run-length encoding (RLE)
Store counts of consecutive repeated values (or 0s/1s) instead of each value. Roaring bitmaps switch forms.
Sort key (column store)
Column(s) whole rows are sorted by; speeds range scans and makes the first key compress very well.
Query compilation / vectorized processing
Generate and compile code per query (e.g. LLVM) / interpret, but run built-in operators over batches of column values.
SIMD
Single instruction, multiple data: one CPU instruction processes several values at once.
Materialized view / virtual view
Stored copy of a query's results, updated on change / saved query expanded at read time.
Data cube (OLAP cube)
Materialized grid of aggregates grouped by several dimensions. Fast, but can't answer questions outside its dimensions.
Concatenated index
Several fields joined into one key in a fixed order, like a phone book (last, first).
Multidimensional index / R-tree
Index for ranges on several columns at once / spatial index grouping nearby points in subtrees (PostGIS).
Full-text search
Search documents by keywords appearing anywhere in the text.
Inverted index / postings list
Term → list (or bitmap) of IDs of documents containing it. Lucene, PostgreSQL GIN.
n-gram
Substring of length n ("hel", "ell", "llo" are trigrams of hello); indexing them enables substring and regex search.
Edit distance / Levenshtein automaton
Number of single-letter insertions, deletions or replacements between words / structure Lucene uses to find words within an edit distance.
Semantic search
Search by meaning and intent, not exact words. Part of retrieval-augmented generation (RAG).
Vector embedding
Array of floats (often 1,000+) from an embedding model; similar meanings are close in space.
Cosine similarity / Euclidean distance
Closeness of two vectors by the angle between them / by straight-line distance.
Vector index: flat / IVF / HNSW
Compare with every vector (exact, slow) / search only nearest partitions, "probes" (approximate) / walk layered proximity graphs (approximate). Faiss, pgvector.
