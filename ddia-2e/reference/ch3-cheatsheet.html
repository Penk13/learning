🗃 Relational vs 📄 document

  • Relation = table, tuple = row (Codd 1970). NoSQL → document model; NewSQL → NoSQL scale + relational guarantees.
  • Impedance mismatch: objects ↔ tables. ORMs cut boilerplate, help caching and migrations, but make N+1 easy. Fix with a join or eager loading.
  • Doc weaknesses: can't reference nested items directly; whole doc loaded and rewritten → keep docs small.
  • Relational weaknesses: shredding trees; reorderable lists need tricks (fractional indexing).
  • Locality also via Spanner interleaving, Oracle clusters, Bigtable column families.
  • Converging: JSON in SQL; joins and indexes in Mongo/Couchbase.

⚖ Normalize vs denormalize

  • ID (normalized): consistent, unambiguous, update once, localizable, smarter search.
  • Normalized → fast writes, joins on read. Denormalized → fast reads, costly writes, copies drift.
  • Denormalized = derived data; needs a sync process (transactions or streams).
  • OLTP / moderate scale → normalize. Analytics → denormalize.
  • X timelines: store IDs, hydrate at read (app-level join). Copy what's slow-changing, keep fast-changing data normalized.

📐 Schema

  • "Schemaless" = schema-on-read (implicit; ≈ dynamic typing).
  • Schema-on-write = enforced (≈ static typing).
  • On-read suits heterogeneous data / external formats. On-write documents and enforces uniform data.
  • ADD COLUMN … DEFAULT NULL is fast; a full UPDATE rewrites every row.

⭐ Analytics schemas

  • Fact table: one row per event (huge, wide). Dimensions: who / what / where / when / how / why.
  • Star (simple) · snowflake (sub-dimensions, more normalized) · OBT (pre-joined).
  • Denormalizing is fine: history rarely changes.

🕸 Graphs

  • Property graph: vertex (id, label, in/out edges, props); edge (id, tail, head, label, props). = generalized join table.
  • Edges link only 2 vertices (else add a vertex / hypergraph).
  • Cypher -[:WITHIN*0..]-> = 4 lines; SQL WITH RECURSIVE = 31. GQL ISO 2024.
  • Triple store (subject, predicate, object), RDF/Turtle, SPARQL :within*.
  • Datalog: facts + rules → virtual tables; recursive rules traverse graphs.
  • GraphQL: client-shaped JSON for OLTP UIs; no recursion or arbitrary search (untrusted clients); any backend DB.

📜 Event sourcing + CQRS

  • Command → validate → event (immutable, past tense) → append to log → materialized views (projections / read models).
  • Views can't reject events; rebuild = delete + replay in the same order.
  • + intent, reproducible, many views, new views from old log, fewer irreversible actions, audit log, absorbs bursts.
  • − external data must be deterministic; GDPR vs immutability (crypto-shredding); no side effects on replay; ordering is hard when distributed.

🔢 DataFrames & arrays

  • Table-like, imperative command chains; join = merge.
  • Pivot to a sparse matrix; one-hot encoding for categories; then linear algebra / ML.
  • Array DBs (TileDB): rasters, imaging, astronomy.

Design-review questions (steal these)

  1. Are our relationships mostly one-to-many, many-to-many, or "everything to everything"? Does our model match?
  2. Which fields are copied (denormalized)? What keeps the copies in sync, and what happens on a crash halfway?
  3. Is our schema enforced on write or assumed on read? Who handles old-format records?
  4. Any N+1 query patterns hiding behind the ORM? Check the query count per page.
  5. Do our documents stay small, or do we rewrite big documents for tiny updates?
  6. Would an append-only event log give us an audit trail or easier rebuilds? Can we meet deletion requests if we use one?
