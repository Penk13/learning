DDIA 2nd ed. · Reference

Glossary

One meaning per term, used consistently in every lesson. Grows each chapter. [Ch.n] = where it's introduced (2nd edition numbering).

Chapter 1 · Trade-offs in data systems architecture

Data-intensive application
App where data management (volume, change, consistency under failure/concurrency, availability) is a primary challenge — vs compute-intensive. [Ch.1]
Frontend / backend
Frontend: client-side code (browser, mobile app), one user's data. Backend: server-side code handling requests for all users. [Ch.1]
Data infrastructure
The databases, caches, message queues etc. a backend reads and writes. [Ch.1]
Stateless
Forgets everything about a request once handled; anything persistent lives on the client or in data infrastructure. Easy to scale out. [Ch.1]
Operational system / OLTP
Backend services where data is created; point queries and single-record writes, driven by users. Online transaction processing. [Ch.1]
Analytical system / OLAP
Read-only copy of operational data optimized for aggregate queries by analysts and data scientists. Online analytical processing. [Ch.1]
Point query
Look up a small number of records by key. [Ch.1]
Business intelligence (BI)
Reports on an organization's activity to support management decisions. [Ch.1]
Data engineer / analytics engineer
Data engineer: integrates operational and analytical systems, owns data infrastructure. Analytics engineer: models and transforms data for analysts. [Ch.1]
Product / real-time analytics
Analytical (aggregate) queries embedded in user-facing products; real-time ingest, low latency (e.g. Pinot, Druid, ClickHouse). [Ch.1]
Data warehouse
Separate database with a read-only, analysis-friendly copy of data from many OLTP systems. [Ch.1]
Data silo
Data spread across separate systems, hard to combine in one query. [Ch.1]
ETL / ELT
Extract–transform–load: pull from sources, reshape and clean, load into the warehouse. ELT transforms after loading. [Ch.1]
HTAP
Hybrid transactional/analytical processing: OLTP and analytics in one system. Doesn't replace a warehouse. [Ch.1]
Data lake
Central repository of files in any format, no imposed schema; often on object storage. [Ch.1]
Sushi principle
"Raw data is better": keep data unprocessed so each consumer can transform it their own way. [Ch.1]
Data pipeline
Generalized ETL: processes moving and transforming data between systems. [Ch.1, detail Ch.11]
Reverse ETL
Making outputs of analytical systems (e.g. an ML model) available to operational systems. [Ch.1]
System of record / source of truth
Holds the authoritative version of data; written first; each fact once (normalized). Wins any disagreement. [Ch.1]
Derived data
Data produced by transforming other data (cache, index, materialized view, warehouse copy, ML model). Redundant; can be rebuilt from the source. [Ch.1]
Self-hosting / on premises
Running software yourself — on your own hardware (even in a rented rack) or on cloud VMs. [Ch.1]
IaaS
Infrastructure as a service: renting VMs (instances) with CPU, memory, disk, network; you administer the software. [Ch.1]
SaaS
Software as a service: vendor builds and operates it; you use a web UI or API. [Ch.1]
Vendor lock-in
High cost of switching providers, typically because there's no standard compatible API. [Ch.1]
Cloud native
Architecture designed to take advantage of cloud services, built on lower-level cloud services (e.g. object storage). [Ch.1]
Object storage
Cloud service storing large files (S3, Azure Blob, R2) across many machines; simpler API than a filesystem; no disk-space worries. [Ch.1]
Separation of storage and compute (disaggregation)
Durable data lives in a storage service; compute nodes treat local disk as cache. Scale each independently; costs network transfer. [Ch.1]
Multitenancy
Many customers' data and computation on the same shared hardware/service. Needs performance and security isolation. [Ch.1]
DevOps / SRE
Shared responsibility for development and operations; SRE is Google's implementation. Emphasis on automation, ephemeral infrastructure, frequent updates, learning from incidents. [Ch.1]
Distributed system / node
Several machines communicating over a network; each participating process is a node. [Ch.1, detail Ch.9]
Elasticity
Automatically scaling resources up or down with demand, paying only for what you use. [Ch.1]
Data residency
Laws requiring data about people in a jurisdiction to be stored/processed in that country. [Ch.1]
Observability / tracing
Collecting execution data so both high-level metrics and individual events can be queried. Tracing (OpenTelemetry, Zipkin, Jaeger) tracks which service called which, and how long it took. [Ch.1]
Microservices (SOA)
Application split into services with one purpose, an API and one owning team, each with its own database. Solves a people problem. [Ch.1]
Serverless / FaaS
Cloud allocates resources per request; billed only for execution time. Limits: execution time, runtimes, cold starts. [Ch.1]
HPC (supercomputing)
Large batch scientific computation; checkpoint and restart on failure; trusted users. Contrast: cloud services must stay continuously available. [Ch.1]
Right to be forgotten
GDPR right to have personal data erased on request — hard with immutable logs and derived data. [Ch.1, detail Ch.14]
Data minimization (Datensparsamkeit)
Collect and keep only data needed for a specified purpose, no longer than necessary. [Ch.1]

Chapter 2 · Defining nonfunctional requirements

Functional / nonfunctional requirement
Functional: what the app does. Nonfunctional: how well — fast, reliable, scalable, maintainable, secure, compliant. [Ch.2]
Polling
Client repeatedly re-sends a query to check for changes. [Ch.2]
Fan-out
Factor by which one request multiplies into downstream requests (e.g. one post → one write per follower). [Ch.2]
Materialization / materialized view
Precomputing a query's result and keeping it updated (e.g. the home-timeline cache). Faster reads, more work on writes. [Ch.2]
Response time
Elapsed time from request to answer, as the client sees it; includes all delays. What users care about. [Ch.2]
Throughput
Requests or data volume processed per second. Determines required resources and cost. [Ch.2]
Service time
Time the service is actively processing the request. [Ch.2]
Queueing delay
Time spent waiting (for a CPU, for an output buffer…). Not part of service time; rises sharply near capacity. [Ch.2]
Latency / network latency
Catch-all for time a request is latent — not being processed. Network latency = time travelling through the network. [Ch.2]
Jitter
Variation in network delay. [Ch.2]
Head-of-line blocking
A few slow requests hold up the fast ones queued behind them. [Ch.2]
Retry storm / metastable failure
Overload → timeouts → client retries → more load; system can stay overloaded even after load drops. [Ch.2]
Exponential backoff · circuit breaker · token bucket
Client-side overload protection: increasing randomized waits between retries; temporarily stop calling a failing service; rate-limit retries. [Ch.2]
Load shedding · backpressure
Server-side protection: proactively reject requests near overload; tell clients to slow down. [Ch.2]
Percentile (p50, p95, p99, p999)
Sort response times; pX = threshold X% of requests are faster than. p50 = median. [Ch.2]
Tail latency
High-percentile response times — the slowest experiences. [Ch.2]
Tail latency amplification
When a request needs many backend calls, the chance at least one is slow grows: 1 − (1 − p)ⁿ. [Ch.2]
SLO / SLA
Service level objective: target for performance/availability, often in percentiles. Service level agreement: contract saying what happens if the SLO is missed. [Ch.2]
Reliability
Continuing to work correctly — expected function, tolerates user mistakes, good-enough performance, prevents abuse — even when things go wrong. [Ch.2]
Fault
A particular part of a system stops working correctly (a disk, a machine, a dependency). [Ch.2]
Failure
The system as a whole stops providing the required service — doesn't meet its SLO. [Ch.2]
Fault-tolerant
Keeps serving users despite certain faults — always limited in number and type. [Ch.2]
Single point of failure (SPOF)
A part whose fault escalates into failure of the whole system. [Ch.2]
Fault injection / chaos engineering
Deliberately triggering faults (e.g. killing processes) so fault-tolerance machinery stays tested. [Ch.2]
Availability zone
Cloud label for physically co-located resources, which are more likely to fail together. [Ch.2]
Rolling upgrade
Restarting/patching one node at a time so the service never goes down. [Ch.2, detail Ch.5]
Correlated (systematic) fault
Fault that hits many nodes at once because they share code, config or a dependency. Typical of software. [Ch.2]
Cascading failure
A problem in one component overloads another, which brings down another… [Ch.2]
Blameless postmortem
Incident review where people share full details without fear of punishment, so the organization learns. [Ch.2]
Scalability
A system's ability to cope with increased load — having options for specific growth. Not a yes/no label. [Ch.2]
Linear scalability
Doubling resources lets you handle double the load at the same performance. [Ch.2]
Vertical scaling / shared-memory
Moving to a bigger machine; threads share RAM. Cost grows faster than linearly. [Ch.2]
Shared-disk
Several machines with own CPU/RAM sharing a disk array over a fast network (NAS/SAN). Limited by locking and contention. [Ch.2]
Horizontal scaling / shared-nothing
Many nodes each with own CPU, RAM, disks; coordination in software over a normal network. Can scale linearly; needs sharding. [Ch.2, detail Ch.7]
Autoscaling
Automatically adding/removing resources in response to demand. Manual scaling may have fewer surprises if load is predictable. [Ch.2]
Maintainability
Ease of keeping a system running and changing it over the long term = operability + simplicity + evolvability. [Ch.2]
Legacy system
Long-lived system with outdated tech and lost institutional knowledge. Every valuable system becomes one. [Ch.2]
Operability
Easy for the organization to keep the system running: observability, no single-machine dependency, clear operational model, good defaults, predictable behaviour. [Ch.2]
Simplicity
Easy for new engineers to understand: well-understood consistent patterns, no unnecessary complexity. [Ch.2]
Big ball of mud
A software project mired in complexity. [Ch.2]
Essential vs accidental complexity
Essential: inherent in the problem domain. Accidental: from limitations of our tooling. The boundary shifts as tools evolve. [Ch.2]
Abstraction
Clean façade hiding implementation detail (e.g. SQL hides storage, concurrency, crash recovery). Main tool for managing complexity. [Ch.2]
Evolvability
Ease of changing a whole data system for new requirements — agility at system level. [Ch.2]
Irreversibility
A change you can't undo (e.g. a migration with no way back). Major obstacle to evolvability; minimize it. [Ch.2]

Chapter 3 · Data models and query languages

Data model
How data is represented for the layer above: tables, JSON documents, graph, event log, DataFrame. Shapes how you think about the problem. [Ch.3]
Declarative query language
States what result you want (conditions, sorting, grouping), not how. The query optimizer picks indexes, join algorithms and order. E.g. SQL, Cypher, SPARQL, Datalog. [Ch.3]
Query optimizer
Database component that decides how to execute a declarative query. [Ch.3]
Relational model / relation / tuple
Codd (1970): data as relations (SQL tables), each an unordered collection of tuples (rows). [Ch.3]
NoSQL / NewSQL
NoSQL: 2010s set of ideas (new data models, schema flexibility, scaling, open source). NewSQL: NoSQL-style scale with relational model and transactions. [Ch.3]
Document model
Data as self-contained documents, usually JSON. Fits trees of one-to-many relationships. [Ch.3]
Impedance mismatch
The awkward translation between application objects and relational tables, rows and columns. [Ch.3]
ORM
Object-relational mapping framework (e.g. ActiveRecord, Hibernate) that reduces translation boilerplate between objects and tables. [Ch.3]
N+1 query problem
1 query fetches N records, then 1 extra query per record fetches related data. Fix with a join or eager loading. [Ch.3]
One-to-many (one-to-few) / many-to-one / many-to-many
One parent, several children (a tree) / many records reference one shared record / both sides have many (needs a join table). [Ch.3]
Join (associative) table
Table whose rows each link one ID on each side of a many-to-many relationship. [Ch.3]
Normalization / denormalization
Normalized: human-meaningful data stored once, referenced by ID (fast writes, joins on read). Denormalized: copies stored where used (fast reads, costly writes, risk of drift). Denormalized data is a form of derived data. [Ch.3]
Join
Resolving a reference (ID) into the record it points to, in the database or in application code. [Ch.3]
Hydrating IDs
Looking up human-readable data for IDs at read time. A join in application code (e.g. X timelines). [Ch.3]
Locality
Storing data that's read together in one place, so one read fetches it. Documents have it; also Spanner interleaving and Bigtable column families. [Ch.3]
Shredding
Splitting a document-like tree into multiple relational tables. [Ch.3]
Schema-on-read / schema-on-write
On-read: structure implicit, interpreted when read ("schemaless", like dynamic typing). On-write: schema explicit and enforced on every write (like static typing). [Ch.3]
Schema migration
Changing the structure of stored data (e.g. ALTER TABLE). Big rewrites are slow and operationally risky. [Ch.3]
Aggregation pipeline
MongoDB's JSON-syntax query language for filtering, grouping and joining ($lookup) documents. [Ch.3]
Star schema / fact table / dimension table
Warehouse schema: central fact table (one row per event) with foreign keys to dimension tables (who, what, where, when, how, why). [Ch.3]
Snowflake schema
Star schema whose dimensions are split into sub-dimensions. More normalized, more joins. [Ch.3]
One big table (OBT)
Warehouse design that folds dimensions into the fact table (pre-joined). More storage, sometimes faster queries. [Ch.3]
Graph / vertex / edge
Vertices (nodes, entities) connected by edges (relationships, arcs). [Ch.3]
Property graph
Vertices and edges each have an ID, a label and key-value properties; edges have a tail (start) and head (end) vertex. E.g. Neo4j. [Ch.3]
Cypher / GQL
Declarative property-graph query language (from Neo4j, now openCypher). GQL: ISO standard based on Cypher (2024). [Ch.3]
Recursive CTE
SQL WITH RECURSIVE: expresses variable-length traversals, but clumsily compared with graph languages. [Ch.3]
Triple store / RDF / SPARQL
Data as (subject, predicate, object) triples. RDF is the Semantic Web data model (written e.g. in Turtle). SPARQL is its query language. [Ch.3]
Datalog
Older relational query language (subset of Prolog): facts plus rules that derive virtual tables. Rules can be recursive. [Ch.3]
GraphQL
Client query language for OLTP UIs: the response JSON mirrors the requested shape. No recursion or arbitrary search, because clients are untrusted. Works on any backend. [Ch.3]
Event sourcing
Store every state change as an immutable, past-tense event appended to a log. The log is the source of truth. [Ch.3]
CQRS
Command query responsibility segregation: write to a write-optimized form (event log), and derive separate read-optimized views from it. [Ch.3]
Command vs event
Command: a user request, validated first and possibly rejected. Event: a fact recorded after a valid command. Views may not reject events. [Ch.3]
Projection / read model
A materialized view derived from an event log. Can be deleted and rebuilt by replaying the events in order. [Ch.3]
Crypto-shredding
Encrypt personal data with a per-user key and delete the key to "erase" the data from an immutable log. [Ch.3]
DataFrame
Table-like structure manipulated by a series of commands (R, Pandas, Spark). Join is called merge. [Ch.3]
Sparse matrix / one-hot encoding
Matrix where most cells are empty / one 0-or-1 column per category value, turning categories into numbers for ML. [Ch.3]
Array database
Database specialized in large multidimensional numeric arrays (e.g. TileDB): rasters, imaging, astronomy. [Ch.3]

Chapter 4 · Storage and retrieval

Log
An append-only sequence of records on disk, possibly binary. Not the same as application log text. [Ch.4]
Index
Extra structure derived from the primary data to speed up reads. Costs disk space and slows every write. [Ch.4]
Storage engine
The part of a database that lays data out on disk/memory and finds it again (e.g. B-tree, LSM-tree, column store). [Ch.4]
Hash index
In-memory hash map from key to byte offset in a log. Fast point lookups; no range queries, must fit in RAM. [Ch.4]
SSTable (Sorted String Table)
Immutable file of key-value pairs sorted by key, each key once, split into (compressed) blocks. [Ch.4]
Sparse index
Index storing only some keys (e.g. the first key of each block); scan the block to find the rest. [Ch.4]
Memtable
Sorted in-memory structure (red-black tree, skip list, trie) receiving new writes before they're flushed as an SSTable. [Ch.4]
Segment
One SSTable file in an LSM engine; written once, then immutable. [Ch.4]
Compaction / merging
Background process combining segments mergesort-style, keeping the newest value per key and dropping overwritten or deleted data. [Ch.4]
Tombstone
Special deletion record; tells compaction to discard older values for that key. [Ch.4]
LSM-tree (Log-Structured Merge-tree)
Storage engine of memtable + cascading SSTables merged in the background (1996). RocksDB, Cassandra, ScyllaDB, HBase. [Ch.4]
Bloom filter
Small bit array giving a fast, probabilistic "definitely not present" or "probably present" for a key. [Ch.4]
False positive
A check says "present" when the item isn't (Bloom filter bits set by other keys). [Ch.4]
Size-tiered / leveled compaction
Merge small SSTables into ever-larger ones (write-heavy) / fixed-size SSTables in key-range-partitioned levels L0, L1… (read-heavy, less disk). [Ch.4]
Embedded database
Storage engine running as a library inside the application process, no network API (SQLite, RocksDB, LMDB, DuckDB). [Ch.4]
B-tree
Balanced tree of fixed-size pages sorted by key, overwritten in place. Standard index in relational DBs. [Ch.4]
Page
Fixed-size block (4 KiB traditionally; PostgreSQL 8 KiB, MySQL 16 KiB) referenced by page number. [Ch.4]
Leaf page
Bottom B-tree page holding individual keys with their values or references to them. [Ch.4]
Branching factor
Number of child-page references in one B-tree page; typically several hundred. [Ch.4]
Page split
Splitting a full B-tree page into two half-full pages and adding the boundary to the parent. [Ch.4]
Write-ahead log (WAL)
Append-only file every change is written to before it's applied to data pages; replayed after a crash. Journaling in filesystems. [Ch.4]
Torn page / orphan page
Partially written page after a crash / page no longer referenced by any parent. [Ch.4]
Copy-on-write
Write modified pages to a new location and create new parent versions instead of overwriting (LMDB). [Ch.4]
Sequential vs random writes
Few large contiguous writes vs many small writes scattered across the disk. Sequential is faster, even on SSDs. [Ch.4]
Write amplification
Bytes actually written to disk ÷ bytes a plain append-only log would write. Limits write throughput and wears SSDs. [Ch.4]
Fragmentation / vacuum
Unused pages left inside B-tree files after deletes / background process that reorganizes them (PostgreSQL). [Ch.4]
Backpressure
Engine pauses reads and writes when it can't flush and compact fast enough (e.g. RocksDB). [Ch.4]
Primary key / secondary index
Unique identifier of a row, document or vertex / extra index on other columns, whose keys need not be unique. [Ch.4]
Clustered index
Index storing the whole row inside it (InnoDB primary key). [Ch.4]
Heap file
Unordered file holding rows; indexes point to row locations in it (PostgreSQL). [Ch.4]
Covering index
Index that includes some extra columns so certain queries are answered from the index alone. [Ch.4]
In-memory database
Serves all reads from RAM; may still log or snapshot to disk for durability (VoltDB, Redis, RAMCloud). [Ch.4]
HTAP
Hybrid transactional/analytical processing: one product for both, increasingly two engines behind one SQL interface. [Ch.4]
Query engine / storage format / table format / data catalog
Unbundled warehouse parts: runs SQL (Trino) / encodes rows into files (Parquet) / defines which files form a table, time travel (Iceberg, Delta) / lists tables (Polaris, Unity). [Ch.4]
Row-oriented vs column-oriented storage
All values of a row stored together (OLTP) / all values of a column stored together, same row order in each (analytics). [Ch.4]
Wide-column (column-family) model
Rows with many, varying columns (Bigtable, HBase). Despite the name, row-oriented. [Ch.4]
Bitmap encoding
One bitmap per distinct column value, one bit per row. Filters become bitwise OR / AND. [Ch.4]
Run-length encoding (RLE)
Store counts of consecutive repeated values (or 0s/1s) instead of each value. Roaring bitmaps switch forms. [Ch.4]
Sort key (column store)
Column(s) whole rows are sorted by; speeds range scans and makes the first key compress very well. [Ch.4]
Query compilation / vectorized processing
Generate and compile code per query (e.g. LLVM) / interpret, but run built-in operators over batches of column values. [Ch.4]
SIMD
Single instruction, multiple data: one CPU instruction processes several values at once. [Ch.4]
Materialized view / virtual view
Stored copy of a query's results, updated on change / saved query expanded at read time. [Ch.4]
Data cube (OLAP cube)
Materialized grid of aggregates grouped by several dimensions. Fast, but can't answer questions outside its dimensions. [Ch.4]
Concatenated index
Several fields joined into one key in a fixed order, like a phone book (last, first). [Ch.4]
Multidimensional index / R-tree
Index for ranges on several columns at once / spatial index grouping nearby points in subtrees (PostGIS). [Ch.4]
Full-text search
Search documents by keywords appearing anywhere in the text. [Ch.4]
Inverted index / postings list
Term → list (or bitmap) of IDs of documents containing it. Lucene, PostgreSQL GIN. [Ch.4]
n-gram
Substring of length n ("hel", "ell", "llo" are trigrams of hello); indexing them enables substring and regex search. [Ch.4]
Edit distance / Levenshtein automaton
Number of single-letter insertions, deletions or replacements between words / structure Lucene uses to find words within an edit distance. [Ch.4]
Semantic search
Search by meaning and intent, not exact words. Part of retrieval-augmented generation (RAG). [Ch.4]
Vector embedding
Array of floats (often 1,000+) from an embedding model; similar meanings are close in space. [Ch.4]
Cosine similarity / Euclidean distance
Closeness of two vectors by the angle between them / by straight-line distance. [Ch.4]
Vector index: flat / IVF / HNSW
Compare with every vector (exact, slow) / search only nearest partitions, "probes" (approximate) / walk layered proximity graphs (approximate). Faiss, pgvector. [Ch.4]
