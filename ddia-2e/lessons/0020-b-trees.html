B-Trees

The index in almost every relational database: fixed-size pages, overwritten in place, kept balanced.

Introduced in 1970 and called "ubiquitous" by 1979, the B-tree is the standard index in almost every relational database. Like SSTables, B-trees keep keys sorted, so point lookups and range queries are fast. Unlike them, a B-tree splits the database into fixed-size pages (traditionally 4 KiB; PostgreSQL 8 KiB, MySQL 16 KiB) and overwrites pages in place. Pages refer to child pages by page number, forming a tree.

Insert into a full page → split it into two half-full pages and add the new boundary to the parent. If the parent is full it splits too, possibly up to the root (then a new root grows on top). This keeps the tree balanced.

Making B-trees crash-safe

A split overwrites several pages. Crash halfway and you can get an orphan page (no parent points to it) or a half-written torn page. The fix is a write-ahead log (WAL): an append-only file where every change is written before the pages are touched. After a crash, replay it to restore consistency (filesystems call this journaling). Pages are buffered in memory for speed; once the WAL entry is fsynced, the write is durable.

🧬 Copy-on-write

LMDB writes modified pages to a new location and creates new parent versions, instead of overwriting plus WAL. Also helps concurrency (consistent snapshots).

✂ Abbreviated keys

Interior pages need only enough of a key to act as a boundary: more keys per page, higher branching factor, fewer levels.

↔ Sibling pointers

Leaf pages link to their neighbours, so range scans don't jump back up to parents.

Why does a B-tree storage engine need a write-ahead log?

B-trees overwrite pages in place. A crash during a multi-page split leaves orphan or torn pages. Changes go to the WAL first and are replayed after a crash.

What happens when you insert a key into a B-tree page that is already full?

The page is split into two half-full pages and the new boundary key is added to the parent page. If the parent is also full it splits too, possibly all the way up to the root, where a new root is created. This keeps the tree balanced.

What is a B-tree's branching factor, and why can a tree only 3–4 levels deep hold a huge database?

The number of child-page references in one page, typically several hundred. Capacity grows exponentially with depth: four levels of 4 KiB pages with a branching factor of 500 can hold up to about 250 TB, so lookups touch only a few pages.

How do B-trees and SSTables differ in how they store sorted keys on disk?

Both keep keys sorted. SSTables are immutable files written once and merged later (log-structured). B-trees divide data into fixed-size pages that are overwritten in place, with pages referencing child pages to form a balanced tree.
