Data Models and Query Languages

Tables, documents, graphs, event logs, DataFrames. Each one makes some data easy to express and other data awkward. The data model you pick shapes how you think about the problem.

⏱ ~30 min 📖 Book pp. 65–108 (2nd ed.) 🧰 Glossary · Ch.3 cheat sheet
Your one win for today: given a dataset, you can tell whether its relationships are mostly one-to-many (documents fit), many-to-many (relational or graph), or a history of changes (event sourcing). You can also say what normalizing or denormalizing it costs.

1 · Data models are stacked layers

Each layer represents its data using the layer below it, and hides that complexity from the layer above. This chapter covers layer 2. Chapter 4 covers layer 3.

Declarative query languages (SQL, Cypher, SPARQL, Datalog) say what result you want: the conditions, sorting, grouping. They don't say how to get it. The query optimizer picks the indexes, join algorithms and order of execution. The database can therefore get faster, or run your query in parallel across cores and machines, without you changing a line. With Python or Java you write the algorithm yourself.

2 · Relational vs document

The relational model (Codd, 1970) stores data as relations (SQL: tables), each an unordered collection of tuples (rows). By the mid-1980s it was the default choice, and it still dominates business analytics. Challengers came and went: the network and hierarchical models, object databases, XML databases. NoSQL in the 2010s brought new data models, flexible schemas, scaling and open source. NewSQL aimed for NoSQL-style scale while keeping relational transactions. The buzzwords faded, but one lasting effect remains: the document model (usually JSON), which most relational databases now also support.

The object-relational mismatch

App code uses objects. A relational database uses tables, rows and columns. The awkward translation between the two is called the impedance mismatch, a term borrowed from electronics. ORMs (ActiveRecord, Hibernate, also Django ORM and Entity Framework) remove the boilerplate, but they have catches:

👎 ORM downsides

They can't hide both models fully, so you still think in both. Analysts still query the underlying tables, so schema design still matters. Mostly OLTP + relational only. Auto-generated schemas can be awkward or inefficient. Easy to write slow queries by accident, e.g. N+1.

👍 ORM upsides

Some translation is unavoidable for relational data, so less boilerplate is a win for simple, repetitive cases. Some ORMs cache query results. Many also manage schema migrations.

One-to-many data is a tree, and documents fit trees

The book's example is a résumé (LinkedIn profile). One user has many positions, many education entries and contact info. Relational: split them into separate tables with foreign keys to users. Document: one JSON object with nested arrays.

3 · Normalization, denormalization, joins

Why does the profile store region_id: "us:91" and not the text "Washington, DC"? A standardized list gives you consistent spelling, no ambiguity between places with the same name, a single place to update a renamed city, localization into other languages, and smarter search (it knows DC is on the East Coast).

NormalizedDenormalized
WritesFaster: one copySlower: update every copy, more disk
ReadsSlower: needs joinsFaster: fewer joins
RiskJoin cost at very large scaleCopies drift apart. A crash halfway through an update needs atomic transactions across documents (not every DB has them) or stream processing (Ch.12)
FitsOLTP; small-to-moderate scale (the usual default)Analytics (bulk updates, read-heavy); hot read paths at huge scale

Think of denormalized data as derived data (Ch.1): you need a process that keeps the redundant copies up to date.

Back to the timelines from Ch.2

The materialized home timeline is a denormalized cache of a join. But X's timeline stores only IDs (post ID, sender ID), not the post text or like counts. At read time the service hydrates those IDs by looking up the post content and the sender's profile, which is effectively a join in application code. Why? Like counts change many times per second and people change their profile photos. Copying that into millions of timelines would be wrong and expensive.

The lesson: joins at read time don't stop you from scaling. Hydration parallelizes well, and its cost doesn't depend on follower counts. The best design often mixes the two: denormalize what rarely changes and is costly to compute, and keep fast-changing data normalized.
🧠 Pause & recall: a course-registration page shows each class's lecturer name and the live "seats left" count. Which would you denormalize into the class listing, and which would you keep as an ID? Lecturer name changes rarely, so copying it is cheap and safe (as long as a process keeps it updated). Seats-left changes constantly during registration, so keep it normalized (or look it up live). Copying it would go stale immediately, just like X's like counts.

4 · Many-to-one and many-to-many

One-to-many

One résumé → several positions; each position belongs to one résumé. A tree, so it fits documents.

Many-to-one

Many people → one region. A reference, so it fits normalization.

Many-to-many

A person worked at many orgs; an org has many employees. Needs a join (associative) table.

In a document model, the person document can hold org_id references inside its positions array. Many document DBs (and relational DBs with JSON) can index values inside documents. Storing the IDs on both sides (the person lists orgs, the org lists people) is denormalized, and the two lists can disagree.

5 · Stars and snowflakes: schemas for analytics

Data warehouses are usually relational and follow conventions built for analysts. ETL moves operational data into them.

⭐ Star

Fact table in the middle, dimension tables around it. Mostly many-to-one. Simpler for analysts, so usually preferred.

❄ Snowflake

Dimensions split into sub-dimensions (brand, category). More normalized, more joins.

📏 One big table (OBT)

Fold the dimensions into the fact table, i.e. pre-join it. More storage, sometimes faster queries.

Tables are wide: often 100+ columns. Fact tables can grow to petabytes. Denormalizing is fine here because the data is a log of history that rarely changes.

Schema-on-read vs schema-on-write

"Schemaless" is misleading. The reading code still assumes a structure. It's just implicit.

Schema-on-read

Structure interpreted when read. Like dynamic typing. Document DBs, JSON columns.

if (user && user.name && !user.first_name) {
  // old docs lack first_name
  user.first_name = user.name.split(" ")[0];
}

Every reader must handle old formats forever.

Schema-on-write

DB enforces structure on every write. Like static typing. Relational tables.

ALTER TABLE users
  ADD COLUMN first_name text DEFAULT NULL;
UPDATE users
  SET first_name = split_part(name, ' ', 1);

ADD COLUMN is fast. The UPDATE rewrites every row, which is slow on big tables. Online migration tools exist, but it's still hard to operate.

Schema-on-read wins when data is heterogeneous: many object types that don't merit a table each, or structure dictated by external systems that change anytime. When all records share a structure, a schema documents and enforces it. Debate: no clear winner, just like static vs dynamic typing. More on schema evolution in Ch.5.

Locality and query languages

  • A document is stored as one contiguous string (JSON, XML, BSON). That's great if you need most of it at once. It's wasteful if you need a small part, and an update rewrites the whole document. Keep documents small and avoid frequent small updates.
  • Locality isn't document-only: Spanner's interleaved tables, Oracle's multi-table index clusters, and Bigtable/HBase column families do the same.
  • Document query languages vary: key-value only, secondary indexes, or rich languages (XQuery/XPath, JSONPath, MongoDB's aggregation pipeline).
SQL · sharks per month
SELECT date_trunc('month', observation_timestamp)
         AS observation_month,
       sum(num_animals) AS total_animals
FROM observations
WHERE family = 'Sharks'
GROUP BY observation_month;
MongoDB aggregation pipeline
db.observations.aggregate([
  { $match: { family: "Sharks" } },
  { $group: {
      _id: { year:  { $year:  "$observationTimestamp" },
             month: { $month: "$observationTimestamp" } },
      totalAnimals: { $sum: "$numAnimals" } } }
]);

Same expressiveness, different syntax: SQL reads like English sentences, the pipeline like JSON. Mostly a matter of taste.

The models are converging. Relational DBs added JSON types, operators and indexes inside documents. Document DBs (MongoDB, Couchbase, RethinkDB) added joins, secondary indexes and declarative queries. Hybrids are powerful. Codd's 1970 paper even allowed nested relations ("nonsimple domains").

7 · Graph-like data models

Mostly one-to-many: use documents. Some many-to-many: relational handles it. Anything potentially related to everything: use a graph. A graph has vertices (nodes, entities) and edges (relationships, arcs). Examples: social graphs, the web graph (PageRank), road and rail networks (shortest path). A graph can also hold many different kinds of things in one store, like Facebook's single graph of people, places, events and comments, or a search engine's knowledge graph.

Property graph (Neo4j, Memgraph, KùzuDB…)

Vertex

ID · label (type) · outgoing edges · incoming edges · properties (key-value).

Edge

ID · tail vertex (start) · head vertex (end) · label (relationship kind) · properties.

You can store it as two relational tables, vertices and edges, with indexes on tail_vertex and head_vertex so you can traverse both ways. The edges table is a generalized join table. Any vertex can link to any other, and labels keep many kinds of data in one clean graph. Limitation: an edge connects only two vertices. Three-way relationships need an extra vertex or a hypergraph.

Four lines vs 31 lines

Query: find people who emigrated from the US to Europe. The hard part is that a person's BORN_IN edge may point at a city, a state or a country. You must follow WITHIN edges a variable number of times.

Cypher (graph) · 4 lines
MATCH
 (person) -[:BORN_IN]-> () -[:WITHIN*0..]-> (:Location {name:'United States'}),
 (person) -[:LIVES_IN]-> () -[:WITHIN*0..]-> (:Location {name:'Europe'})
RETURN person.name

*0.. = "follow WITHIN zero or more times", like * in a regex.

SQL · recursive CTE (excerpt of 31 lines)
WITH RECURSIVE
  in_usa(vertex_id) AS (
    SELECT vertex_id FROM vertices
      WHERE label = 'Location'
        AND properties->>'name' = 'United States'
    UNION
    SELECT edges.tail_vertex FROM edges
      JOIN in_usa ON edges.head_vertex = in_usa.vertex_id
      WHERE edges.label = 'within'
  ),
  in_europe(...) AS (...),
  born_in_usa(...) AS (...),
  lives_in_europe(...) AS (...)
SELECT ... JOIN born_in_usa ... JOIN lives_in_europe ...;

Each edge traversed is a join. SQL normally knows its joins in advance, but here the count isn't fixed, so you need WITH RECURSIVE. It's possible, but clumsy. The right data model and query language can make a huge difference. GQL, an ISO standard based on Cypher, was published in 2024. The optimizer can also run the query backwards: find "United States" and "Europe" by index, walk incoming WITHIN edges, then the BORN_IN and LIVES_IN edges.

Triple stores & SPARQL · Datalog · GraphQL

🔺 Triple store + SPARQL

Everything is (subject, predicate, object): (lucy, marriedTo, alain) is an edge, and (lucy, birthYear, 1989) is a property. Mostly equivalent to property graphs. Comes from RDF and the Semantic Web, so predicates are often URIs to avoid name clashes. Written in Turtle.

?person :bornIn / :within* / :name "United States".

SPARQL predates Cypher. Cypher borrowed its pattern matching.

📐 Datalog

Academic (1980s), a subset of Prolog. Relational, but great at recursion. Data = facts (rows). Queries = rules that derive virtual tables, built up step by step like functions calling functions.

within_recursive(Loc, Name) :- location(Loc, Name, _).
within_recursive(Loc, Name) :- within(Loc, Via),
                               within_recursive(Via, Name).

Rule 2 calls itself, which is how it traverses a graph.

🧩 GraphQL

Not a graph DB language. It's for OLTP clients (mobile, web) to ask for exactly the JSON shape the UI needs. The response mirrors the query. Deliberately limited, because queries come from untrusted clients: no recursion, no arbitrary search, so a client can't DoS the server. Only joins declared in the schema are allowed. Duplicates data in the response (sender name per message) to keep the UI simple. Runs on top of any database. Costs: tooling to reach REST/gRPC services, plus authorization, rate limiting and performance work.

🧠 Pause & recall: why can't a GraphQL client ask "find all students born in Jakarta who now live in Bandung", while Cypher can? GraphQL deliberately forbids arbitrary search conditions and recursive queries (unless the service owner explicitly exposes such a search), because its queries come from untrusted clients and could be expensive enough to cause a denial of service. Cypher is a full query language for trusted users of a graph database.

8 · Event sourcing and CQRS

Every model so far is queried in the same form it's written. Event sourcing breaks that: write in the form that's best for writing, then derive read-optimized forms. The simplest, fastest and most expressive way to write is an append-only log of immutable events.

A command is validated first. Only if it's valid does it become a fact, appended as an event. So the log contains only valid events, and a view builder may not reject an event. Name events in the past tense ("seats were booked"): a later cancellation doesn't erase the fact that the booking existed. Try it:

👍 Why it's attractive

  • Events state intent ("booking cancelled" vs "active=false on row 4001…").
  • Views are reproducible: delete, fix code, replay.
  • Many views, any data model, denormalized; even in-memory only.
  • New feature = new view from the old log; add event types freely.
  • Mistakes fixed by a compensating event, so fewer irreversible actions (evolvability, Ch.2).
  • Built-in audit log, useful in regulated domains.
  • Sequential appends absorb write bursts; views catch up later.

👎 Watch out for

  • External data (exchange rates) must be in the event or looked up as of the event time, or replays give different results.
  • Immutability vs GDPR deletion: per-user logs, keep personal data outside events, or crypto-shredding (delete the key). Each makes rebuilding harder.
  • Side effects on replay: don't resend confirmation emails.
  • All views must process events in exactly the same order, which is hard in distributed systems (Ch.10).

Tools: EventStoreDB, MartenDB (on PostgreSQL), Axon, or Kafka + stream processors (Ch.12). Compared with a star-schema fact table: both record past events, but event types differ in shape, and order matters (a fact table is unordered).

9 · DataFrames, matrices and arrays

These belong to analytics, data science and ML, rarely OLTP. A DataFrame (R, Pandas, Spark, Dask, ArcticDB) looks like a table and supports filter, group, aggregate and join (called merge). It's driven by a series of commands rather than declarative SQL, which matches how data scientists "wrangle" a private copy step by step.

Array databases (e.g. TileDB) store huge multidimensional arrays: geospatial rasters, medical imaging, telescope data. DataFrames are also common for financial time series and now live inside Spark and Flink (Ch.11).

Not covered, but they exist: genome sequence-similarity search (GenBank), double-entry ledgers (TigerBeetle; blockchains as distributed ledgers), and full-text search (Ch.4).

One model can emulate another (a graph in SQL tables), but often awkwardly. Specialist databases exist for each model, while general ones keep absorbing their neighbours' features. Non-relational models usually don't enforce a schema, yet your code still assumes one. The real question is explicit (on write) or implicit (on read).

10 · Practice: answer from memory

Scrolling up to check is cheating yourself. Recalling the answer now, with effort, is what makes it stick.

1. A student profile with addresses, emergency contacts and study history, always loaded whole on one page. Which model fits most naturally?
A tree of one-to-many (one-to-few) relationships loaded at once fits documents: better locality, no shredding into many tables.
2. Your ORM page runs 1 query for 200 comments, then 200 more for authors. Best fix?
That's the N+1 query problem. Do the join in the database (or tell the ORM to fetch authors with the comments): 1 round trip instead of 201.
3. Which statement about normalized data is generally true?
One copy makes writes cheap and consistent. Reads must resolve IDs with joins. Denormalized is the reverse, and analytics usually favours it.
4. X's materialized timelines store only post and sender IDs. Why not the post text and like count?
Like counts and profiles change constantly, and copying them into every timeline wastes storage. IDs are hydrated at read time, which parallelizes well.
5. Dimension tables are themselves split into sub-dimensions (brand, category). This is a…
Snowflake = more normalized star. Star is usually preferred for analyst simplicity. OBT goes the other way and folds dimensions into the fact table.
6. "Schemaless" document databases are more accurately described as…
Code reading the data still assumes a structure; the DB just doesn't enforce it. Like dynamic typing (vs schema-on-write ≈ static typing).
7. Why is "people born in the US who live in Europe" clumsy in plain SQL?
Each WITHIN hop is a join, and locations nest to varying depth. SQL needs WITH RECURSIVE (31 lines vs 4 in Cypher).
8. Why does GraphQL forbid recursive queries and arbitrary search conditions?
Expensive queries from clients could cause a denial of service. GraphQL is for OLTP UIs and can sit on any database.
9. A bug in a view's code corrupted it. In event sourcing, how do you recover?
Views are derived reproducibly from the immutable log, so delete them and rebuild by replaying the same events in the same order with the fixed code. Views may never reject events.
