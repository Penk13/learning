Storage and Retrieval

A database does two things: store the data you give it, and find it again when you ask. This chapter opens the hood. OLTP engines (LSM-trees, B-trees) and analytics engines (column stores) look completely different inside, because they serve different query patterns.

1 · The world's simplest database

The book starts with a key-value store made of two bash functions:

bash · a complete (terrible) database
db_set () { echo "$1,$2" >> database; }
db_get () { grep "^$1," database | sed -e "s/^$1,//" | tail -n 1; }

✍ Writes: great

Appending to the end of a file is the cheapest write there is. Updating a key just appends a new line; the old line stays. Many real databases use the same idea internally: a log, meaning an append-only sequence of records (not application logging text).

🔍 Reads: awful

db_get scans the whole file every time: O(n). Double the records, double the lookup time. To find things fast you need an index.

An index is derived data built from the primary data. It speeds up reads, but every index costs disk space and slows down every write, because it must be updated too. That's why databases don't index everything by default: you choose indexes from your query patterns.

2 · Log-structured storage

Step 1: a hash map of byte offsets

Keep appending to the log, but keep an in-memory hash map from each key to the byte offset of its latest value. A read becomes: look up the offset, seek, read. Problems: the log grows forever, the map must be rebuilt by scanning the log after a restart, the map must fit in RAM, and range queries (keys 10000–19999) are impossible without checking each key. So real databases rarely use hash indexes.

Step 2: SSTables (Sorted String Tables)

Store key-value pairs sorted by key, each key once. Now you don't need every key in memory: group pairs into blocks of a few KB, and keep only the first key of each block in a sparse index. Blocks can also be compressed (less disk and I/O, a bit more CPU).

Step 3: how do writes stay sorted? The LSM-tree

You can't append to a sorted file without breaking the order. The trick is a hybrid of a log and a sorted file:

To delete, append a tombstone: a marker saying "this key is gone". Merging discards older values under it. This design is the Log-Structured Merge-tree (LSM-tree, 1996), popularized by Google's Bigtable paper (which coined SSTable and memtable). Used by RocksDB, Cassandra, ScyllaDB, HBase. Play with it:

Bloom filters: skip segments that can't contain the key

Reading a key that's old, or missing entirely, means checking many segments. Each SSTable therefore carries a small Bloom filter: a bit array where each key sets a few hashed bit positions. Any 0 among a key's bits means definitely absent. All 1s means probably present (a false positive is possible, costing one wasted block read, never a wrong answer). Rule of thumb: 10 bits per key ≈ 1% false positives; every 5 more bits per key cuts that tenfold.

Compaction strategies

📦 Size-tiered

Merge newer, smaller SSTables into older, larger ones (four 256 MB → one ~898 MB, smaller thanks to overwrites and deletes). Handles very high write throughput. Big merges need lots of temporary disk space. Best for write-heavy.

🪜 Leveled

Fixed-size SSTables in levels L0, L1, L2… Each level beyond L0 is split by key range (L1: a–m, n–z), each bigger than the last. Overflow merges into the next level. Incremental, less disk, fewer SSTables per read. Best for read-heavy, or few hot keys written often.

Embedded storage engines (RocksDB, SQLite, LMDB, DuckDB, KùzuDB) are libraries running inside your process, called by functions instead of over a network. Common in mobile apps. On a backend they fit small data with few concurrent transactions, e.g. one database per tenant when tenants never need to be queried together.

3 · B-trees

The most widely used index structure: introduced 1970, called "ubiquitous" by 1979, the standard in almost every relational database. Like SSTables, B-trees keep keys sorted (so point lookups and range queries are fast). Unlike them, a B-tree splits the database into fixed-size pages (traditionally 4 KiB; PostgreSQL 8 KiB, MySQL 16 KiB) and overwrites pages in place. Pages point to child pages by page number, forming a tree.

Insert into a full page → split it into two half-full pages and add the new boundary to the parent. If the parent is full, it splits too, possibly up to the root (then a new root grows on top). This keeps the tree balanced.

Making B-trees crash-safe

A split overwrites several pages. Crash halfway and you get a corrupted tree (an orphan page) or a half-written torn page. The fix: a write-ahead log (WAL), an append-only file where every change is written before touching the pages. After a crash, replay it to restore consistency (filesystems call this journaling). Pages are buffered in memory for speed; once the WAL entry is fsynced, the write is durable.

🧬 Copy-on-write

LMDB writes modified pages elsewhere and creates new parent versions, instead of overwriting + WAL. Also helps concurrency (snapshot isolation, Ch.8).

✂ Abbreviated keys

Interior pages only need enough of a key to act as a boundary, so more keys per page, higher branching factor, fewer levels.

↔ Sibling pointers

Leaf pages link to left/right neighbours, so range scans don't jump back up to parents.

4 · B-trees vs LSM-trees

Rule of thumb: LSM-trees for write-heavy, B-trees for read-heavy. But benchmarks are sensitive to workload details: test with your workload. Engines also blend the two.

🌳 B-tree (update in place)🪵 LSM-tree (log-structured)
Point readsOne page per level; fast and predictableMay check several SSTables; Bloom filters help
Range queriesSimple and fast (sorted tree)Scan all segments in parallel and merge; Bloom filters can't help
WritesMany small random writes to pages anywhere on diskFew big sequential writes (whole segments) → higher write throughput
Write amplification≥ 2× (WAL + page), whole page rewritten for a few bytesLog + flush + each compaction; usually lower (no full pages, compressed blocks)
Disk spaceFragmentation after deletes; needs vacuum (PostgreSQL)Compaction rewrites anyway; compresses better. Stale values linger until compacted
GotchasSnapshots are harder (pages overwritten)Latency spikes / backpressure when compaction can't keep up; deletes take time to really vanish (tombstones), awkward for data-protection law
Used inAll major relational DBs, many othersRocksDB, Cassandra, ScyllaDB, HBase, Lucene
🧠 Pause & recall: why are sequential writes faster than random writes even on SSDs, which have no moving disk head? Flash is written per page (~4 KiB) but erased only per block (~512 KiB). Random writes leave blocks with a mix of valid and stale pages, so the SSD's garbage collector must copy the valid pages elsewhere before erasing. That uses write bandwidth and wears the drive. Sequential writes tend to fill whole blocks with one file, which can later be erased without that extra copying.

5 · Secondary indexes, values in the index, in-memory

A primary key uniquely identifies a row, document or vertex. A secondary index (CREATE INDEX) lets you search by other columns, like user_id in the Ch.3 résumé tables. Its keys are not unique, so each entry either holds a list of matching row IDs (like a postings list) or is made unique by appending a row ID. Both B-trees and LSM-trees can implement it.

Keeping everything in memory

Disks are awkward but durable and cheap per GB. As RAM gets cheaper, many datasets just fit in memory. Memcached is cache-only (lost on restart is fine). Durable in-memory DBs (VoltDB, SingleStore, Oracle TimesTen, RAMCloud) persist via a log on disk, snapshots, or replicas; Redis and Couchbase write to disk asynchronously (weak durability). Reads are served entirely from RAM.

Counterintuitive: in-memory DBs are not faster because they skip disk reads. With enough RAM, the OS page cache serves a disk-based engine from memory anyway. They're faster because they avoid encoding in-memory structures into an on-disk format. Bonus: they can offer data structures that are hard on disk, like Redis's priority queues and sets.

6 · Storage for analytics: column-oriented

A warehouse and an OLTP database both speak SQL, but the internals differ because the queries differ. HTAP products (SQL Server, SAP HANA, SingleStore) increasingly run two separate engines behind one SQL interface.

Cloud warehouses and the unbundled stack

BigQuery, Redshift and Snowflake keep data in object storage and decouple storage from compute (scale each independently, Ch.1). Open-source warehouses that used to be one system (Hive) are now separate parts:

⚙ Query engine

Parse, plan, run SQL in parallel. Trino, Presto, DataFusion (Spark/Flink for execution).

🧱 Storage format

How rows become bytes in files. Parquet, ORC, Lance, Nimble.

📒 Table format

Which immutable files make up a table, plus schema. Inserts/deletes, time travel, transactions. Iceberg, Delta.

🗂 Data catalog

Which tables a database has. Often a REST service (Polaris, Unity Catalog), also usable for discovery and governance.

Rows vs columns

A fact table can have 100+ columns and trillions of rows, but a typical analytics query touches 4–5 columns. A row store must still load and parse every full row. A column store keeps each column's values together, so the query reads only the columns it needs.

Don't confuse column-oriented storage with the wide-column (column-family) model of Bigtable, HBase and Accumulo. Wide-column databases are actually row-oriented: they store all of a row's values together.

Column compression: bitmaps and run-length encoding

Columns repeat a lot, so they compress well. A column with few distinct values (100,000 products vs billions of sales) becomes one bitmap per value: bit k = 1 if row k has that value. Sparse bitmaps are then run-length encoded (store counts of consecutive 0s and 1s). Roaring bitmaps switch between the two forms, whichever is smaller.

Sort order and writes

  • Rows can be stored in insertion order, or sorted like an SSTable. Sort whole rows (never each column separately, or rows can't be rebuilt). Pick sort keys from common queries: date_key first if queries target date ranges, then product_sk.
  • Bonus: the first sort key gets long runs of equal values, so RLE shrinks it to kilobytes even for billions of rows. Later sort keys compress less.
  • Inserting one row into the middle of sorted, compressed columns would rewrite everything after it. So writes are bulk (ETL), using the LSM idea: an in-memory, row-oriented sorted store that is merged into new column files in batches. Queries combine both, so analysts see changes immediately. Immutable files suit object storage.

7 · Query execution, materialized views, data cubes

Scanning millions of rows makes CPU time, not just disk reads, a bottleneck. A naive interpreter that checks the query plan for every row is too slow. Two fixes:

🛠 Query compilation

Generate code for this specific query, compile it to machine code (often with LLVM), and run it over the column data in memory. Like a JIT in the JVM.

📦 Vectorized processing

Still interpreted, but each built-in operator processes a batch of column values at once. E.g. "product = bananas" → a bitmap; "store = X" → a bitmap; bitwise AND → matching sales.

Both exploit modern CPUs: sequential memory access (fewer cache misses), tight inner loops (no branch mispredictions), parallelism (threads + SIMD), and working directly on compressed data.

Materialized views and data cubes

A virtual view is a saved query, expanded at read time. A materialized view is an actual stored copy of the results that must be updated when the data changes: more write work, faster repeated reads (the Ch.2 home timelines were one). 8 · Multidimensional, full-text and vector indexes

Concatenated vs multidimensional

A concatenated index joins fields into one key, like a phone book sorted by (last name, first name). It finds a last name, or last + first, but is useless for first name alone. A map query ("restaurants inside this rectangle") needs latitude and longitude ranges at once, which a concatenated index can't do.

🗺 Spatial indexes

R-trees and Bkd-trees group nearby points in the same subtree (PostGIS uses R-trees via PostgreSQL's GiST). Alternatives: a space-filling curve mapped onto a normal B-tree, or grids of triangles/squares/hexagons.

📐 Not just maps

(red, green, blue) for product colours; (date, temperature) to find days of 25–30 °C in one year. A 2-D index narrows both at once instead of scanning one and filtering the other.

Full-text search: the inverted index

  • n-grams: index every substring of length n ("hello" → hel, ell, llo). Allows arbitrary substring and even regex search; the index gets big.
  • Typos: Lucene finds words within an edit distance (1 = one letter added, removed or replaced) using a trie-like automaton turned into a Levenshtein automaton.
  • Real language handling (word splitting in languages without spaces, grammar forms, synonyms) is a specialist field outside the book.

Vector embeddings: search by meaning

Semantic search finds "canceling your subscription" when the user types "how to close my account". An embedding model (often an LLM) turns each document into a vector embedding: an array of floats (often 1,000+) marking a point in space, where similar meanings land close together. Distance is measured with cosine similarity (angle) or Euclidean distance (straight line). It's a core part of retrieval-augmented generation (RAG).

Two meanings of "vector": in vectorized processing (§7) it's a batch of values processed by tight CPU code. In embeddings it's an array of floats marking a point in space.

OLTP engines are optimized for many small key-based reads and writes (B-trees, LSM-trees). Analytics engines are optimized for scanning huge numbers of rows (columns, compression, vectorized or compiled execution). Knowing the internals tells you which tool fits, and what a tuning knob will do.

9 · Practice: answer from memory

Scrolling up to check is cheating yourself. Recalling the answer now, with effort, is what makes it stick.

1. You add three new secondary indexes to a busy table. What is the main cost?
Indexes are derived data: they speed up the reads they serve, but use disk space and add work to every insert, update and delete.
2. In an LSM-tree, where does a new write go first (besides the crash-recovery log)?
Writes go to the memtable (and the log). When it's full it's flushed as a new immutable SSTable; background compaction merges segments later.
3. A segment's Bloom filter says a key is "probably present". What follows?
"All bits 1" may be a coincidence caused by other keys. You check the block; if it's a false positive you just keep searching older segments. A 0 bit would mean "definitely absent".
4. Why does a B-tree need a write-ahead log?
B-trees overwrite pages in place. A crash during a multi-page split leaves orphan or torn pages. Changes are written to the WAL first, then replayed after a crash.
5. A sensor platform ingests huge volumes of writes and reads rarely. Which engine is the safer first bet?
LSM-trees turn writes into big sequential writes with lower write amplification; size-tiered compaction favours write throughput. Still: benchmark with your real workload.
6. Why can in-memory databases beat disk-based ones even when the disk DB's data is all in the OS cache?
The speed-up comes from avoiding the overhead of encoding in-memory structures into an on-disk format. Many still write a log or snapshots to disk for durability.
7. A report query uses 4 of a fact table's 150 columns over 2 billion rows. Why is a column store faster?
Values of each column are stored together, so the query skips the other 146 columns. Columns also compress well (bitmaps, RLE). Columns are never sorted independently, or rows couldn't be rebuilt.
8. An index on (last_name, first_name) exists. Which query can it NOT serve efficiently?
A concatenated index is sorted by the first field, then the second. Like a phone book, it can't find everyone with a given first name without scanning.
9. A help-desk search should find "reset my password" when users type "can't log in". What index fits?
The words don't overlap, but the meaning does: semantic search with embeddings and a vector index (flat, IVF or HNSW, e.g. pgvector). Full-text and n-gram indexes match words, not meaning.
