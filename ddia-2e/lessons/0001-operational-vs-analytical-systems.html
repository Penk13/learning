DDIA · Ch.1 Trade-Offs in Data Systems Architecture

Operational vs Analytical Systems

The same data gets used in two very different ways. Many arguments about databases start from mixing them up.

An app is data-intensive when managing data is a primary challenge: big volumes, data that keeps changing, staying consistent through failures and concurrency, staying available. (Compute-intensive = the hard part is a huge calculation.) Nobody builds this from scratch: application code glues standard building blocks together.

No approach is fundamentally better; everything has pros and cons. The skill is asking the right questions to compare them.

Two ways to use the same data

🛠 Operational (OLTP)

Backend services where data is created. App code reads and modifies data based on user actions. Built by backend engineers.

📊 Analytical (OLAP)

A read-only copy of operational data, optimized for analysis. Used by business analysts (BI reports) and data scientists.

🔗 Bridge roles

Data engineers integrate both sides and own the data infrastructure. Analytics engineers model and transform data for analysts.

OLTP users can't write custom SQL (security and performance); analysts can, or use dashboards. A hybrid exists: product / real-time analytics (Pinot, Druid, ClickHouse) runs aggregate queries, but with low latency, inside a user-facing product.

Example. "Show this student's class schedule" is OLTP: one key, latest state, an end user. "Total registrations per faculty this semester" is OLAP: an aggregate over many records, for a decision-maker.

Why not run analytics on the OLTP database?

SQL works for both, and early on the same database did both. Since the late 1980s, analytics moved to a separate data warehouse, for four reasons:

🏝 Data silos

Data is spread over dozens or hundreds of OLTP systems, hard to combine in one query.

📐 Wrong layout

Schemas and storage good for OLTP are poor for analytics.

🐢 Hurts users

Expensive analytic queries slow the app for everyone.

🔒 Access rules

OLTP may sit in a network analysts can't reach, for security or compliance.

"Fetch this student's current grades by student ID." Which access pattern is this?

A few records, looked up by key, latest state, for an end user: an OLTP point query.

Name four differences between operational (OLTP) and analytical (OLAP) systems.

Reads: point queries by key vs aggregates over many records. Writes: single-record CRUD vs bulk ETL or streams. Queries: fixed in app code vs ad hoc. Data: latest state vs history of events. Also users (end users vs analysts) and size (GB–TB vs TB–PB).

A dashboard counts helpdesk tickets per category per month. A separate screen shows one ticket's current status to the person who filed it.

Which part is operational and which is analytical, and why?

The ticket-status screen is operational: a point lookup by key, latest state, for an end user. The monthly counts are analytical: an aggregate over many records and over time, for decision support.

SQL works fine on operational databases. So why do organizations copy data into a separate data warehouse for analytics? Give the four reasons.

Data silos: data is spread across many OLTP systems and can't be combined in one query. Wrong layout: schemas good for OLTP are poor for analytics. Performance: expensive analytic queries would slow the app for users. Access: OLTP systems may sit in networks analysts can't reach, for security or compliance.
