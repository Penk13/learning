DDIA · Ch.2 Defining Nonfunctional Requirements

Response Time, Queueing and Overload

What "fast" means, why it collapses near capacity, and how a busy system can get stuck in failure.

⏱ Response time

Time from request to answer, as the user sees it. What users care about.

🚚 Throughput

Requests (or data volume) per second. Decides how many machines you need, i.e. cost.

They're linked by queueing: as throughput nears the hardware's maximum, each new request waits for earlier ones, and response time shoots up.

When an overloaded system won't recover. Slow responses → clients time out and retry → even more load → a retry storm. The system can stay stuck even after the original load drops: a metastable failure. Defences:
  • Client side: exponential backoff with randomness; a circuit breaker or token bucket to stop calling a failing service for a while.
  • Server side: load shedding (reject early when near overload); backpressure (tell clients to slow down).

Four timing words, used precisely

  • Service time: the service is actively processing the request.
  • Queueing delay: waiting for a CPU, an output buffer, earlier requests. Rises sharply near capacity.
  • Latency: catch-all for time a request is latent; network latency is time in transit.
  • Response time: all of the above, as seen by the client.

Why do identical requests take different times? Context switches, lost packets and TCP retransmission, garbage-collection pauses, page faults, even rack vibration. And head-of-line blocking: a few slow requests hold up the fast ones queued behind them. Variation in network delay is called jitter.

A service near capacity slows down; clients time out and resend; it stays down even after traffic drops. What is this called?

Retries add load to an already overloaded system, which can then stay overloaded on its own. Fix with exponential backoff, circuit breakers, load shedding and backpressure.

Your server logs say p99 = 80 ms, but users complain about 2-second waits.

Where could the missing time be, and how should you measure instead?

Server logs measure service time only. The missing time is queueing delay before processing starts (e.g. head-of-line blocking behind slow requests) and network latency. Measure response time on the client side.

Distinguish response time, service time, queueing delay and latency.

Service time: the server actively working on the request. Queueing delay: time waiting for resources or for earlier requests. Latency: any time the request is latent (not being processed), e.g. network latency in transit. Response time: everything the client sees, from sending the request to getting the answer.

Name two client-side and two server-side defences against overload and retry storms.

Client side: exponential backoff with randomness (jitter) between retries; a circuit breaker or token bucket that stops calling a failing service for a while. Server side: load shedding (reject requests early near overload) and backpressure (tell clients to slow down).
