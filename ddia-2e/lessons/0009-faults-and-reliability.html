DDIA · Ch.2 Defining Nonfunctional Requirements

Faults, Failures and Reliability

Parts will break. Reliability means the system as a whole keeps working anyway.

"Working correctly" = does what users expect, tolerates user mistakes, performs well enough under expected load, and prevents unauthorized access. Reliability ≈ continuing to work correctly even when things go wrong.

  • Fault-tolerant = keeps serving users despite certain faults, always limited ("up to 2 disks", "1 of 3 nodes").
  • Fault injection: deliberately kill processes so recovery code is exercised constantly; many critical bugs are just poor error handling. The discipline is chaos engineering.
  • Prevent rather than tolerate where no cure exists, e.g. security: leaked data can't be un-leaked.

Why software faults are the scariest: redundancy assumes faults are independent. If all replicas run the same bug, they fail together, at the same instant.

Blameless culture. "Bob should have been more careful" doesn't help. When a preventable mistake happens, the problem is usually the organization's priorities (features over resilience), not the person. Blameless postmortems let people share full details so everyone learns.

How much does it matter? A few minutes of downtime is often tolerable; permanent data loss or corruption is catastrophic. In the UK Post Office Horizon scandal, accounting-software bugs led to hundreds of wrongful theft and fraud convictions. Cutting reliability corners (say, for a prototype) can be fine, but do it consciously.

One disk in a 3-node database cluster dies. Users notice nothing. In DDIA's terms, this was…

A component stopped working (fault), but the system still met its SLO, so there was no failure. Fault tolerance worked.

Which kind of fault is least helped by adding more replicas or servers, and why?

Software faults. Every replica runs the same code, so a bug triggered by the same input or condition hits them all at once (correlated faults). Redundancy only helps against independent faults, like most hardware faults.

An operator pushes a bad configuration change and takes the service down. A manager wants to know who to blame.

How does DDIA frame this incident, and what defences does it suggest?

"Human error" is a symptom of the sociotechnical system, not the root cause; the fix is in the system and priorities, not blaming a person. Defences: testing, fast config rollback, gradual rollouts, monitoring and observability, interfaces that make the right thing easy, and blameless postmortems so people share full details.

What is fault injection (chaos engineering), and why deliberately cause faults?

Deliberately triggering faults, such as killing processes or machines, in a running system. It keeps the fault-tolerance and recovery code constantly exercised, because many critical bugs hide in rarely run error-handling paths.
