DDIA · Ch.3 Data Models and Query Languages

Graph Data Models

When anything can relate to anything, model it as vertices and edges, and query it with a language built for traversal.

Mostly one-to-many: documents. Some many-to-many: relational. Anything potentially related to everything: a graph of vertices (entities) and edges (relationships). Examples: social graphs, the web graph, road networks. One graph can also hold many kinds of things, like a search engine's knowledge graph.

Property graphs (Neo4j, Memgraph, KùzuDB)

  • Vertex: ID, label (type), outgoing and incoming edges, properties (key-value).
  • Edge: ID, tail vertex (start), head vertex (end), label (relationship kind), properties.

You can store it as two relational tables, vertices and edges, indexed on tail_vertex and head_vertex to traverse both ways. The edges table is a generalized join table. Limitation: an edge links only two vertices.

Four lines vs thirty-one

Query: people who emigrated from the US to Europe. A BORN_IN edge may point at a city, a state or a country, so you follow WITHIN edges a variable number of times.

MATCH
 (person) -[:BORN_IN]->  () -[:WITHIN*0..]-> (:Location {name:'United States'}),
 (person) -[:LIVES_IN]-> () -[:WITHIN*0..]-> (:Location {name:'Europe'})
RETURN person.name

In Cypher, *0.. means "zero or more times", like * in a regex. In SQL, each hop is a join and the number of joins isn't known in advance, so you need a WITH RECURSIVE common table expression: about 31 lines. The right model and query language make a huge difference. GQL, an ISO standard based on Cypher, was published in 2024.

Triple stores, Datalog, GraphQL

  • Triple store + SPARQL: everything is (subject, predicate, object). (lucy, marriedTo, alain) is an edge; (lucy, birthYear, 1989) is a property. Mostly equivalent to property graphs; comes from RDF and the Semantic Web. SPARQL predates Cypher, which borrowed its pattern matching.
  • Datalog: an older relational language (a subset of Prolog) that's great at recursion. Data = facts; queries = rules that derive virtual tables. A rule that calls itself traverses a graph.
  • GraphQL: not a graph-database language. It lets OLTP clients ask for exactly the JSON shape a UI needs, on top of any database. Queries come from untrusted clients, so it deliberately allows no recursion and no arbitrary search: a client must not be able to send a query expensive enough to take the server down.

Why is "find people born in the US who now live in Europe" clumsy in plain SQL over a graph of locations?

Each WITHIN hop is a join, and locations nest to varying depth. SQL needs WITH RECURSIVE (about 31 lines vs 4 in Cypher).

Why does GraphQL deliberately forbid recursive queries and arbitrary search conditions, while Cypher allows them?

GraphQL queries come from untrusted clients (mobile and web apps), and a recursive or arbitrary search could be expensive enough to cause a denial of service. Cypher is a full query language for trusted users of a graph database.

What does a property graph store for each vertex and each edge, and how can it be stored in a relational database?

Vertex: ID, label, incoming and outgoing edges, properties. Edge: ID, tail (start) vertex, head (end) vertex, label, properties. Relationally: a vertices table and an edges table, with indexes on tail_vertex and head_vertex so traversal works in both directions; the edges table is a generalized join table.

In a triple store, how are "Lucy is married to Alain" and "Lucy was born in 1989" each represented?

Both as (subject, predicate, object) triples: (lucy, marriedTo, alain), where the object is another vertex so it acts as an edge, and (lucy, birthYear, 1989), where the object is a value so it acts as a property.
