DDIA · Ch.2 Defining Nonfunctional Requirements

Maintainability

Most of software's cost comes after launch. Be kind to the people who run it and change it next.

Software doesn't wear out, but requirements change, platforms change and bugs need fixing. Every valuable system eventually becomes a legacy system: outdated technology, knowledge that left with former staff. Maintenance is as much a people problem as a technical one. Maintainability has three parts:

⚙ Operability

Easy for the organization to keep the system running.

"Good operations can often work around bad software, but good software cannot run reliably with bad operations."

Automation is two-edged: the cases it can't handle are the hardest ones, so more automation needs a more skilled ops team, and a misbehaving automated system is harder to debug.

Data systems help with: monitoring and observability, no dependency on single machines, documentation and a clear "if I do X, Y happens" model, good defaults with overrides, self-healing with manual control, predictable behaviour.

🧩 Simplicity

Easy for new engineers to understand.

Complexity slows everyone down and hides bugs: a big ball of mud.

Essential vs accidental complexity (Brooks, "No Silver Bullet"): inherent in the problem vs caused by our tools. Useful, but the line moves as tooling improves.

Best tool: abstraction. SQL hides on-disk structures, concurrency and crash recovery. The book is about general-purpose abstractions (transactions, indexes, event logs) you build on.

🌱 Evolvability

Easy to change for new requirements.

Agile, TDD and refactoring help inside one codebase; evolvability is that agility at the whole-data-system level. Loosely coupled, simple systems are easier to change.

Irreversibility is the big enemy: a migration you can't roll back is far riskier than one you can. Minimize irreversible steps.

You plan a database migration. Which choice most improves evolvability?

Irreversibility is a major obstacle to change. If you can roll back, the stakes are much lower.

Name the three parts of maintainability in DDIA and who or what each one serves.

Operability: easy for the organization (ops) to keep the system running. Simplicity: easy for new engineers to understand. Evolvability: easy to change the system for new requirements in the future.

What is the difference between essential and accidental complexity, and what does DDIA call the best tool against complexity?

Essential complexity is inherent in the problem domain; accidental complexity comes from the limitations of our tools (the boundary shifts as tools improve). The best tool is abstraction: a clean interface hiding detail, like SQL hiding storage structures, concurrency and crash recovery.

Why does DDIA call automation "two-edged" for operability?

Automation handles the routine cases, leaving humans only the hardest edge cases it can't handle, so the ops team needs more skill, not less. And when an automated system misbehaves, it can be harder to debug than a manual process.
