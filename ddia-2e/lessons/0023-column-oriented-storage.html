Column-Oriented Storage

Analytics reads a few columns of billions of rows, so store each column together, compress it, and sort it well.

Rows vs columns

A fact table can have 100+ columns and trillions of rows, but a typical analytics query touches 4–5 columns. A row store must still load every full row. A column store keeps each column's values together, so a query reads only the columns it needs.

Every column stores rows in the same order, so the k-th entry of each column rebuilds row k. In practice the table is split into blocks (often by time range), each storing its columns. Snowflake, DuckDB, Druid, Parquet and Arrow work this way.

Don't confuse column-oriented storage with the wide-column (column-family) model of Bigtable and HBase. Wide-column databases are actually row-oriented.

Compression: bitmaps and run-length encoding

Sort order and writes

  • Rows can be stored sorted, like an SSTable. Sort whole rows, never each column separately, or rows can't be rebuilt. Pick sort keys from common queries: date_key first if queries target date ranges.
  • The first sort key gets long runs of equal values, so RLE shrinks it to kilobytes even for billions of rows. Later sort keys compress less.
  • Inserting one row into the middle of sorted, compressed columns would rewrite everything. So writes are bulk, LSM-style: an in-memory, row-oriented sorted store merged into new column files in batches. Queries combine both, so new data is visible immediately.

A report query uses 4 of a fact table's 150 columns over 2 billion rows. Why is a column store much faster than a row store here?

Each column's values are stored together, so the query skips the other 146 columns, and columns compress well. Columns are never sorted independently, or rows couldn't be rebuilt.

How does bitmap encoding compress a column with few distinct values, and how do filters like IN (31, 68) or conditions on two columns use it?

Store one bitmap per distinct value, with bit k set if row k has that value; sparse bitmaps are run-length encoded. An IN list is a bitwise OR of the values' bitmaps; conditions on two columns are a bitwise AND of their bitmaps, which works because every column stores rows in the same order.

In a sorted column store, why must whole rows be sorted rather than each column on its own, and which column compresses best?

Rows are rebuilt by taking the k-th entry of every column; sorting columns independently would break that alignment. The first sort key compresses best, because sorting creates long runs of equal values that run-length encoding shrinks dramatically.

Is a wide-column database like HBase or Bigtable the same as a column-oriented store? Explain.

No. Wide-column (column-family) databases have rows with many, varying columns but store each row's values together, so they are row-oriented. Column-oriented stores keep all values of one column together, which suits analytics scans.
