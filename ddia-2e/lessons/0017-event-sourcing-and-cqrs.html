Event Sourcing and CQRS

Write in the form best for writing, an immutable log of events, and derive every read form from it.

Every other model is queried in the same form it's written. Event sourcing breaks that: write in the form best for writing, then derive read-optimized forms. The simplest, fastest and most expressive way to write is an append-only log of immutable events.

A command is validated first; only a valid one becomes a fact, appended as an event. So the log holds only valid events, and a view builder may not reject one. Name events in the past tense ("seats were booked"): a later cancellation doesn't erase the fact that the booking existed.

👍 Why it's attractive

  • Events state intent ("booking cancelled", not "active=false on row 4001").
  • Views are reproducible: delete, fix the code, replay.
  • Many views in any model; a new feature can build a new view from the old log.
  • Mistakes fixed by a compensating event: fewer irreversible actions.
  • Built-in audit log; sequential appends absorb write bursts.

👎 Watch out for

  • External data (exchange rates) must be in the event or looked up as of the event's time, or replays give different results.
  • Immutability vs deletion laws: per-user logs, personal data kept outside events, or crypto-shredding (delete the key). Each makes rebuilding harder.
  • Side effects on replay: don't resend confirmation emails.
  • All views must process events in exactly the same order, hard in distributed systems.

Tools: EventStoreDB, MartenDB (on PostgreSQL), Axon, or Kafka with stream processors. A star-schema fact table also records past events, but its rows share one shape and are unordered; in event sourcing, event types differ and order matters.

In an event-sourced system, a bug in a view's code has corrupted the view. How do you recover?

Views are derived reproducibly from the immutable log, so rebuild them by replaying the same events in the same order with fixed code. Views may never reject events.

In event sourcing, what is the difference between a command and an event, and why are events named in the past tense?

A command is a request that is validated and may be rejected. An event is the fact recorded after a valid command; it is immutable and views may not reject it. Past tense ("seats were booked") because it records something that happened; a later cancellation is a new event and doesn't erase the earlier fact.

Name three pitfalls of event sourcing.

External data (e.g. exchange rates) must be stored in the event or looked up as of the event time, or replays differ. Immutable logs clash with deletion rights such as the GDPR (workarounds: per-user logs, data outside events, crypto-shredding). Replays must not repeat side effects like emails. And every view must process events in exactly the same order.

A university records grade changes by overwriting the grade column in a table. Someone proposes an event log of grade changes instead.

What would event sourcing gain here?

Each change is kept as an immutable, past-tense event stating intent (e.g. "grade corrected after appeal"), giving a built-in audit log. Current grades, transcripts and statistics become views that can be rebuilt or added later by replaying the log, and mistakes are fixed with compensating events instead of irreversible overwrites.
