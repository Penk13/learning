LSM-Trees and Bloom Filters

Sort in memory, write sorted files once, merge them in the background: the log-structured storage engine.

How writes stay sorted

To delete, append a tombstone: a marker saying "this key is gone"; compaction discards older values under it. This is the Log-Structured Merge-tree (LSM-tree), popularized by Google's Bigtable paper (which coined SSTable and memtable). Used by RocksDB, Cassandra, ScyllaDB, HBase.

Bloom filters: skip segments that can't contain the key

Reading an old or missing key means checking many segments. So each SSTable carries a small Bloom filter: a bit array where each key sets a few hashed bit positions. Any 0 among a key's bits means definitely absent. All 1s means probably present: a false positive is possible, costing one wasted block read, never a wrong answer. Rule of thumb: 10 bits per key ≈ 1% false positives; every 5 more bits per key cuts that tenfold.

Compaction strategies

📦 Size-tiered

Merge newer, smaller SSTables into older, larger ones. Handles very high write throughput, but big merges need lots of temporary disk space. Best for write-heavy workloads.

🪜 Leveled

Fixed-size SSTables in levels L0, L1, L2…; each level beyond L0 is split by key range and bigger than the last. Incremental, less disk, fewer SSTables per read. Best for read-heavy workloads.

In an LSM-tree, where does a new write go first, besides the crash-recovery log?

Writes go to the memtable (and the log). When it's full it's flushed as a new immutable SSTable; background compaction merges segments later.

An SSTable's Bloom filter reports a key as "probably present". What does the engine do next? And what does it mean if one of the key's bits is 0?

It reads the block, because all-1 bits may be a false positive caused by other keys; if the key isn't there it keeps searching older segments. A 0 bit means the key is definitely not in that SSTable, so it's skipped without any disk read.

How does an LSM-tree delete a key, and why can't it just remove the value?

It writes a tombstone, a special record marking the key as deleted. Older values live in immutable SSTables that can't be edited, so the tombstone tells reads the key is gone and tells compaction to discard older values when segments are merged.

Compare size-tiered and leveled compaction: how each works and which workload each suits.

Size-tiered merges newer, smaller SSTables into older, larger ones: very high write throughput but big merges need lots of temporary disk; suits write-heavy loads. Leveled keeps fixed-size SSTables in key-range-split levels of growing size: incremental, less disk, fewer SSTables per read; suits read-heavy loads.
