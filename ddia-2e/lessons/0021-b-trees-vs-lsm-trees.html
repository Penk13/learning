B-Trees vs LSM-Trees

Update in place or append and merge: how the two engines trade read speed, write speed and disk.

Rule of thumb: LSM-trees for write-heavy, B-trees for read-heavy. But benchmarks are sensitive to workload details: test with your workload. Engines also blend the two.

Write amplification

Benchmark long enough. An empty LSM-tree has no compaction work yet, so it looks faster than it will be once compaction kicks in.

Why sequential writes win, even on SSDs

SSDs have no moving head, yet sequential writes are still faster. Flash is written per page (~4 KiB) but erased only per block (~512 KiB). Random writes leave blocks with a mix of valid and stale pages, so the SSD's garbage collector must copy the valid pages elsewhere before erasing, using write bandwidth and wearing the drive. Sequential writes tend to fill whole blocks with one file, which can later be erased without that copying.

A sensor platform ingests huge volumes of writes and reads rarely. Which storage engine is the safer first bet?

LSM-trees turn writes into big sequential writes with lower write amplification, and size-tiered compaction favours write throughput. Still: benchmark with your real workload.

Define write amplification, and give its sources in a B-tree and in an LSM-tree.

Bytes actually written to disk divided by the bytes a plain append-only log would write. B-tree: the WAL entry plus rewriting a whole page for a small change. LSM-tree: the log, the memtable flush, and rewriting the data again in each compaction. It limits write throughput and wears out SSDs.

SSDs have no moving disk head. Why are sequential writes still faster than random writes on them?

Flash is written per page but erased only per larger block. Random writes leave blocks mixing valid and stale pages, so the SSD's garbage collector must copy valid pages elsewhere before erasing, costing bandwidth and wear. Sequential writes fill whole blocks that can later be erased without that copying.

Why are range queries a weaker spot for LSM-trees than for B-trees?

A B-tree walks one sorted tree, using sibling pointers along the leaves. An LSM-tree must scan the range in every segment (and the memtable) in parallel and merge the results, and Bloom filters can't help because they only answer "is this exact key present?".
