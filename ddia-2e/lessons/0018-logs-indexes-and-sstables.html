DDIA · Ch.4 Storage and Retrieval

Logs, Indexes and SSTables

Appending is the cheapest write; finding things again needs an index; sorting the log makes the index small.

The world's simplest database

db_set () { echo "$1,$2" >> database; }
db_get () { grep "^$1," database | sed -e "s/^$1,//" | tail -n 1; }

✍ Writes: great

Appending to a file is the cheapest write there is. An update appends a new line; the old one stays. Many databases use the same idea internally: a log, an append-only sequence of records (not application log text).

🔍 Reads: awful

db_get scans the whole file every time: O(n). To find things fast you need an index.

An index is derived data. It speeds up reads, but costs disk space and slows down every write, because it must be updated too. So you choose indexes from your query patterns instead of indexing everything.

Step 1: a hash map of byte offsets

Keep appending to the log, plus an in-memory hash map from each key to the byte offset of its latest value. A read: look up the offset, seek, read. Problems: the log grows forever, the map must be rebuilt by scanning the log after a restart, the map must fit in RAM, and range queries (keys 10000–19999) need a lookup per key. So real databases rarely use hash indexes.

Step 2: SSTables (Sorted String Tables)

Store key-value pairs sorted by key, each key once. Now you don't need every key in memory: group pairs into blocks of a few KB and keep only the first key of each block in a sparse index. Blocks can also be compressed (less disk and I/O, a bit more CPU).

The catch: you can't append to a sorted file without breaking the order. How writes stay sorted is the LSM-tree, next.

You add three new secondary indexes to a busy table. What is the main cost?

Indexes are derived data: they speed up the reads they serve but use disk space and add work to every insert, update and delete.

A storage engine keeps an in-memory hash map from each key to its byte offset in an append-only log. Name three limitations of this design.

The log grows forever unless compacted; the hash map must fit in RAM; after a restart the map must be rebuilt by scanning the log; and range queries are impossible without looking up every key individually.

An SSTable's sparse index lists only "handbag → 0" and "handsome → 4096". You look up "handiwork".

How does the lookup proceed, and why does sorting make a sparse index possible?

"handiwork" sorts between handbag and handsome, so it can only be in the block starting at offset 0: seek there and scan that one small block. Because keys are sorted, knowing each block's first key tells you which block a key must be in, so not every key needs to be in memory.
