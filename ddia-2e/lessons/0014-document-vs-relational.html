Document vs Relational: Choosing a Model

The shape of your relationships decides the model. And "schemaless" doesn't mean there's no schema.

Three relationship shapes

One-to-many

One résumé → several positions, each belonging to one résumé. A tree: fits documents.

Many-to-one

Many people → one region. A reference: fits normalization.

Many-to-many

A person worked at many orgs; an org has many employees. Needs a join (associative) table.

In a document model, the person document can hold org_id references in its positions array (many document databases can index values inside documents). Storing IDs on both sides is denormalized, and the two lists can disagree.

When to use which

Schema-on-read vs schema-on-write

"Schemaless" is misleading: the code that reads the data still assumes a structure. It's just implicit.

Schema-on-read

Structure interpreted when read, like dynamic typing. Document DBs, JSON columns. Every reader must handle old formats forever:

if (user && user.name && !user.first_name) {
  user.first_name = user.name.split(" ")[0];
}

Schema-on-write

Database enforces structure on every write, like static typing. Relational tables.

ALTER TABLE users ADD COLUMN first_name text;
UPDATE users SET first_name = split_part(name, ' ', 1);

ADD COLUMN is fast; the UPDATE rewrites every row, slow on big tables.

Schema-on-read wins when data is heterogeneous (many object types, or structure dictated by external systems that change anytime). When all records share a structure, a schema documents and enforces it. No clear winner, just like static vs dynamic typing.

Locality and convergence

  • A document is stored as one contiguous string (JSON, BSON). Great if you need most of it; wasteful if you need a small part, and any update rewrites the whole document. Keep documents small.
  • Locality isn't document-only: Spanner's interleaved tables and Bigtable's column families do the same.
  • The models are converging. Relational databases added JSON types and indexes inside documents; document databases (MongoDB, Couchbase) added joins, secondary indexes and declarative queries such as MongoDB's aggregation pipeline.

"Schemaless" document databases are more accurately described as…

Code reading the data still assumes a structure; the database just doesn't enforce it. Like dynamic typing, versus schema-on-write ≈ static typing.

Name the three relationship shapes (one-to-many, many-to-one, many-to-many) with an example each, and the data model each fits best.

One-to-many: a résumé and its positions; a tree, fits documents. Many-to-one: many people in one region; a reference by ID, fits normalized relational data. Many-to-many: people and the organizations they worked at; needs a join table, fits relational (or graph).

A student profile with addresses, emergency contacts and study history is always loaded whole on one page.

Which data model fits most naturally, and why?

A document (JSON tree). It's a tree of one-to-few relationships loaded at once, so one read fetches it all (locality) with no shredding into many tables or multiway joins.

Why should documents in a document database be kept small?

A document is stored as one contiguous string: reading a small part still loads the whole thing, and updating any field typically rewrites the whole document. Large documents waste I/O on partial reads and frequent small updates.
