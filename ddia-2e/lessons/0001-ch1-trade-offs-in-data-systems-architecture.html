Trade-Offs in Data Systems Architecture

"There are no solutions; there are only trade-offs." Four big choices that shape every data system — and the vocabulary the rest of the book is built on.

1 · Your app is already a data system

An app is data-intensive when data management is a primary challenge: big volumes, data that keeps changing, staying consistent through failures and concurrency, staying available. (Compute-intensive = the hard part is parallelizing a huge calculation.) Nobody builds from scratch — we glue standard building blocks together with application code.

No approach is fundamentally better; everything has pros and cons. This book teaches you to ask the right questions to compare them.

2 · Operational vs analytical systems

Different people do very different things with the same data — often without saying so, which breeds disagreement.

🛠 Operational (OLTP)

Backend services where data is created. App code reads and modifies data based on user actions.

Backend engineers.

📊 Analytical (OLAP)

A read-only copy of operational data, optimized for analysis.

Business analysts (BI reports) and data scientists (insights, ML/AI features).

🔗 The bridge roles

Data engineers integrate the two sides and own data infrastructure. Analytics engineers model and transform data for analysts.

PropertyOperational (OLTP)Analytical (OLAP)
Main readPoint queries — fetch a few records by keyAggregate (count/sum/avg) over huge numbers of records
Main writeCreate/update/delete individual recordsBulk import (ETL) or event stream
Human userEnd user of web/mobile appInternal analyst, decision support
Machine use"Is this action authorized?"Detect fraud/abuse patterns
QueriesFixed, baked into app codeArbitrary, ad hoc exploration
VolumeLots of small queriesFew queries, each complex
Data representsLatest state (now)History of events over time
SizeGB → TBTB → PB

Book's Table 1-1. OLTP users can't write custom SQL (security + performance); analysts can, or use dashboards like Power BI. Hybrid: product / real-time analytics (Pinot, Druid, ClickHouse) — aggregate queries, but low-latency and user-facing.

🧠 Pause & recall: "Total registrations per faculty this semester" vs "Show this student's class schedule" — which is OLTP, which OLAP? Schedule = OLTP (point query by key, latest state, end user). Registrations per faculty = OLAP (aggregate over many records, decision support).

3 · Warehouses, lakes & pipelines

Since the late '80s, analytics moved off OLTP databases into a separate data warehouse. Why not just query the operational DBs?

🏝 Data silos

Data is spread over dozens or hundreds of OLTP systems — hard to combine in one query.

📐 Wrong layout

Schemas good for OLTP are poor for analytics (Ch.3–4).

🐢 Hurts users

Expensive analytic queries slow the app for everyone.

🔒 Access rules

OLTP may sit in a network analysts can't reach, for security/compliance.

🔀 HTAP

Hybrid transactional/analytical processing: OLTP + analytics in one system. Often two engines behind one interface. Useful when one app needs both (e.g. fraud detection) — but it doesn't replace the warehouse.

🌊 Data lake

Just files — no imposed format or schema (Parquet, text, images, feature vectors…). Cheaper (object storage) and suits data scientists who use Pandas, scikit-learn, Spark rather than SQL. Sushi principle: "raw data is better".

🚀 Beyond the lake

Event streams let analytics react in seconds (e.g. block fraud). Reverse ETL pushes analytic outputs back to operational systems. DataOps, governance, privacy rules raise the bar.

Bigger trend: the larger the scale, the more specialized systems become. General-purpose works fine for small data.

4 · Systems of record vs derived data

It's about use, not the tool. The same PostgreSQL can be a system of record in one app and a derived cache in another. Being explicit about "what's derived from what" brings clarity to a confusing architecture — and raises the real question: what process updates derived data when the source changes? (Ch.11–13.)

5 · Cloud vs self-hosting

Build or buy? Rule of thumb: do in-house what's a core competency or competitive advantage; outsource what's routine. For software, two separate choices: who builds it and who runs it.

👍 Cloud is good when…

You don't already know how to run the system (hiring/training is expensive); load varies a lot (e.g. interactive analytics: huge bursts, then idle); you want a specialist's operational expertise.

👎 But you lose control

Missing feature → ask politely. Outage → wait. Bug → no internals or server logs. Shutdown, price hike or product change → forced migration (vendor lock-in). Sanctions risk across borders. Must trust them with data security.

🏠 Self-hosting is good when…

You have the skills, load is predictable, you need deep tuning for your workload, or you have specialist needs (e.g. high-frequency trading's hardware control).

Cloud native architecture

Systems designed for the cloud (not just hosted there) can be faster on the same hardware, recover faster, scale quicker and handle bigger datasets.

CategorySelf-hostedCloud native
Operational / OLTPMySQL, PostgreSQL, MongoDBAWS Aurora, Azure SQL DB Hyperscale, Google Cloud Spanner
Analytical / OLAPTeradata, ClickHouse, SparkSnowflake, Google BigQuery, Azure Synapse Analytics

🧱 Layering

Cloud services build on lower-level cloud services: Snowflake builds on S3; other services build on Snowflake. Higher-level = more use-case-specific. If one fits, use it; if none fits, build from lower-level blocks.

🏢 Multitenancy

Many customers share the same hardware and service. Better utilization and easier scaling — but needs careful isolation of performance and security.

🧑‍🔧 Ops still matters

DevOps/SRE: automation, ephemeral VMs, frequent updates, learning from incidents, preserving knowledge. In the cloud, capacity planning becomes financial planning and performance tuning becomes cost optimization. Mind quotas; integration between services is real work.

6 · Distributed vs single-node

A distributed system = several machines communicating over a network; each participating process is a node. Nine reasons to go distributed:

🌐 Inherent

Multiple users on their own devices.

☁ Between services

Data stored in one service, processed in another.

🛡 Fault tolerance

One machine dies, another takes over.

📈 Scalability

More data/compute than one machine can handle.

🌏 Latency

Servers near users worldwide.

🎈 Elasticity

Scale up/down with demand; pay for what you use.

🔧 Special hardware

Disk-heavy storage nodes, CPU-heavy analytics, GPUs for ML.

⚖ Legal

Data residency laws: keep citizens' data in-country.

🌱 Sustainability

Run jobs where/when renewable power is plentiful.

But distribution costs a lot:
  • Any network call can fail or time out — and then you don't know if the request was processed; blind retry may be unsafe (Ch.9).
  • A network call is vastly slower than a function call. Sometimes a single-threaded program on one machine beats a 100+ core cluster.
  • Debugging is hard → you need observability (e.g. tracing with OpenTelemetry, Zipkin, Jaeger).
  • Each service with its own DB → cross-service consistency becomes the app's problem.

Don't rush to distribute. Hardware has grown huge and fast; with single-node databases like SQLite or DuckDB, many workloads fit on one machine.

Microservices and serverless

🧩 Microservices

Each service: one purpose, an API, one owning team, its own database (a shared DB makes its schema part of everyone's API).

👍 independent deploys, right-sized resources, freedom to change internals.

👎 hard to test, per-service infra (deploy, logs, monitoring, on-call — hence Kubernetes), APIs hard to evolve (OpenAPI/gRPC help).

A technical solution to a people problem: lets teams move independently. Small org with few teams? Probably unnecessary overhead.

⚡ Serverless (FaaS)

Cloud allocates and frees resources per request; you pay only while your code runs — metered billing for compute, like cloud storage did for disks.

👎 execution time limits, restricted runtimes, slow cold starts. It still runs on servers — just not the same one each time. "Serverless" is also used loosely to mean "autoscaling, billed by usage".

Cloud vs supercomputing (HPC): HPC runs huge batch jobs (weather, molecular simulation), checkpoints, and on a node failure stops everything and restarts from the checkpoint; trusts its users; uses special topologies; nodes close together. Cloud must stay continuously available, isolate untrusting tenants, and may span regions. This book is about the latter.

7 · Data systems, law & society

Architecture is shaped not just by business needs but by the rights of the people whose data you hold. GDPR (EU, 2018), CCPA, the EU AI Act — and automated decisions about loans, jobs or policing affect lives.

🗑 Right to be forgotten

GDPR lets people demand erasure. But many systems are built on immutable, append-only logs. How do you delete from the middle of an immutable file — or from derived data such as ML training sets? No settled answer yet.

💸 True cost of storing data

Not just the storage bill: leak liability, reputational damage, fines for non-compliance, government demands, and real safety risks for users (e.g. location history).

✂ Data minimization

Datensparsamkeit: some data isn't worth keeping — delete it. Opposite of "store everything just in case". Fits GDPR: collect only for a specified purpose, don't reuse for others, don't keep longer than needed.

Industry standards push the same way: PCI for card payments, SOC 2 Type 2 audits for software vendors. The book returns to ethics in Ch.14. Local note (not from the book): Indonesia has its own Personal Data Protection Law (UU PDP, No. 27/2022) — check specifics with the relevant BINUS compliance/legal function rather than assuming.

8 · Practice — answer from memory

Scroll up = cheating yourself.

1. "Fetch this student's current grades by student ID." Which access pattern is this?
A few records, looked up by key, latest state, for an end user = OLTP point query.
2. Which is NOT a reason the book gives for a separate data warehouse?
SQL works fine for both — that's why the same DB was used for both at first. The reasons are silos, unsuitable layouts, performance impact and access restrictions.
3. The search index says a course has 30 seats; the main database says 28. Which is correct?
If derived data disagrees with the system of record, the system of record is right by definition. Rebuild the index from it.
4. What's the key difference between a data lake and a data warehouse?
Warehouse = relational schema, SQL. Lake = just files in any format (Parquet, text, images…), cheaper, raw ("sushi principle").
5. Your team knows the database well and its load is steady all year. The book's rule of thumb suggests…
Existing skills + predictable load → buying and running your own machines is often cheaper. Cloud shines for variable load or unfamiliar systems.
6. Why do cloud native databases treat a VM's local disk as only a cache?
When an instance dies or is replaced by a bigger/smaller one on another machine, its local disk is gone. Durable data goes to a separate storage service.
7. According to the book, microservices are primarily…
They let many teams progress independently. With few teams, they're often unnecessary overhead.
8. A request to another service times out. What do you actually know?
A timeout tells you nothing about whether the other side did the work — so blind retries can be unsafe. Deep dive in Ch.9.

Apply it to your own work

Pick one system you work on at BINUS. In 4 lines:

  1. Is it mainly operational or analytical? Who are its users?
  2. What is its system of record, and what derived data hangs off it (caches, indexes, reports, warehouse copies)? Who keeps them in sync?
  3. Is it self-hosted or cloud? Give one reason the choice fits (or doesn't) — skills, load variability, control.
  4. Is it distributed? Which of the nine reasons justifies it — or could it run on one node?
