Data Models, Declarative Queries and ORMs

The data model you pick shapes how you think about the problem, and translating between models has a cost.

Data models are stacked layers

Each layer represents its data using the layer below and hides that complexity from the layer above. Chapter 3 is about layer ②; Chapter 4 is about layer ③.

Declarative query languages (SQL, Cypher, SPARQL, Datalog) say what result you want: conditions, sorting, grouping. The query optimizer decides how: indexes, join algorithms, execution order. So the database can get faster, or run your query in parallel across cores and machines, without you changing a line. In Python or Java you write the algorithm yourself.

Relational, NoSQL and the document model

The relational model (Codd, 1970) stores data as relations (SQL tables), each an unordered collection of tuples (rows). By the mid-1980s it was the default; it still dominates business analytics. NoSQL in the 2010s brought new data models, flexible schemas, scaling and open source; NewSQL aimed for NoSQL-style scale with relational transactions. The lasting effect is the document model (usually JSON), which most relational databases now also support.

The object-relational mismatch

App code uses objects; relational databases use tables, rows and columns. The awkward translation is the impedance mismatch. ORMs (ActiveRecord, Hibernate, Django ORM, Entity Framework) remove boilerplate, with catches:

👎 Downsides

Can't fully hide either model, so you still think in both. Analysts query the underlying tables, so schema design still matters. Auto-generated schemas can be awkward. Easy to write slow queries by accident, e.g. N+1.

👍 Upsides

Some translation is unavoidable, so less boilerplate is a win for simple, repetitive cases. Some ORMs cache results; many manage schema migrations.

N+1 queries: one query fetches N records, then one extra query per record fetches related data. Fix it with a join or eager loading:

An ORM-backed page runs 1 query for 200 comments, then 200 more queries to load each comment's author. What is the best fix?

That's the N+1 query problem. Do the join in the database (or tell the ORM to fetch authors with the comments): 1 round trip instead of 201.

What does a declarative query language leave to the database, and what does that let the database do?

You state what result you want; the query optimizer chooses how (indexes, join algorithms, order of execution). So the database can improve performance or parallelize the query across cores and machines without the query being rewritten.

What is the impedance mismatch, and name two downsides of using an ORM to bridge it.

The awkward translation between application objects and relational tables, rows and columns. ORM downsides: you still have to think in both models; schema design still matters because analysts query the tables directly; generated schemas can be inefficient; and it's easy to write slow queries such as N+1.
