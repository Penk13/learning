Query Execution, Materialized Views and Data Cubes

When scans cover millions of rows, the CPU becomes the bottleneck; precomputing results is the other escape.

Making the CPU fast enough

Scanning millions of rows makes CPU time, not just disk reads, a bottleneck. A naive interpreter that consults the query plan for every row is too slow. Two fixes:

🛠 Query compilation

Generate code for this specific query, compile it to machine code (often with LLVM), and run it over the column data in memory. Like a JIT compiler in the JVM.

📦 Vectorized processing

Still interpreted, but each built-in operator processes a batch of column values at once. "product = bananas" → a bitmap; "store = X" → a bitmap; bitwise AND → matching sales.

Both exploit modern CPUs: sequential memory access (fewer cache misses), tight inner loops (no branch mispredictions), parallelism (threads and SIMD: one instruction processing several values), and working directly on compressed data.

Materialized views and data cubes

A virtual view is a saved query, expanded at read time. A materialized view is a stored copy of the results that must be updated when the data changes: more write work, faster repeated reads (the precomputed home timelines of a social network are one). A data cube aggregates net sales by date and product. Which question can it NOT answer without going back to the raw data?

A cube only answers questions along its dimensions. Price isn't a dimension here, so that question needs the raw fact rows, which is why warehouses keep them.

Compare query compilation and vectorized processing as ways to speed up analytic queries. What CPU properties do both exploit?

Query compilation generates and compiles machine code for the specific query (e.g. via LLVM). Vectorized processing stays interpreted but runs built-in operators over batches of column values. Both exploit sequential memory access, tight loops without branch mispredictions, parallelism (threads and SIMD), and operating directly on compressed data.

What is the difference between a virtual view and a materialized view, and what does each cost?

A virtual view is a saved query, expanded each time it's read: no extra storage or write work, but the full query runs on every read. A materialized view stores the query's results: fast repeated reads, but it takes space and must be updated whenever the underlying data changes.
