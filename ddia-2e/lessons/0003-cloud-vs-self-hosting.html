DDIA · Ch.1 Trade-Offs in Data Systems Architecture

Cloud vs Self-Hosting

Build or buy, run it yourself or rent it: when each wins, and what "cloud native" changes inside a database.

Rule of thumb: do in-house what's a core competency or competitive advantage; outsource what's routine. For software there are two separate choices: who builds it and who runs it.

👍 Cloud wins when…

You don't know how to run the system (hiring and training cost a lot); load varies a lot (interactive analytics: huge bursts, then idle); you want a specialist's operational expertise.

🏠 Self-hosting wins when…

You have the skills and load is predictable (often cheaper), you need deep tuning for your workload, or you have specialist hardware needs.

👎 What cloud takes away

Missing feature: ask politely. Outage: wait. Bug: no internals or server logs. Shutdown, price hike or product change: forced migration (vendor lock-in). Sanctions risk across borders. You must trust them with security.

Cloud native architecture

Systems designed for the cloud, not just hosted there: Aurora, Spanner, Azure SQL Hyperscale (OLTP); Snowflake, BigQuery (analytics). Compare self-hosted MySQL, PostgreSQL, ClickHouse.

  • Layering: cloud services build on lower-level ones (Snowflake on S3). If a high-level service fits your use case, use it; if not, build from lower-level blocks.
  • Multitenancy: many customers share hardware and service. Better utilization and easier scaling, but needs careful performance and security isolation.
  • Ops still matters (DevOps/SRE): automation, ephemeral VMs, learning from incidents. In the cloud, capacity planning becomes financial planning and performance tuning becomes cost optimization.

Why do cloud native databases treat a VM's local disk as only a cache?

When an instance dies or is replaced by a bigger or smaller one on another machine, its local disk is gone. Durable data lives in a separate storage service.

Your team runs a database it knows well, and its load is steady all year. Another team needs an interactive analytics tool that is hammered for an hour after each exam period, then sits idle.

Which of the two fits self-hosting and which fits a cloud service, by the book's rule of thumb?

The steady, well-understood database: self-hosting is often cheaper when you have the skills and predictable load. The bursty analytics tool: cloud, because you pay for capacity only while it's used and avoid buying hardware for peaks.

Name four kinds of control you give up by using a cloud service instead of self-hosting.

You can't add missing features (only ask), you wait out outages, you can't inspect internals or server logs when debugging, and you face forced migration if the service shuts down, changes or gets pricier (vendor lock-in). Also: sanctions risk and trusting the vendor with security.

What does "separation of storage and compute" mean in cloud native databases, with one benefit and one cost?

Durable data lives in a separate storage service (e.g. object storage); compute nodes are stateless and use local disk only as a cache. Benefit: scale compute and storage independently and recover fast from node loss. Cost: data travels over the network.
