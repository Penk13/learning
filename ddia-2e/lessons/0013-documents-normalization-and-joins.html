Documents, Normalization and Joins

Store a fact once and join on read, or copy it everywhere and pay on write.

One-to-many data is a tree, and documents fit trees

A résumé: one user has many positions, many education entries and contact info. Relational: split into tables with foreign keys to users. Document: one JSON object with nested arrays.

Normalized vs denormalized

Why store region_id: "us:91" instead of the text "Washington, DC"? A standard list gives consistent spelling, no ambiguity between places with the same name, one place to update a rename, localization into other languages, and smarter search. An ID means nothing to humans, so it never has to change; anything humans read may change, and every copy must change with it.

Normalized (store an ID)Denormalized (copy the value)
WritesFaster: one copySlower: update every copy, more disk
ReadsSlower: need joinsFaster: fewer joins
RiskJoin cost at very large scaleCopies drift apart; a crash halfway through an update needs atomic transactions across documents, or stream processing
FitsOLTP at small-to-moderate scale (the usual default)Analytics; hot read paths at huge scale

Denormalized data is derived data: you need a process that keeps the redundant copies up to date.

Joins at read time can scale: X's timelines

The materialized home timeline is a denormalized cache of a join. But X stores only IDs in it (post ID, sender ID), not post text or like counts. At read time the service hydrates the IDs, looking up post content and the sender's profile: a join in application code. Like counts change many times per second and people change profile photos; copying those into millions of timelines would be wrong and expensive. Hydration parallelizes well and its cost doesn't depend on follower counts.

The best design often mixes the two: denormalize what rarely changes and is costly to compute; keep fast-changing data normalized.

Which statement about normalized data is generally true?

One copy makes writes cheap and consistent; reads resolve IDs with joins. Denormalized is the reverse, and analytics usually favours it.

A course-registration page lists each class with its lecturer's name and a live "seats left" count.

Which would you denormalize into the class listing, and which keep as a reference looked up at read time? Why?

Copy the lecturer name: it rarely changes, so a copy is cheap and safe (with a process to update it). Keep seats-left normalized or look it up live: it changes constantly during registration, so a copy would go stale immediately, like X's like counts.

X's materialized home timelines store only post IDs and sender IDs. Why not the post text and like counts, and how are the IDs turned into a page?

Like counts and profiles change constantly, so copying them into millions of timelines would be stale and expensive in storage. At read time the IDs are hydrated by looking up the post and sender profile, a join in application code that parallelizes well and doesn't depend on follower counts.

When does embedding one-to-many data in a single document fit well, and when does it stop fitting?

It fits a tree of one-to-few relationships that is usually loaded whole, like a profile with its positions: one read, good locality, no shredding into tables. It stops fitting when the children number in thousands (e.g. comments on a celebrity's post): the document gets unwieldy and separate tables work better.
