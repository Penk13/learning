Multidimensional, Full-Text and Vector Indexes

Searching by location, by words, and by meaning each needs a different kind of index.

Concatenated vs multidimensional

A concatenated index joins fields into one key, like a phone book sorted by (last name, first name). It finds a last name, or last + first, but is useless for first name alone. A map query ("restaurants inside this rectangle") needs latitude and longitude ranges at once, which a concatenated index can't do. Spatial indexes such as R-trees group nearby points in the same subtree (PostGIS). The same applies beyond maps: (date, temperature) to find days of 25–30 °C in one year.

Full-text search: the inverted index

  • n-grams: index every substring of length n ("hello" → hel, ell, llo). Allows substring and even regex search; the index gets big.
  • Typos: Lucene finds words within an edit distance (1 = one letter added, removed or replaced) using a Levenshtein automaton.

Vector embeddings: search by meaning

Semantic search finds "canceling your subscription" when the user types "how to close my account". An embedding model turns each document into a vector embedding: an array of floats (often 1,000+) marking a point in space, where similar meanings land close together. Closeness is measured with cosine similarity (angle) or Euclidean distance. It's a core part of retrieval-augmented generation (RAG). R-trees don't work for 1,000+ dimensions, so vector indexes are special:

Flat

Compare the query with every vector. Exact, slow.

IVF

Cluster vectors into partitions; search only the nearest ones ("probes"). More probes: more accurate, slower. Approximate.

HNSW

Layered proximity graphs, sparse at the top, dense at the bottom; walk down greedily toward the nearest vector. Approximate.

Faiss and PostgreSQL's pgvector support both IVF and HNSW. Note the two meanings of "vector": in vectorized processing it's a batch of values for tight CPU loops; in embeddings it's a point in space.

An index exists on (last_name, first_name). Which query can it NOT serve efficiently?

A concatenated index is sorted by the first field, then the second. Like a phone book, it can't find everyone with a given first name without scanning.

How does an inverted index answer a search for "red apples"?

It maps each term to a postings list of the documents containing it. The search intersects the postings lists for "red" and "apples", which with bitmaps is a bitwise AND; the documents left contain both words.

A help-desk search should find the article "reset my password" when users type "can't log in". The words don't overlap.

What kind of index fits, and how does it work?

A vector index over text embeddings (semantic search). An embedding model turns each text into a vector of floats where similar meanings are close; the index (flat, IVF or HNSW, e.g. pgvector) finds the vectors nearest the query's by cosine or Euclidean distance. Full-text and n-gram indexes only match words.

Compare flat, IVF and HNSW vector indexes.

Flat compares the query with every vector: exact but slow. IVF clusters vectors into partitions and searches only the nearest few (probes): approximate, more probes = more accurate but slower. HNSW walks layered proximity graphs from a sparse top layer down to a dense bottom layer: approximate.
