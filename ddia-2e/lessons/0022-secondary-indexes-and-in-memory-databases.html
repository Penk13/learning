Secondary Indexes and In-Memory Databases

Where the row actually lives relative to its indexes, and why "in memory" is fast for a surprising reason.

Secondary indexes

A primary key uniquely identifies a row, document or vertex. A secondary index (CREATE INDEX) lets you search by other columns, such as user_id in a positions table. Its keys are not unique, so each entry either holds a list of matching row IDs (like a postings list) or is made unique by appending a row ID. Both B-trees and LSM-trees can implement it.

Keeping everything in memory

Disks are awkward but durable and cheap per GB. As RAM gets cheaper, many datasets simply fit in memory. Memcached is cache-only: losing data on restart is fine. Durable in-memory databases (VoltDB, SingleStore, Oracle TimesTen, RAMCloud) persist via a log on disk, snapshots or replicas; Redis and Couchbase write to disk asynchronously (weaker durability). Reads are served entirely from RAM.

Counterintuitive: in-memory databases are not faster because they skip disk reads. With enough RAM, the OS page cache serves a disk-based engine from memory anyway. They're faster because they avoid encoding in-memory structures into an on-disk format. Bonus: they can offer structures that are hard on disk, like Redis's priority queues and sets.

Embedded storage engines

RocksDB, SQLite, LMDB, DuckDB and KùzuDB are libraries running inside your process, called by function rather than over a network. Common in mobile apps. On a backend they fit small data with few concurrent transactions, e.g. one database per tenant when tenants never need to be queried together.

Why can an in-memory database beat a disk-based one even when all the disk-based database's data sits in the OS page cache?

The speed-up comes from skipping the encoding overhead. Many in-memory databases still write a log or snapshots to disk for durability.

Compare a clustered index, an index pointing into a heap file, and a covering index: where does the row data live in each?

Clustered: the whole row is stored inside the index (InnoDB primary key). Heap file: the index stores a pointer to the row's location in a separate unordered heap file (PostgreSQL). Covering: the index stores a few extra columns so some queries can be answered from the index alone, with a reference to the full row for the rest.

A secondary index's keys are not unique. What are the two ways an index entry handles many matching rows?

Either each index entry holds a list of matching row IDs (like a postings list in full-text search), or each entry is made unique by appending the row ID to the key.

A SaaS backend serves many small tenants whose data is never queried across tenants.

What storage option does DDIA mention for this case, and why does it fit?

An embedded storage engine such as SQLite, with one database per tenant. Embedded engines run inside the application process (no network hop) and suit small data with few concurrent transactions, which per-tenant databases have.
