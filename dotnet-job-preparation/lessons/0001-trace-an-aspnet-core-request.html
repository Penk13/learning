Middleware is an ordered chain with a return trip; order decides behavior.

A pipeline is a chain with a return trip

ASP.NET Core composes an ordered pipeline of request delegates. Each middleware gets two chances: before it calls the next component and after the next component returns. It can also stop the journey early by not calling next.

The request walks forward through the doors; the response walks back through the same doors in reverse. That is why logging or timing code can wrap an endpoint.

Use continues; Run can finish

app.Use(async (context, next) =>
{
    Console.WriteLine("A before");
    await next.Invoke(context);
    Console.WriteLine("A after");
});

app.Use(async (context, next) =>
{
    Console.WriteLine("B before");
    await next.Invoke(context);
    Console.WriteLine("B after");
});

app.Run(async context =>
{
    Console.WriteLine("terminal");
    await context.Response.WriteAsync("OK");
});
  • Use receives a next delegate and chooses whether to invoke it.
  • Code before await next runs on the way in; code after it runs on the way back out.
  • Run is terminal: there is no later delegate to invoke.
  • Short-circuit: any middleware that does not call next stops traversal.

Exact overloads vary; focus on the control flow. Source: ASP.NET Core middleware — Microsoft Learn.

The 60-second interview answer

“What is ASP.NET Core middleware, and why does its order matter?” A strong answer:

  • Defines middleware as an ordered chain of request delegates.
  • Says a component can run before and after the next delegate.
  • Explains short-circuiting: not invoking next stops traversal.
  • Gives one order example: exception handling goes early so it can observe failures from later components.

Cards

An ASP.NET Core app registers middleware A with app.Use, then middleware B with app.Use, then a terminal app.Run. A and B each log “before”, await next, then log “after”; the terminal delegate logs “terminal”.

What is the output order for one request?

The request enters in registration order (A, then B, then the terminal delegate); the response unwinds in reverse, so B resumes before A.

In ASP.NET Core, what does “terminal middleware” mean, and how is it related to short-circuiting?

Terminal middleware ends the pipeline: it does not pass control to a later delegate (app.Run creates one). Short-circuiting is the same effect from any middleware that chooses not to call next.

In an interview: what is ASP.NET Core middleware, and why does its order matter?

An ordered chain of request delegates. Each can run code before and after calling the next one, or short-circuit by not calling it. Order is behavior: the request goes in registration order and the response unwinds in reverse, so e.g. exception handling goes early to observe failures from later components.

You want to log how long every request takes, including the endpoint's work.

Where in a middleware do you put the timing code, and why does that capture the endpoint's time?

Start the timer before await next(...) and log after it returns. Everything later in the pipeline, including the endpoint, runs inside that await, so the code after it runs on the response's way back out.
