Django request lifecycle

A compact interview-ready model of how a request becomes a response.

Request
→
Middleware
→
URLconf
→
View
→

Middleware wraps the path and may short-circuit it. A view can return HTML, a redirect, an error response, JSON, or another valid response type.

Interview answer

“Django receives the request through its middleware stack, resolves the URL against the root URLconf in order, and calls the first matching view with an HttpRequest plus any captured parameters. The view performs application work—possibly querying the ORM or rendering a template—and returns an HttpResponse. The response then travels back through response middleware before it is sent to the client. A missing match or exception is handled by Django's error handlers.”

Three boundaries to remember

  1. URLconf selects. A URLconf is a Python mapping from URL path expressions to view callables. Patterns are checked in order and Django stops at the first match.
  2. The view decides. A view receives the request and returns a response. It is not synonymous with a template and does not have to return HTML.
  3. The model describes data. A model is a Python class that generally maps to a database table. The ORM gives the application a database-access API, but the view remains responsible for the response decision.
Common correction: do not say “Django finds the template from the URL.” Django first resolves the URL to a view; the view may then choose to render a template, redirect, return JSON, or produce another response.
