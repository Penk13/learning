Defining Nonfunctional Requirements

🐦 Case study: home timelines

  • 5.8k posts/s (spikes 150k), 200 follows/followers avg, visible in 5 s.
  • Polling a join: 2M polls/s × 200 = 400M lookups/s.
  • Materialize (fan-out on write): 5.8k × 200 ≈ 1.16M writes/s; reads = cache.
  • Spikes → enqueue deliveries. Celebrities → store separately, merge at read. Super-followers → sample.

⚡ Performance

  • Response time (users care) vs throughput (cost).
  • Near capacity, queueing makes response time explode.
  • Retry storm → metastable failure. Fix: backoff + jitter, circuit breaker, load shedding, backpressure.
  • Response time = latency (network + queueing) + service time. Measure client-side.
  • Use percentiles (p50, p95, p99, p999), not mean.
  • Tail amplification: P(slow) = 1 − (1 − p)ⁿ
  • SLO = target; SLA = contract + consequences.
  • Never average percentiles → add histograms (HdrHistogram, t-digest, DDSketch).

🛡 Reliability

  • Fault (one part) ≠ failure (system misses SLO).
  • Find & remove SPOFs. Tolerance is always for certain faults.
  • Fault injection / chaos engineering. Prevent only where no cure (security).

📈 Scalability

  • Ask "if load grows this way, what are our options?" — never "does it scale?"
  • Early product: simplicity > hypothetical scale.
  • Describe load: throughput, peaks, read:write, hit rate, items/user.
  • Linear scalability = 2× resources → 2× load.
  • Shared-memory (up) · shared-disk (NAS/SAN) · shared-nothing (out).
  • Rethink every ~10×; plan ≤ 1 order ahead. No magic scaling sauce.
  • Split into independent parts; don't over-complicate (5 services < 50).

🔧 Maintainability

  • Most cost is after launch; everything becomes legacy.
  • Operability: observability, no single-machine dependency, docs, defaults + overrides, self-heal + manual control, predictable. Automation is two-edged.
  • Simplicity: avoid big ball of mud; essential vs accidental (Brooks) — fuzzy line; weapon = abstraction.
  • Evolvability: loose coupling; minimize irreversibility.

Design-review questions (steal these)

  1. What are our 2–3 load numbers, with current and peak values?
  2. What's our SLO in percentiles, measured from the client side?
  3. How close to capacity do we run at peak? What happens when clients retry?
  4. Which single fault would cause a user-visible failure today (SPOF)?
  5. Which faults are correlated (same code/config/dependency on every node)?
  6. How fast can we roll back a bad config? Do we roll out gradually? Are postmortems blameless?
  7. Which upcoming change is irreversible — and can we make it reversible?
