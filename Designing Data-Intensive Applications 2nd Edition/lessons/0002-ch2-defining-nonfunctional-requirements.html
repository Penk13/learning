Defining Nonfunctional Requirements

Fast, reliable, scalable, maintainable — the words every architecture discussion throws around, made precise enough to measure and argue with.

1 · What vs how well

Functional requirements say what the app does: which screens, which buttons, what each operation does. Nonfunctional requirements say how well: fast, reliable, secure, legally compliant, easy to maintain. They're often not written down because they seem obvious — but an app that is unbearably slow or unreliable might as well not exist.

Functional: "students can register for a class." Nonfunctional: "…in under a second at p99, even on registration day, even if a server dies — and next year's team can still change it."

⚡ Performance

How fast? Measured with response time & throughput.

🛡 Reliability

Keeps working correctly even when things go wrong.

📈 Scalability

Efficient ways to add capacity as load grows.

🔧 Maintainability

Easy to keep running and change over years.

Security matters just as much, but it's mostly outside this book's scope.

2 · Case study: social network home timelines

The book makes everything concrete with an X/Twitter-style network: users post and follow each other. Assumptions: 500M posts/day ≈ 5,800 posts/s (spikes up to 150k/s); average user follows 200 and has 200 followers — but a few celebrities have 100M+. Followers should see a post within 5 seconds.

When one request triggers many downstream requests, the multiplication factor is called fan-out. Precomputing a query's result and keeping it updated is materialization; the timeline cache is a materialized view. Try both designs:

🌟 Celebrity posts

Fanning out to 100M timelines is too much. Store celebrity posts separately and merge them in at read time. A hybrid.

📚 Super-followers

Someone following thousands of busy accounts won't read everything — it's OK to drop some writes and show a sample.

⚡ Spikes

Enqueue timeline deliveries; posts show up a bit later, but reads stay fast because they come from cache.

Do work at write time when that makes the frequent operation cheap. But the extreme cases, not the average, often decide the design.

3 · Describing performance

⏱ Response time

Time from request to answer, as the user sees it. Unit: seconds/ms. What users care about.

🚚 Throughput

Requests (or data volume) per second. Decides how many machines you need — i.e. cost.

They're linked by queueing: as throughput nears the hardware's maximum, each new request waits for earlier ones, and response time shoots up (book's Fig. 2-3). Drag it:

When an overloaded system won't recover. Slow responses → clients time out and retry → even more load → a retry storm. The system can stay stuck even after the original load drops: a metastable failure. Defences:
  • Client side: exponential backoff with randomness; circuit breaker or token bucket to stop calling a failing service for a while.
  • Server side: load shedding (reject early when near overload); backpressure (tell clients to slow down).

Four timing words, used precisely

Why do identical requests take different times? Context switches, lost packets + TCP retransmission, GC pauses, page faults, even rack vibration. And head-of-line blocking: a few slow requests hold up the fast ones queued behind them. Variation in network delay is called jitter.

Use percentiles, not the mean

Response time is a distribution. The mean is useful for estimating throughput limits, but it doesn't tell you how many users actually felt that delay. Drag the outlier slider:

p50 (median)

Half of requests are faster. How long users typically wait.

p95 · p99 · p999

The tail. Amazon targets p999 for internal services: slowest requests often belong to customers with the most data — the most valuable. p9999 was judged too costly.

SLO / SLA

SLO = target, e.g. "p50 < 200 ms, p99 < 1 s, ≥ 99.9% non-error". SLA = contract saying what happens if the SLO is missed (e.g. refunds).

Why the tail matters more than it looks

If one user request needs several backend calls — even in parallel — it waits for the slowest. Rare slowness per call becomes common slowness per page: tail latency amplification (Dean & Barroso, "The Tail at Scale").

Computing percentiles on a dashboard: keep a rolling window (e.g. last 10 min) and recompute every minute. Sorting all values works; at scale use sketch libraries — HdrHistogram, t-digest, OpenHistogram, DDSketch.
Never average percentiles (across machines or time buckets) — it's mathematically meaningless. Add the histograms, then compute the percentile.
🧠 Pause & recall: your server logs say p99 = 80 ms, but users complain of 2-second waits. Name two places the missing time could be. Queueing delay before the request is processed (not counted in service time) and network latency — that's why response time should be measured on the client side. Head-of-line blocking behind slow requests is a classic cause.

RELIABILITY 4 · Faults are not failures

"Working correctly" = does what users expect, tolerates user mistakes, performs well enough under expected load, and prevents unauthorized access. Reliability ≈ continuing to work correctly even when things go wrong.

  • Fault-tolerant = keeps serving users despite certain faults. Always limited: "up to 2 disks" or "1 of 3 nodes". Tolerating a black hole swallowing Earth needs hosting in space — good luck with that budget.
  • Fault injection: deliberately kill processes so recovery code is exercised constantly — many critical bugs are just poor error handling. The discipline is chaos engineering.
  • Prevent rather than tolerate where no cure exists — e.g. security: leaked data can't be un-leaked.

Why software faults are scariest: redundancy assumes faults are independent. If all replicas run the same bug, they fail together — at the same instant.
Blameless culture. "Bob should have been more careful" isn't useful — and neither is "rewrite the backend in Haskell". Organizations often choose features over resilience; when a preventable mistake happens, the problem is the priorities, not the person. Blameless postmortems let people share full details so everyone learns. (In a real BINUS incident, follow the IR procedure and involve IT Security.)

How important is reliability?

Business bugs cost productivity and create legal risk. A few minutes of downtime is often tolerable; permanent data loss or corruption is catastrophic. The book's sobering example: the UK Post Office Horizon scandal (1999–2019) — accounting-software bugs led to hundreds of wrongful theft/fraud convictions, partly because English law presumed computers work correctly. Cutting reliability corners (e.g. for a prototype) can be fine — but do it consciously.

🧠 Pause & recall: which fault type is least helped by adding more servers? Why? Software faults. Extra replicas run the same code, so they share the same bug and fail together (correlated faults).

SCALABILITY 5 · "Is it scalable?" is the wrong question

Never say "X scales" or "Y doesn't scale". Ask: "If the system grows in this particular way, what are our options — and when do we hit the limits?"

Small new product? Keep it simple and flexible; worrying about hypothetical scale is premature optimization that can lock you into an inflexible design. Learn where the bottlenecks really are first.

Step 1 · Understand the load

Usually throughput (requests/s, GB/day, checkouts/hour), sometimes a peak (simultaneous online users). Plus statistics that shape access patterns: read:write ratio, cache hit rate, items per user (followers!). Sometimes averages matter; sometimes a few extreme cases dominate.

Then ask two questions: (a) load grows, resources fixed → what happens to performance? (b) load grows → how many more resources to keep performance the same? Doubling resources for double load = linear scalability (good). Usually cost grows faster than linear.

Step 2 · Pick an architecture

Step 3 · Principles

  • No one-size-fits-all architecture — no "magic scaling sauce". 100k req/s × 1 kB looks nothing like 3 req/min × 2 GB, despite the same 100 MB/s.
  • Expect to rethink the architecture at every order-of-magnitude load increase; don't plan more than ~10× ahead.
  • Break the system into parts that operate largely independently — the idea behind microservices, sharding, stream processing, shared-nothing. Hard part: where to draw the lines.
  • Don't over-complicate. A single-machine database that does the job beats a distributed setup. Autoscaling is cool, but predictable load may be calmer with manual scaling. 5 services are simpler than 50.

MAINTAINABILITY 6 · Be kind to the next engineer

Software doesn't wear out — but requirements change, platforms change, bugs need fixing. Most of software's cost is after launch. Every valuable system becomes a legacy system one day (think COBOL nobody understands, knowledge that left with former staff) — and maintenance is as much a people problem as a technical one.

⚙ Operability

"Good operations can often work around bad software, but good software cannot run reliably with bad operations."

Automation is two-edged: the cases it can't handle are the hardest ones, so more automation needs a more skilled ops team — and a misbehaving automated system is harder to debug.

Data systems help by: monitoring + observability, no dependency on single machines, docs & a clear "if I do X, Y happens" model, good defaults with overrides, self-healing with manual control, predictable behaviour.

🧩 Simplicity

Complexity slows everyone and hides bugs: a big ball of mud. "Simple" is subjective, though.

Essential vs accidental complexity (Brooks, "No Silver Bullet"): inherent to the problem vs caused by our tools. Useful, but flawed — the line moves as tooling improves.

Best tool: abstraction. SQL hides on-disk structures, concurrency and crash recovery. This book is about general-purpose abstractions (transactions, indexes, event logs) you build on.

🌱 Evolvability

Requirements are always in flux. Agile/TDD/refactoring help inside one codebase; evolvability is that agility at the whole-data-system level.

Loosely coupled + simple = easier to change.

Irreversibility is the big enemy: a DB migration you can't roll back is far riskier than one you can. Minimize irreversible steps.

7 · Practice — answer from memory

Scroll up = cheating yourself. Effortful recall now is what makes this stick next month.

1. One disk in a 3-node database cluster dies. Users notice nothing. This was…
A component stopped working (fault), but the system still met its SLO, so no failure. Fault tolerance worked.
2. Which faults most often take down many nodes at once?
Software faults are highly correlated: every node runs the same code and meets the same trigger (e.g. the 2012 leap second).
3. p50 = 200 ms, p99 = 1.5 s. What does the p99 tell you?
99 of 100 requests are faster than 1.5 s; 1 in 100 takes 1.5 s or longer. That's the tail.
4. A page makes 10 parallel backend calls; each has a 1% chance of being slow. Roughly what share of pages are slow?
1 − 0.99¹⁰ ≈ 9.6%. Tail latency amplification: the page waits for its slowest call.
5. In the book's case study, why materialize home timelines instead of polling a join?
5.8k posts/s × 200 followers ≈ 1.16M timeline writes/s, vs 2M polls/s × 200 follows = 400M lookups/s. Pay once at write time; reads become a cache hit.
6. You average the p99 of five servers to get a cluster p99. Verdict?
Averaging percentiles is mathematically meaningless. Add the underlying histograms, then compute the percentile.
7. A service near capacity slows down; clients time out and resend; it stays down even after traffic drops. This is…
Retry storm → metastable failure. Fix with exponential backoff, circuit breakers, load shedding, backpressure.
8. Several machines with own CPU/RAM share one SAN disk array. Which architecture?
Independent compute, common storage over a fast network (NAS/SAN) = shared-disk. Locking and contention limit how far it scales.
9. You plan a database migration. Which change most improves evolvability?
Irreversibility is a major obstacle to change. If you can roll back, the stakes are much lower.
