Environment Variables and Scripts

Every program you start is a child of your shell. It gets a copy of the shell's environment, runs, and hands back one number. Understand that, and export, source, cd, &&, and CI failures all stop being magic.

15–20 minutes WSL + bash First principles Sandbox only
Why this lesson exists. ASPNETCORE_ENVIRONMENT, DJANGO_SETTINGS_MODULE, NODE_ENV, CI secrets, .env files — your apps are configured through environment variables. Today you learn exactly how they flow from shell to program, and you write your first reusable script.

Warm-up — two gaps from last time

Recall 1

Why does which cd print nothing?

which only searches $PATH for files. A separate cd program would change its own directory, exit, and leave your shell where it was — so bash implements cd itself. type cd confirms it. Today's mental model is the general rule behind this.
Recall 2

What does false && echo yes; false || echo no print?

false exits non-zero (failure). && runs its right side only after success → skipped. || runs its right side only after failure → prints no. ; just runs the next command regardless.

The one mental model

Running a program creates a child process. The child receives its arguments and a copy of the parent's exported environment. Changes flow down, never back up. The only thing the child returns is its exit status.

That's why cd must be a builtin, why a script can't set variables in your terminal unless you source it, and why CI decides pass/fail by exit status alone.

Knowledge you need

Shell variables vs environment variables

$ foo=bar                 # no spaces around =
$ echo "$foo"             # bar
$ bash -c 'echo $foo'     # (empty) — child didn't get it
$ export foo              # now it's an environment variable
$ bash -c 'echo $foo'     # bar
$ unset foo               # remove it

A plain assignment creates a shell variable, visible only to this shell. export marks it to be copied into every child. Convention: environment variables are ALL_CAPS (HOME, PATH, DEBUG). printenv lists what children will receive.

Set a variable for one command only

$ TZ=Asia/Jakarta date    # this date runs with Jakarta time
$ echo "$TZ"              # (empty) — your shell was never changed

Prefixing VAR=value puts it into that one child's environment and nowhere else. This is the cleanest way to run an app in a different mode without polluting your terminal.

Command substitution

$ today=$(date +%F)
$ echo "backup-$today.sql"   # backup-2026-09-23.sql

$(cmd) runs cmd and replaces itself with the command's stdout. Always wrap expansions in double quotes ("$today") so spaces don't split them into multiple arguments.

Scripts: shebang, permission, ./

#!/usr/bin/env bash
echo "script name: $0"
echo "first arg:   $1"
echo "all args:    $@"
echo "arg count:   $#"
exit 0
  • Shebang #!/usr/bin/env bash — first line tells the kernel which interpreter runs the file. env finds bash via $PATH.
  • chmod +x script.sh — marks the file executable. Without it: Permission denied.
  • ./script.sh — the current directory is not in $PATH (a safety choice, so a malicious ls file in some folder can't hijack you). ./ gives an explicit path.
  • $1 $2 … $@ $# — the arguments, all of them, and how many. ${1:-dev} means "$1, or dev if missing".
  • exit N — the one number the script hands back. 0 = success.

Run vs source

$ ./env.sh        # runs in a CHILD — its cd/export vanish when it exits
$ source env.sh   # runs in THIS shell — its cd/export stick

source (or its short form .) reads the file into your current shell. This is how ~/.bashrc and Python virtualenvs (source .venv/bin/activate) change your terminal: they must be sourced, because a child can't modify its parent.

A safer script header

#!/usr/bin/env bash
set -euo pipefail

Not in the lecture, but standard practice (see help set / the Bash manual): -e stop at the first failing command, -u treat unset variables as errors, -o pipefail make a pipeline fail if any part fails (by default only the last command counts). Without these, a script can fail halfway and still report success.

Check yourself

Quiz 1

You run APP_ENV=staging (no export), then python app.py. What does the Python program see for APP_ENV?

Only exported variables are copied into children. Fix with export APP_ENV=staging, or one-shot: APP_ENV=staging python app.py.
Quiz 2

setup.sh contains cd /tmp and export DEBUG=1. After ./setup.sh, where is your shell and what is $DEBUG?

./setup.sh runs in a child; its cd and export die with it. source setup.sh would give "in /tmp, DEBUG is 1".
Quiz 3

Without set -o pipefail, what is $? after false | true?

By default a pipeline's status is its last command's. That hides failures like python manage.py dumpdata | gzip > backup.gz — gzip succeeds even if the dump crashed. pipefail fixes it.

Sandbox task — 10 minutes

Work in ~/shell-sandbox. Nothing here touches your work projects.

  1. Down, not up. Run foo=bar; bash -c 'echo "child: $foo"', then export foo; bash -c 'echo "child: $foo"'. Explain the difference in one sentence.
  2. One-shot variable. Run TZ=Asia/Tokyo date, then date, then echo "TZ is: $TZ".
  3. Write a script. Create run-app.sh: 
    #!/usr/bin/env bash
set -euo pipefail

app_env="${1:-Development}"
echo "Starting in $app_env with $# argument(s)"

APP_ENV="$app_env" bash -c 'echo "child sees APP_ENV=$APP_ENV"'
echo "parent sees APP_ENV=${APP_ENV:-}"

if [ "$app_env" = "Production" ]; then
  echo "Refusing to run Production from a sandbox" >&2
  exit 1
fi
  4. Try ./run-app.sh first — read the error. Then chmod +x run-app.sh and run ./run-app.sh, ./run-app.sh Staging.
  5. Exit codes. Run ./run-app.sh Production; echo "exit: $?", then ./run-app.sh Staging && echo "deploy step would run" and the same with Production. Where did the "Refusing…" line go — stdout or stderr? Prove it with ./run-app.sh Production 2> /dev/null.
  6. Run vs source. Create env.sh containing cd /tmp and export DEBUG=1. Run bash env.sh; pwd; echo "$DEBUG". Then source env.sh; pwd; echo "$DEBUG". Then cd ~/shell-sandbox; unset DEBUG to clean up.

Stretch (if time): run false | true; echo $?, then set -o pipefail; false | true; echo $?. Open a fresh terminal afterwards — set only changed that shell.

Retrieval practice

Without running anything, explain in your own words: why does source .venv/bin/activate work, but bash .venv/bin/activate seems to do nothing? Use the words child process, parent, and environment.

Model answer (after you have tried)

activate changes PATH (so python resolves to the venv's copy) and sets VIRTUAL_ENV. bash activate runs it in a child process: the child's environment changes, then the child exits and its changes vanish — the parent shell never sees them. source runs the file inside the current shell, so the changes stick. Same reason cd is a builtin.

Connect it to your work

  • DJANGO_SETTINGS_MODULE=config.settings.test python manage.py test — one-shot settings switch. Default manage.py uses os.environ.setdefault(...), so a variable already in the environment wins over the file's default. (Your project's module name may differ.)
  • ASPNETCORE_ENVIRONMENT=Staging dotnet run — picks appsettings.Staging.json. Caveat: Properties/launchSettings.json profiles can set it too; dotnet run --no-launch-profile ignores them. Check your project before trusting either.
  • NODE_ENV=production npm run build — same pattern for React tooling.
  • CI pipelines are chains of child processes: a step "fails" only when some command exits non-zero. set -euo pipefail at the top of every deploy script makes failures actually fail.
  • Security: secrets belong in environment variables or a secret store, never hardcoded in scripts or committed .env files. But children inherit everything you export — don't export tokens in a shell where you then run untrusted tools.
