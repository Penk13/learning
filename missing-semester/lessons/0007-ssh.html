SSH: Remote Shells and Keys

SSH is an encrypted pipe to a shell on another machine, opened with a key pair instead of a password.

The model

SSH carries stdin, stdout and stderr through an encrypted connection, so remote commands compose with local ones. You prove who you are with a key pair: the private key stays with you, the public key goes on the server.

Where does each part run?

$ ssh alice@server.example.com          # interactive shell as alice
$ ssh alice@server ls | wc -l           # ls REMOTE, wc LOCAL
$ ssh alice@server 'ls | wc -l'         # both remote (one quoted string)

Your local shell interprets everything unquoted first, including |, > and $VAR. Quoting decides what is sent to the server.

Keys instead of passwords

$ ssh-keygen -a 100 -t ed25519 -f ~/.ssh/id_ed25519
#   ~/.ssh/id_ed25519      ← PRIVATE: never share, never commit
#   ~/.ssh/id_ed25519.pub  ← PUBLIC: safe to give to servers / GitHub
$ ssh-copy-id -i ~/.ssh/id_ed25519 alice@server   # appends .pub to ~/.ssh/authorized_keys

The server checks that you hold the private key without the key ever crossing the network. Protect the private key with a passphrase; ssh-agent remembers it so you don't retype it. Use one key per machine, so you can revoke one without the others. If a private key leaks, remove its public key everywhere and generate a new pair. GitHub SSH remotes (git@github.com:…) use these same keys.

~/.ssh/config: name your hosts

Host vm
    User alice
    HostName 172.16.174.141
    Port 2222
    IdentityFile ~/.ssh/id_ed25519
    LocalForward 9999 localhost:8888

Now ssh vm is enough. scp, rsync and git read the same file, so the short name works everywhere.

Copying files

$ scp ./app.zip vm:/tmp/app.zip              # simple copy
$ rsync -av --partial ./dist/ vm:/srv/app/   # sends only changes; resumable

Prefer rsync for anything bigger than one file. Trailing slash matters: dist/ copies the folder's contents, dist copies the folder itself.

Port forwarding

$ ssh -L 9999:localhost:8888 vm    # -L local_port:target_host:target_port

Traffic to localhost:9999 on your laptop travels through the tunnel and comes out on the server as localhost:8888. The target address is resolved on the server. This is how you reach a web UI or database that only listens inside the server, without exposing anything publicly. (LocalForward in the config does the same.)

For bad connections, Mosh is an SSH alternative that survives network changes and laptop sleep. For work servers, follow your organisation's access process; practise only on your own VM.

Check yourself

In ssh vm ls | wc -l, where do ls and wc run, and how do you make both run on vm?

ls runs on vm, wc runs locally: your local shell splits on the unquoted |, so only ls is sent. Quote the whole command: ssh vm 'ls | wc -l'.

Which file is safe to paste into GitHub's "SSH keys" settings?

Only the public .pub key leaves your machine. The private key works like a password; if it leaks, remove its public key from every server and account and generate a new pair.

A PostgreSQL server on host vm listens only on vm's own port 5432. You run ssh -L 5433:localhost:5432 vm.

What can you now do from your laptop, and does this expose the database publicly?

Point a local client at localhost:5433; traffic goes through the SSH tunnel and reaches port 5432 on vm (localhost is resolved on the server). Nothing new is exposed publicly; only you, through SSH, reach it.
