Introduction to the Shell

Every command your IDE hides from you is a program. The shell is a programming language and a plumbing system: type a command, and its text output flows to your terminal — or straight into the next program.

15–20 minutes WSL + bash First principles Sandbox only
Why this lesson exists. In your .NET/React and Django work you run dotnet run, npm test, and python manage.py migrate hundreds of times. Today you learn what is actually happening under each of those commands — and how to combine programs instead of reaching for copy-pasted incantations.

The one mental model

A command is a program plus arguments. The shell splits your line into words, finds the program, runs it with your arguments, and its standard output flows to the terminal — or, with a pipe, into the next program.
you type
echo hello
→
shell splits it
into words
→
shell finds
the program
→
program runs &
prints text

The terminal is just the window you type into. The shell (on WSL/Linux: bash) is the program inside that window which interprets your commands. Verify yours: echo $SHELL should print something like /bin/bash. Nearly every conclusion in this lesson comes from the GNU Bash manual or the man pages on your own machine — the best help is installed locally.

Knowledge you need

Reading the prompt

missing:~$ date
Fri 10 Jan 2020 11:49:31 AM EST
missing:~$ echo hello
hello

The prompt missing:~$ shows the machine and your current working directory (~ = your home). The $ means you are a normal user, not root. The shell parses your line by splitting it on whitespace: the first word is the program, the rest are arguments. An argument containing spaces must be quoted ("My Photos") or escaped (My\ Photos).

How the shell finds programs

$ echo $PATH
/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin
$ which echo
/bin/echo

$PATH is a :-separated list of directories. The shell looks there for a program named echo; which echo tells you which file it found. That is why dotnet, npm, and python work from anywhere — they are files in $PATH directories.

Help is local

man date opens the manual for any command; most programs also accept --help. The course suggests tldr for quick examples and notes that LLMs are also good at explaining command usage.

Streams, redirection, and pipes

Every program has three standard streams: stdin (input, 0), stdout (normal output, 1), and stderr (errors, 2). By default all flow to your terminal. You can redirect them:

$ date > now.txt          # overwrite a file with stdout
$ date >> log.txt         # append instead
$ grep hi < notes.md     # read stdin from a file
$ ls /nonexistent 2> err.txt   # send errors to a file

And a pipe | connects two programs: stdout of the left becomes stdin of the right.

$ grep TODO notes.md | wc -l
2

This counts how many lines of notes.md contain TODO. Two programs, one composed task — that composition is the whole point of the shell.

Exit status and control operators

Every program exits with a status: 0 means success, anything else means failure. $? holds the last command's status.

$ date; echo $?      # 0 — it worked
$ true  && echo yes   # yes  (&& runs only after success)
$ false || echo no    # no   (|| runs only after failure)

Two commands worth knowing today

ls -l prints one line per file; the first 10 characters are the file type and permissions (e.g. -rw-r--r-- = regular file, owner can read/write, everyone else reads). man ls decodes the rest. cd is a shell builtin, not a program — the next lesson (or the official exercises) explains why. which cd prints nothing for this reason.

Check yourself

Quiz 1

What does the shell actually do when you type echo hello?

The first word names a program the shell finds via $PATH; the remaining words are passed to that program as arguments. echo then happens to print them.
Quiz 2

How does the shell find the program for a command like date?

$PATH is a :-separated list of directories. The shell tries each in order until it finds an executable file with that name; which date shows the winner.
Quiz 3

What does the pipe in grep TODO notes.md | wc -l do?

A pipe connects stdout of the left program to stdin of the right one. grep finds matching lines; wc -l counts the lines it receives.

Sandbox task — 10 minutes

Work in a disposable directory. Nothing here touches your work projects.

  1. mkdir -p ~/shell-sandbox && cd ~/shell-sandbox
  2. Run ls -l / and look at the first 10 characters of three different lines. Which ones are directories? Which are regular files? (Hint: man ls.)
  3. Create test files: touch notes.txt report.txt photo.jpg a.txt b.txt c.txt. Then try ls *.txt, ls file?.txt, and ls {a,b,c}.txt. The *, ?, and {} patterns are called globs — the shell expands them before running the program.
  4. Contrast quoting: echo '$PATH' vs echo "$PATH". Single quotes are literal; double quotes expand variables.
  5. Redirect: create a file with date > now.txt, inspect it with cat now.txt, then append with date >> now.txt.
  6. Compose: create notes.md with two lines containing the word TODO, then run grep TODO notes.md | wc -l. You should see 2.

Stretch (if time): ls /nonexistent /tmp > out.txt 2> err.txt then inspect both files — one holds the listing, the other the error. That is stdin/stdout/stderr in action.

Retrieval practice

Without running anything, write your prediction: what exactly will grep TODO notes.md | wc -l print when notes.md contains exactly two lines that each include TODO? For each word in the command, say what it does. Then run it in your sandbox and compare your prediction.

Model answer (after you have tried)

grep reads notes.md, keeps only lines containing TODO, and writes those two lines to its stdout. The pipe feeds them into wc's stdin; wc -l counts lines and prints 2. So the command prints the single number 2. The pipeline is one composed program: find then count.

Connect it to your work

  • python manage.py migrate | tee deploy.log — tee shows output on screen and saves it to a file: a one-word upgrade for any deployment command you run manually.
  • npm test && npm run build in your React work is exactly the && control operator: build only runs if tests succeeded.
  • When dotnet run fails, the error you see is stderr — and echo $? right after (or dotnet run; echo $?) tells your script whether it failed, which is how CI systems decide to fail a build.
  • Interview framing: "the shell is a programming language where each command is a program and pipes compose them" is the sentence that separates rote users from people who understand the model.
