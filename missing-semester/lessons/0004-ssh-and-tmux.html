SSH and tmux

SSH gives you a shell on another machine. tmux keeps a shell alive after you disconnect. Together they make working on a server feel like working locally, even over a bad connection.

15–20 minutes WSL + bash Read first, practise later Sandbox only
Why this lesson exists. Deploying, reading logs, running migrations on a server, pushing to Git over SSH, or reaching a database that only listens on a private network all use SSH. A long migration that dies because your Wi-Fi blinked is exactly the problem tmux solves.

The two mental models

SSH = an encrypted pipe to a shell on another machine. It carries stdin, stdout and stderr just like a local pipe, so remote commands compose with local ones. You prove who you are with a key pair: the private key stays with you, and the public key goes on the server.
tmux = a server process that owns your shells. Your terminal is just a viewer. Close the viewer (or lose the connection), and the shells keep running. Reattach later and everything is exactly where you left it.

Knowledge you need — SSH

Connecting and running commands

$ ssh alice@server.example.com          # interactive shell as user alice
$ ssh alice@server ls | wc -l           # ls runs REMOTELY, wc runs LOCALLY
$ ssh alice@server 'ls | wc -l'         # both run remotely (quoted = sent as one string)

The quoting decides where each part runs. Your local shell interprets anything unquoted first, including |, > and $VAR.

Keys instead of passwords

$ ssh-keygen -a 100 -t ed25519 -f ~/.ssh/id_ed25519    # create a key pair
#   ~/.ssh/id_ed25519      ← PRIVATE key: never share, never commit
#   ~/.ssh/id_ed25519.pub  ← PUBLIC key: safe to give to servers / GitHub

$ ssh-copy-id -i ~/.ssh/id_ed25519 alice@server        # appends .pub to server's ~/.ssh/authorized_keys

Key authentication uses public-key cryptography. The server checks that you hold the private key without the key ever crossing the network. It's more secure and more convenient than passwords. Treat the private key like a password, and protect it with a passphrase (ssh-agent remembers the passphrase so you don't retype it). If you've set up GitHub over SSH, you already did these steps.

~/.ssh/config: name your hosts

Host vm
    User alice
    HostName 172.16.174.141
    Port 2222
    IdentityFile ~/.ssh/id_ed25519

Host *.example.com          # wildcards apply defaults to many hosts
    User alice

Now ssh vm is enough. scp, rsync, git and others read the same file, so the short name works everywhere.

Copying files

$ scp ./app.zip vm:/tmp/app.zip              # simple copy (local → remote)
$ rsync -av --partial ./dist/ vm:/srv/app/   # only sends what changed; can resume

rsync skips files that are already identical and keeps permissions and symlinks. Prefer it for anything bigger than a single file. (Watch the trailing / on the source: dist/ copies the folder's contents, while dist copies the folder itself.)

Port forwarding

Host vm
    ...
    LocalForward 9999 localhost:8888   # your localhost:9999 → vm's localhost:8888

# one-off equivalent on the command line:
$ ssh -L 9999:localhost:8888 vm

Traffic to localhost:9999 on your laptop travels through the SSH tunnel and comes out on the server as localhost:8888. This is how you open a web UI or database that is only reachable from inside the server. The official exercises use exactly this setup.

Bad connections: Mosh

Mosh is an SSH alternative that survives network changes, laptop sleep and high latency. It's optional; tmux covers the most important part, which is not losing your work.

Knowledge you need — tmux

The prefix key

Every tmux shortcut starts with the prefix Ctrl-b. Press Ctrl-b, release it, then press the next key. Written as <C-b> d.

Hierarchy: sessions → windows → panes

  • Session: an independent workspace (one per project or task).
  • Window: like a browser tab inside a session.
  • Pane: a split inside a window, so you can see several shells at once.
# Sessions (typed in a normal shell)
$ tmux                    # new session
$ tmux new -s deploy      # new session named "deploy"
$ tmux ls                 # list sessions
$ tmux a                  # attach to the last session
$ tmux a -t deploy        # attach to a specific one
  <C-b> d                 # DETACH: leave it running in the background

# Windows
  <C-b> c                 # create window      (exit / Ctrl-d closes it)
  <C-b> n / p             # next / previous window
  <C-b> 0..9              # jump to window N
  <C-b> ,                 # rename window
  <C-b> w                 # list windows

# Panes
  <C-b> "                 # split top / bottom
  <C-b> %                 # split left / right
  <C-b> <arrow>           # move between panes
  <C-b> z                 # zoom current pane (toggle)
  <C-b> [                 # scrollback mode (q to leave)
  <C-b> <space>           # cycle pane layouts

Why tmux beats nohup on servers

From lesson 0003: closing a terminal sends SIGHUP to its jobs. Inside tmux, your shell's parent is the tmux server, not the SSH connection. When SSH drops, tmux keeps running and so does your shell. Unlike nohup, you can reattach and interact again, with full scrollback.

Connect it to your work

  • Long server tasks: ssh server, then tmux new -s migrate, then run python manage.py migrate or a long dotnet ef database update. If the connection drops, ssh server then tmux a -t migrate brings you back.
  • Local dev layout: one tmux window with panes for dotnet watch, npm run dev and a free shell. Works the same in WSL.
  • Git: git@github.com:… remotes use the same SSH keys and ~/.ssh/config.
  • Security: never copy a private key into a repo, chat or shared drive. Use a separate key per machine so you can revoke one without the others. For work servers, follow your organisation's access process. Practise only on your own VM or localhost.

Check yourself

Quiz 1

In ssh vm ls | wc -l, where does wc run?

To run both remotely, quote the whole command: ssh vm 'ls | wc -l'.
Quiz 2

Which file is safe to paste into GitHub's "SSH keys" settings?

Only the .pub (public) key leaves your machine. The private key works like a password. If it ever leaks, remove its public key from every server and account, and generate a new pair.
Quiz 3

Your SSH connection drops while a migration runs inside tmux. What state is it in?

The shell's parent is the tmux server on the remote machine, which never received a hang-up. Only the viewer (your SSH session) went away.
Quiz 4

What does ssh -L 5433:localhost:5432 vm let you do?

-L local_port:target_host:target_port. The target address is resolved on the server, so localhost there means the server itself. Nothing new is exposed publicly.

Sandbox task — 10 minutes

No real server needed: practise tmux in WSL. For SSH, use only a VM you own, or skip it for now.

  1. Session survives. tmux new -s play, run top, press <C-b> d. Run tmux ls. Close the whole terminal window, open a new one, and run tmux a -t play. Is top still running?
  2. Panes. Inside tmux: <C-b> %, <C-b> ", move with <C-b> <arrow>, zoom with <C-b> z.
  3. Windows. <C-b> c twice, rename one with <C-b> ,, switch with <C-b> 0/1/2 and <C-b> w.
  4. Keys (read-only check). ls -l ~/.ssh/. Do you already have an id_ed25519/.pub pair (for example, from GitHub)? Don't print the private key.
  5. Clean up. tmux kill-session -t play.

Stretch (official exercise, needs your own Linux VM): add a Host vm entry with LocalForward 9999 localhost:8888, run python3 -m http.server 8888 on the VM, and open http://localhost:9999 on your machine.

Retrieval practice

In your own words: explain to a teammate why running a long command over SSH inside tmux is safer than running it with &. Use the words SIGHUP, parent, detach and reattach.

Model answer (after you have tried)

With &, the job's parent is the shell that belongs to your SSH session. When the connection drops, that shell gets SIGHUP and passes it on, so the job dies. Inside tmux, the shell's parent is the tmux server, which isn't tied to your connection. You can detach on purpose or lose the network, and the job keeps running. Later you reattach and see its live output and scrollback, which nohup can't give you.
