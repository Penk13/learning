Environment Variables

Every program is a child of your shell: it gets a copy of the exported environment, and changes flow down, never back up.

The model

Running a program creates a child process. The child receives its arguments and a copy of the parent's exported environment. Its changes stay private. The only thing it hands back is its exit status.

This one rule explains why cd is a builtin, why a script can't change your terminal unless you source it, and why CI decides pass/fail by exit status alone.

Shell variable vs environment variable

$ foo=bar                 # no spaces around =
$ echo "$foo"             # bar
$ bash -c 'echo $foo'     # (empty) — the child didn't get it
$ export foo              # now it's an environment variable
$ bash -c 'echo $foo'     # bar
$ unset foo               # remove it

A plain assignment is a shell variable, visible only in this shell. export marks it to be copied into every child. printenv lists what children will receive. Convention: environment variables are ALL_CAPS (HOME, PATH).

One-shot variables

$ TZ=Asia/Jakarta date    # this date runs with Jakarta time
$ echo "$TZ"              # (empty) — your shell never changed

VAR=value cmd puts the variable into that one child's environment and nowhere else. It is the clean way to switch an app's mode:

  • DJANGO_SETTINGS_MODULE=config.settings.test python manage.py test (module name depends on your project)
  • ASPNETCORE_ENVIRONMENT=Staging dotnet run (a launchSettings.json profile can also set it; --no-launch-profile ignores profiles)
  • NODE_ENV=production npm run build

Command substitution and quoting

$ today=$(date +%F)
$ echo "backup-$today.sql"   # backup-2026-09-23.sql

$(cmd) runs cmd and is replaced by its stdout. Wrap expansions in double quotes ("$today") so a value with spaces stays one argument.

Security note

Secrets belong in environment variables or a secret store, never hardcoded in scripts or committed .env files. But every child inherits what you export, so don't export tokens in a shell where you then run untrusted tools.

Try it

  1. foo=bar; bash -c 'echo "child: $foo"', then export foo and repeat.
  2. TZ=Asia/Tokyo date, then date, then echo "TZ is: $TZ".

Check yourself

In bash you run APP_ENV=staging on its own line (no export), then python app.py. What does the Python program see for APP_ENV?

Only exported variables are copied into children. Fix with export APP_ENV=staging, or one-shot: APP_ENV=staging python app.py.

In bash, what is the difference between export TZ=Asia/Tokyo; date and TZ=Asia/Tokyo date?

The first sets and exports TZ in the current shell, so every later child (not just date) gets it. The second puts TZ only into that one date process; the shell itself is unchanged afterwards.

State the parent/child rule for processes started from a shell: what does the child receive, and what can it give back?

The child receives its arguments and a copy of the parent's exported environment (and the working directory). Its own changes to environment or directory stay private. It hands back only its exit status.
