Shell Scripts: Run vs Source

A script runs in a child unless you source it; strict mode makes its failures actually fail.

Anatomy of a script

#!/usr/bin/env bash
echo "script name: $0"
echo "first arg:   $1"
echo "all args:    $@"
echo "arg count:   $#"
exit 0
  • Shebang #!/usr/bin/env bash: the first line tells the kernel which interpreter runs the file; env finds bash via $PATH.
  • chmod +x script.sh: marks it executable. Without it: Permission denied.
  • ./script.sh: the current directory is not on $PATH (so a malicious ls file in some folder can't hijack you); ./ gives an explicit path.
  • $1 $2 … $@ $#: the arguments, all of them, how many. ${1:-dev} means "$1, or dev if missing".
  • exit N: the one number handed back. 0 = success.

Run vs source

$ ./env.sh        # runs in a CHILD — its cd/export vanish when it exits
$ source env.sh   # runs in THIS shell — its cd/export stick
$ . env.sh        # same as source

This is why source .venv/bin/activate works and bash .venv/bin/activate seems to do nothing: activate changes PATH and sets VIRTUAL_ENV, and only sourcing applies that to your shell.

Strict mode

#!/usr/bin/env bash
set -euo pipefail
  • -e: stop at the first failing command.
  • -u: an unset variable is an error, not an empty string.
  • -o pipefail: a pipeline fails if any part fails. By default only the last command's status counts.

Not from the lecture, but standard practice (see help set). Without it, python manage.py dumpdata | gzip > backup.gz "succeeds" even when the dump crashed, because gzip succeeded. Check scripts with shellcheck; a script past ~100 lines is usually better in Python.

Try it

  1. Write env.sh with cd /tmp and export DEBUG=1. Run bash env.sh; pwd; echo "$DEBUG", then source env.sh; pwd; echo "$DEBUG".
  2. false | true; echo $?, then set -o pipefail and repeat.

Check yourself

Why does source .venv/bin/activate change your terminal, while bash .venv/bin/activate seems to do nothing? Use the words child process, parent and environment.

activate changes PATH and sets VIRTUAL_ENV. bash activate runs it in a child process; the child's environment changes, then the child exits and the parent shell never sees them. source runs the file inside the current shell, so the changes stick.

setup.sh contains cd /tmp and export DEBUG=1. You run ./setup.sh from ~/project.

Afterwards, what is your shell's directory and what is $DEBUG? What would change with source setup.sh?

Still in ~/project and DEBUG is unset: ./setup.sh ran in a child and its cd and export died with it. With source setup.sh you would be in /tmp with DEBUG=1.

A backup script runs python manage.py dumpdata | gzip > backup.gz. The dump crashes, but the CI step is green.

Why, and what one line fixes it?

By default a pipeline's exit status is that of its last command, and gzip succeeded. Put set -euo pipefail (at least set -o pipefail) at the top so any failing part fails the pipeline and stops the script.
