Signals

Ctrl-C is the OS delivering a small numbered message; the process decides what to do with it.

The model

A signal is a tiny message (a name/number) the OS delivers to a process. The process can handle it (run its own code), ignore it, or take the default action (usually: die). SIGKILL and SIGSTOP can't be caught.

So "Ctrl-C doesn't work" usually means the program chose to catch SIGINT.

The signals worth knowing

SignalSent byNotes
SIGINTCtrl-C"interrupt"; catchable
SIGQUITCtrl-\stronger quit; catchable but rarely caught, so it often works when Ctrl-C is ignored
SIGTERMkill PIDpolite "please exit"; well-behaved programs clean up
SIGKILLkill -9 PIDcan't be caught; instant death, no cleanup
SIGTSTPCtrl-Zpause; terminal version of the uncatchable SIGSTOP
SIGHUPterminal closes"hang up"; default: die

kill -l lists all signals; man signal describes them. Despite its name, kill just sends a signal, SIGTERM by default.

A program that ignores Ctrl-C

import signal, time
def handler(signum, frame):
    print("\nI got a SIGINT, but I am not stopping")
signal.signal(signal.SIGINT, handler)   # replace the default action
while True:
    time.sleep(.1)

Ctrl-C now only prints a message; Ctrl-\ still kills it because SIGQUIT has no handler. "Stop" is something the process agrees to.

Sending signals

$ pgrep -lf runserver      # find processes → PID + command line
$ kill 18653               # SIGTERM (polite) — try this first
$ kill -9 18653            # SIGKILL — last resort
$ pkill -f "sleep 1000"    # signal by matching the command line

kill -9 skips all cleanup: temp files stay, data can be half-written, child processes can be orphaned.

Graceful shutdown in real systems

  • Containers: docker stop sends SIGTERM, waits a grace period (10 s by default), then sends SIGKILL. Kubernetes pod termination works the same way.
  • .NET: the Generic Host treats Ctrl-C and SIGTERM as "stop gracefully" and fires IHostApplicationLifetime.ApplicationStopping. Put cleanup there.
  • Django: Gunicorn treats SIGTERM as graceful shutdown; check your server's docs, as some use SIGHUP for "reload config".
  • Container PID 1: if a shell script is the entrypoint and starts your app as a child, the signal may hit the script and never reach the app. End the script with exec dotnet MyApp.dll (or exec gunicorn …): exec replaces the shell with the app, so the app gets signals directly.

Check yourself

You press Ctrl-C on a Linux program and it keeps running.

What is the most likely reason, and what do you try next, in order?

Ctrl-C sends SIGINT, which the program caught with its own handler. Try Ctrl-\ (SIGQUIT) or kill PID (SIGTERM) from another terminal; use kill -9 (SIGKILL, uncatchable) only as a last resort.

Why is kill -9 a last resort rather than the default way to stop a process?

Plain kill (SIGTERM) lets the app finish requests, flush files and run its cleanup. SIGKILL skips all of that and can leave orphaned children or corrupted data.

Step by step, what happens when docker stop runs on an ASP.NET Core or Django container? Use SIGTERM, grace period, SIGKILL and graceful shutdown.

Docker sends SIGTERM to the container's main process; the app starts a graceful shutdown (stops accepting requests, finishes in-flight ones, releases resources). Docker waits a grace period (10 s by default); if the process is still alive, it sends SIGKILL, which can't be caught. If a wrapper shell script doesn't exec the app, the app may never see SIGTERM and always gets killed.
