Signals and Job Control

Ctrl-C isn't magic: it's the shell sending your program a small numbered message. Once you know that, stopping, pausing, backgrounding and gracefully shutting down a program all work the same way.

15–20 minutes WSL + bash Read first, practise later Sandbox only
Why this lesson exists. You stop dotnet run, npm run dev and python manage.py runserver with Ctrl-C many times a day. Docker, Kubernetes and CI runners stop your apps with the same mechanism. If your app ignores it or handles it badly, you get hung deploys, lost requests and leftover temp files.

The one mental model

A signal is a tiny message (just a name/number) that the OS delivers to a running process. The process can handle it (run its own code), ignore it, or take the default action (usually: die). Two signals can't be caught: SIGKILL and SIGSTOP.

That's why Ctrl-C "sometimes doesn't work": the program chose to catch SIGINT. Signals are software interrupts: they break into whatever the process was doing.

Knowledge you need

The signals worth knowing

  • SIGINT: "interrupt". Sent by Ctrl-C. Catchable.
  • SIGQUIT: sent by Ctrl-\. A stronger "quit" from the terminal. Catchable, but programs rarely catch it, so it works when Ctrl-C is ignored.
  • SIGTERM: the polite, generic "please exit". The default for kill PID. Well-behaved programs clean up and exit.
  • SIGKILL: kill -9 PID. Cannot be caught. Instant death, with no cleanup, so it can leave temp files, half-written data, or orphaned child processes. Use it as a last resort.
  • SIGTSTP: sent by Ctrl-Z. Pauses (suspends) the process. It's the terminal's version of SIGSTOP, which can't be caught.
  • SIGHUP: "hang up". Sent to your jobs when the terminal closes. Default: die.

kill -l lists every signal; man signal describes them. Despite its name, kill just sends a signal, and SIGTERM is only the default.

A program that ignores Ctrl-C

#!/usr/bin/env python
import signal, time

def handler(signum, frame):
    print("\nI got a SIGINT, but I am not stopping")

signal.signal(signal.SIGINT, handler)   # replace the default action
i = 0
while True:
    time.sleep(.1)
    print("\r{}".format(i), end="")
    i += 1

Ctrl-C now just prints a message. Ctrl-\ (SIGQUIT) still kills it because it has no handler for that one. This is the lecture's example, and it shows that "stop" is something the process agrees to.

Sending signals by PID

$ pgrep -lf sleep          # find processes by name → PID + command line
$ kill 18653               # SIGTERM (polite)
$ kill -TERM 18653         # same, explicit
$ kill -9 18653            # SIGKILL (last resort)
$ pkill -f "sleep 1000"    # signal by matching name, no PID needed

Jobs: foreground, background, suspended

A job is a command your current shell started. Only one job owns the keyboard (the foreground). Others can run in the background or be suspended (paused).

$ sleep 1000 &             # & = start in background, prompt returns
[1] 18653
$ sleep 2000               # foreground… now press Ctrl-Z
^Z
[2]+ Stopped     sleep 2000
$ jobs                     # list this shell's jobs
[1]- Running     sleep 1000 &
[2]+ Stopped     sleep 2000
$ bg %2                    # resume job 2 in the background
$ fg %1                    # bring job 1 to the foreground (Ctrl-C to stop it)
$ kill %2                  # %N = job number, works anywhere a PID does
$ echo $!                  # PID of the last backgrounded job

Common move: you started something long and forgot &. Press Ctrl-Z, then bg. A background job still writes to your terminal, so redirect its output if it's noisy: long-task > task.log 2>&1 &.

Surviving a closed terminal

Background jobs are still children of your terminal's shell. Closing the terminal sends them SIGHUP, and they die. Three ways to keep them alive:

  • nohup cmd &: start it ignoring SIGHUP. Output goes to nohup.out.
  • disown: for a job that's already running, remove it from the shell's job table so it isn't sent SIGHUP.
  • tmux: the better answer, covered in lesson 0004. The shell itself lives on, detached.

Cleanup in scripts: trap

#!/usr/bin/env bash
set -euo pipefail

tmpdir=$(mktemp -d)
cleanup() {
    echo "Cleaning up $tmpdir"
    rm -rf "$tmpdir"
}
trap cleanup EXIT   # runs when the script exits, success or failure

# … work using "$tmpdir" …

trap CMD SIGNALS… runs CMD when the script receives those signals. EXIT is a bash pseudo-signal for "the script is ending for any reason". It still runs after Ctrl-C (SIGINT) and kill (SIGTERM), so you rarely need to trap those separately. Nothing runs on SIGKILL, which is another reason to avoid kill -9.

Waiting for background work

$ sleep 5 &
$ wait            # block until all background children finish
$ wait $!         # or just the last one

wait only works on your own children. For an unrelated process, kill -0 PID sends no signal. It only checks whether the process exists (exit status 0 if it does). You'll practise this in the exercises.

Connect it to your work

  • Containers: docker stop sends SIGTERM, waits a grace period (10 s by default), then sends SIGKILL. Kubernetes pod termination works the same way. If your app shuts down slowly or ignores SIGTERM, in-flight requests get cut off.
  • .NET: the Generic Host (used by ASP.NET Core) treats Ctrl-C and SIGTERM as "stop gracefully". It fires IHostApplicationLifetime.ApplicationStopping and cancels hosted services' tokens. Put cleanup there, not in code that assumes the process just disappears.
  • Django: production servers like Gunicorn treat SIGTERM as a graceful shutdown: workers finish current requests first. Check your server's docs for its exact signal meanings, because some use SIGHUP for "reload config".
  • Container PID 1: if a shell script is the container's entrypoint and starts your app as a child, the signal may hit the script and never reach the app. The usual fix is exec dotnet MyApp.dll (or exec gunicorn …) as the script's last line: exec replaces the shell with your app, so the app receives the signals directly.
  • Day to day: a dev server that won't die after Ctrl-C usually still holds the port. Use pgrep -lf runserver (or dotnet/node), then kill, and only then kill -9.

Check yourself

Quiz 1

You press Ctrl-C and the program keeps running. What is the most likely reason?

Ctrl-C sends SIGINT, which is catchable. Try Ctrl-\ (SIGQUIT), or kill PID (SIGTERM) from another terminal. Use kill -9 only as a last resort.
Quiz 2

You started npm run build without & and want your prompt back without stopping it. What do you do?

Ctrl-Z suspends it (SIGTSTP). bg resumes it in the background. fg would put it back in the foreground, where you started.
Quiz 3

Why is kill -9 a last resort rather than the default?

Plain kill (SIGTERM) lets the app finish requests, flush files and run trap … EXIT. SIGKILL skips all of that and can leave orphaned children or corrupted data.
Quiz 4

You run python long_job.py &, then close the terminal window. What happens by default?

& only means "don't wait for it". It's still a child of the shell. Use nohup, disown, or better, tmux.

Sandbox task — 10 minutes

Work in ~/shell-sandbox.

  1. Jobs. Run sleep 1000, press Ctrl-Z, then jobs, bg, jobs. Note the state change from Stopped to Running.
  2. Find without typing the PID. pgrep -lf "sleep 1000", then pkill -f "sleep 1000", then jobs.
  3. Ignore Ctrl-C. Save the Python example above as sigint.py, run python3 sigint.py, press Ctrl-C twice, then Ctrl-\. Then run echo $? and note the number.
  4. trap. Save the trap cleanup EXIT script as tmpwork.sh, and add touch "$tmpdir/data"; sleep 30 after the trap. Run it, press Ctrl-C, and confirm the cleanup message prints.
  5. wait. sleep 5 & wait; echo "done after sleep".

Stretch (official exercise): write a bash function pidwait PID that loops with kill -0 "$1" and sleep 1 until the process is gone.

Retrieval practice

In your own words: what happens, step by step, when docker stop runs on your ASP.NET Core or Django container? Use the words SIGTERM, grace period, SIGKILL and graceful shutdown.

Model answer (after you have tried)

Docker sends SIGTERM to the container's main process. The app catches it and starts a graceful shutdown: it stops accepting new requests, finishes in-flight ones and releases resources. Docker waits for a grace period (10 s by default). If the process hasn't exited by then, Docker sends SIGKILL, which can't be caught, and the process dies immediately. If a wrapper shell script doesn't exec the app, the app may never see SIGTERM and always gets killed.
