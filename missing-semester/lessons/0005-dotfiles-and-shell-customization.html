Dotfiles and Shell Customization

Your shell rebuilds itself from plain-text files every time it starts. Edit those files and every new terminal gets your PATH, aliases and shortcuts. Keep them in Git and any machine can feel like home in a minute.

15–20 minutes WSL + bash Read first, practise later Sandbox only
Why this lesson exists. Installing the .NET SDK, Node or a Python tool usually ends with "add this to your PATH". Typing git status 50 times a day is a candidate for an alias. A new laptop or WSL distro shouldn't cost you a day of re-setup.

The one mental model

Every new interactive bash sources its startup files (mainly ~/.bashrc). Whatever those files export, alias or define exists in that shell, and exported values pass to its children. To change "my shell", you edit a dotfile, then open a new terminal or source it.

This connects directly to lesson 0002: .bashrc must be sourced, not run, because a child process couldn't change your shell.

Knowledge you need

Dotfiles

A dotfile is a plain-text config file whose name starts with ., which hides it from ls (use ls -a). That's just a convention. Common ones:

  • bash: ~/.bashrc, ~/.bash_profile (or ~/.profile)
  • git: ~/.gitconfig
  • ssh: ~/.ssh/config (lesson 0004)
  • tmux: ~/.tmux.conf
  • vim: ~/.vimrc

Which bash file? Startup rules are complicated (login vs interactive shells). The practical rule: put aliases, functions, PATH changes and prompt settings in ~/.bashrc. On Ubuntu (including WSL), the default ~/.profile already sources ~/.bashrc for login shells. After editing, run source ~/.bashrc or open a new terminal.

Extending PATH

export PATH="$PATH:$HOME/.dotnet/tools"   # append a folder to the search list

Read it as: "new PATH = old PATH + one more folder, and export it so children inherit it." This is the most common line you'll paste from install guides. Always keep $PATH in it, because export PATH="/some/dir" alone replaces the list and breaks ls, git and everything else in that shell.

Aliases

alias ll="ls -lh"        # no spaces around =
alias gs="git status"
alias mv="mv -i"         # safer default: ask before overwriting
alias dc=cd              # typo forgiveness

alias ll                 # show a definition → ll='ls -lh'
\ls                      # bypass an alias once
unalias ll               # remove it

An alias is text replacement of the first word before the command runs. Limitation: it can't put an argument in the middle. For that, use a function.

Functions

mkcd() {                 # make a folder and enter it
    mkdir -p "$1" && cd "$1"
}

Functions take $1, $@ and so on, like scripts. Unlike a script, a function runs in the current shell, so its cd sticks. That's why the official marco/polo exercise is solved with functions loaded by source.

History search

Ctrl-R, then type part of an old command, finds it in your history. Press Ctrl-R again for older matches, Enter to run, or an arrow key to edit first. With fzf's shell integration, Ctrl-R becomes a fuzzy, interactive list.

Installing tools

$ sudo apt install ripgrep fd-find tldr   # Ubuntu/WSL package manager
$ rg "TODO" src/                          # ripgrep: faster grep
$ tldr tar                                # short, example-first help

Package managers download, install and update for you: apt on Ubuntu/WSL, Homebrew on macOS, dnf, pacman. Package names vary. On Ubuntu, fd is packaged as fd-find and the command is fdfind. Check with apt search or command-not-found.com.

The curl | bash warning

# convenient but blind:
curl -fsSL https://example.com/install.sh | bash

# safer: download → read → run
curl -fsSL https://example.com/install.sh -o install.sh
less install.sh
bash install.sh

Piping straight to bash runs code you have never seen, with your permissions. Read it first.

Organising dotfiles

~/dotfiles/              ← a Git repo
  bashrc
  gitconfig
  tmux.conf
  install.sh             ← creates symlinks:
                             ln -sf ~/dotfiles/bashrc ~/.bashrc
                             ln -sf ~/dotfiles/tmux.conf ~/.tmux.conf

Put the real files in one version-controlled folder and symlink them into place. You get one-command setup on a new machine, the same behaviour everywhere, easy syncing, and history of every change. Read other people's dotfiles for ideas, but don't copy whole configs blindly.

Frameworks, AI and terminals (brief)

  • Plugins: zsh users often add syntax highlighting, autosuggestions and a prompt theme. You can install single plugins instead of a big framework like oh-my-zsh, which can slow shell startup. The fish shell has many of these built in.
  • AI in the shell: tools can turn English into commands, process messy text in a pipeline, or act as a whole "meta-shell" (like Claude Code). Same rule as curl | bash: read a generated command before you run it.
  • Terminal emulator: the window your shell runs in (on Windows, usually Windows Terminal). It's worth tuning the font, colours, scrollback and shortcuts.

Connect it to your work

  • .NET global tools (dotnet tool install -g …) install to ~/.dotnet/tools. If the command isn't found, that folder is missing from PATH.
  • Aliases to consider: alias dr="dotnet run", alias dw="dotnet watch", alias pm="python manage.py", alias gs="git status". Run the official top-10-commands exercise first so you alias what you actually type.
  • Function idea: venv() { source .venv/bin/activate; } works because a function runs in your shell (lesson 0002).
  • Security: dotfiles repos are often public. Never put tokens, passwords or export API_KEY=… in them. Keep secrets in a separate, uncommitted file (for example ~/.bashrc.local, sourced if it exists) or a secret manager. Never commit ~/.ssh/ private keys.
  • Work machines: before installing tools on a work laptop or server, check your team's approved-software process. The sandbox is for experiments.

Check yourself

Quiz 1

You add alias gs="git status" to ~/.bashrc but gs says "command not found" in the same terminal. Why?

Startup files are read once, at startup. Editing the file doesn't change a shell that's already running until you source it again.
Quiz 2

An install guide says export PATH="/opt/tool/bin". What goes wrong?

Keep the existing list: export PATH="$PATH:/opt/tool/bin".
Quiz 3

You want mkcd foo to create foo and move into it. Which works?

Aliases can't use arguments in the middle. A script runs in a child, so its cd is lost. A function takes arguments and runs in your current shell.
Quiz 4

What belongs in a public dotfiles repo?

Version-control your configuration, not your credentials. Load secrets from an uncommitted local file or a secret manager.

Sandbox task — 10 minutes

  1. Look first. ls -a ~, then less ~/.bashrc. Find where Ubuntu already defines ll or other aliases. Run alias to list the active ones.
  2. Back up. cp ~/.bashrc ~/.bashrc.bak.
  3. Add three things at the end of ~/.bashrc: one alias (alias gs="git status"), one function (mkcd), and one PATH line (export PATH="$PATH:$HOME/bin"). Run source ~/.bashrc, then test each one. Use type gs mkcd.
  4. Top commands. Run history | awk '{$1="";print substr($0,2)}' | sort | uniq -c | sort -n | tail -n 10. Which ones deserve an alias?
  5. Ctrl-R. Press Ctrl-R, type sort, and recall the command from step 4.

Stretch (official exercises): create ~/dotfiles, run git init, move bashrc into it, and write install.sh using ln -sf. Then solve marco/polo as two functions.

Retrieval practice

In your own words: you got a new WSL install. Describe how a dotfiles repo gets your shell back to normal, and why .bashrc changes need source. Use the words symlink, startup, current shell and secrets.

Model answer (after you have tried)

Clone the dotfiles repo and run its install script, which symlinks each file (bashrc → ~/.bashrc) into place. Bash reads ~/.bashrc at startup, so every new terminal now has the aliases, functions and PATH. A terminal that's already open only sees changes after source ~/.bashrc, which runs the file in the current shell. Running it as a script would apply the changes to a child and lose them. Secrets stay out of the repo, in an uncommitted local file or a secret manager.
