The ORM and template are common work done by a view, not mandatory stops for every request.

  1. URLconf selects. Django checks the root URLconf's urlpatterns in order and stops at the first match.
  2. The view decides. It receives an HttpRequest plus captured parameters and returns an HttpResponse: HTML, a redirect, a 404, JSON, or anything else.
  3. The model describes data. A model class generally maps to a table; the ORM is how the view reads it.
  4. Middleware wraps the trip on the way in and on the way back out.

The 45-second answer

“Django receives the request through its middleware stack, resolves the URL against the root URLconf in order, and calls the first matching view with an HttpRequest and any captured parameters. The view does the application work, perhaps querying the ORM or rendering a template, and returns an HttpResponse. The response travels back through middleware to the client. If no URL matches or an exception occurs, Django uses its error-handling path.”
Common correction: don't say “Django finds the template from the URL.” The URL resolves to a view; the view may choose to render a template.

Example: /jobs/42/

# jobs/urls.py
urlpatterns = [
    path("jobs/<int:pk>/", views.detail, name="job-detail"),
]

# jobs/views.py
def detail(request, pk):
    job = get_object_or_404(Job, pk=pk)
    return render(request, "jobs/detail.html", {"job": job})
  1. Match: the pattern matches /jobs/42/ and captures pk=42.
  2. Call: Django calls views.detail(request, pk=42).
  3. Work: the ORM fetches the Job; get_object_or_404 turns a missing row into a 404 response.
  4. Respond: render combines template and context into an HttpResponse.

Source: Django URL dispatcher, section “How Django processes a request”.

Cards

In Django, what does a URLconf primarily do?

A URLconf maps URL path expressions to view callables. Django checks urlpatterns in order, stops at the first match, and calls that view.

A Django app has path("jobs/<int:pk>/", views.detail), and the view calls get_object_or_404(Job, pk=pk) then render(...).

What happens when a user requests /jobs/42/? Name at least four stages and one alternative to rendering HTML.

The request passes through middleware, then Django checks the root URLconf in order. The matching pattern captures pk=42 and Django calls the view with the request and that value. The view queries the ORM and renders a template, or returns a redirect/404/JSON instead. The response travels back through middleware to the client.

What must a Django view return, and why is “a view renders a template” an incomplete definition?

An HttpResponse (or subclass). Rendering a template is only one way to build it; a view can also return a redirect, a 404 or other error, JSON, a file, or any other response type.

An interview candidate says: “Django looks at the URL and finds the matching template.”

What is wrong with this, and how would you correct it?

It skips the view. The URL resolves to a view via the URLconf; the view then decides the response, which may or may not involve rendering a template.
