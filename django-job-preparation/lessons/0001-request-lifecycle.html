Trace a Django request like an interviewer

Build one durable mental model: explain how Django turns a browser request into a response, without confusing URLconf, views, templates, and models.

10–15 minutes Interview-ready fundamentals Retrieval + feedback
Why this matters for your mission. A clear request-lifecycle explanation is a compact way to demonstrate Django fundamentals in web developer, full-stack, and backend interviews. It also gives you a map for deeper topics such as middleware, ORM performance, testing, and APIs.
The mental model

Request in; response out

Keep this pipeline in your head before you discuss individual Django features:

Request
→
Middleware
→
URLconf
→
View
→
ORM / template
→
Response

The ORM and template are common work performed by a view—not mandatory stops for every request.

Say it clearly

A strong 45-second answer

“Django receives the request through its middleware stack, resolves the URL against the root URLconf in order, and calls the first matching view with an HttpRequest and any captured parameters. The view performs the application work—perhaps querying the ORM or rendering a template—and returns an HttpResponse. The response then travels back through response middleware before Django sends it to the client. If no URL matches or an exception occurs, Django uses its error-handling path.”

This answer is strong because it names responsibilities and leaves room for alternatives: a view can return a redirect, a 404, JSON, or another response—not only an HTML page.

Concrete example

Read the code as a pipeline

# jobs/urls.py
from django.urls import path
from . import views

urlpatterns = [
    path("jobs/<int:pk>/", views.detail, name="job-detail"),
]

# jobs/views.py
from django.shortcuts import get_object_or_404, render
from .models import Job

def detail(request, pk):
    job = get_object_or_404(Job, pk=pk)
    return render(request, "jobs/detail.html", {"job": job})
  1. Match: the URL pattern recognizes a path such as /jobs/42/ and captures pk=42.
  2. Call: Django calls views.detail(request, pk=42).
  3. Work: the view asks the ORM for the Job; get_object_or_404 turns a missing object into a 404 response.
  4. Respond: render combines the template and context into an HttpResponse.
Check your understanding

Answer before reading the explanation

Question 1 of 3

What does a URLconf primarily do?

Choose one answer.

A URLconf maps URL path expressions to view callables. Django checks patterns in order and stops at the first match.

Question 2 of 3

What must a view ultimately return?

Choose one answer.

A view receives a request and returns a response. That response may contain rendered HTML, but it can also be a redirect, error, JSON payload, image, or another response type.

Question 3 of 3

What happens after the first URL pattern matches?

Choose one answer.

Once a URL pattern matches, Django imports and calls the associated view, passing the request and any captured arguments. Middleware is not automatically skipped.

Make it stick

Close the page and explain it

Without looking back, write four or five sentences that answer: “What happens when a user requests /jobs/42/?” Name at least four stages and one possible alternative to rendering HTML.

Reveal a model answer

Django passes the request through middleware, then checks the root URLconf in order. The matching pattern captures pk=42 and calls the detail view with the request and that value. The view queries the ORM and may render a template, return a redirect, or produce an error response. The resulting response travels back through middleware to the client.
